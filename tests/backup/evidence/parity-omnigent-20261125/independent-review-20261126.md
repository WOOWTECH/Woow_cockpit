# O-15 independent code review, 2026-11-26

Scope: the integrated tree at `d0cfef06`, `ha_omnigent.py` and its PostgreSQL helpers. This is a source review, separate from the Omnigent lane's review. It does not replace R7 on a real backup.

The HA PostgreSQL cluster is untrusted. The check already opens it. Conversion additionally calls `pg_dump -Fc` inside that throwaway container. Its container has `--network none`, a read-only root, a `noexec,nosuid,nodev` data volume, a process and memory limit, and no live application's secrets. `ha_odoo.start_ha_cluster` overrides the library and command configuration inherited from HA. `dump_user` chooses an OS identity different from root and the PostgreSQL server identity. These measures contain code that HA's catalog might cause PostgreSQL to run. They do not make HA's query answers trustworthy.

The output cluster is new and uses this device's own PostgreSQL image and schema dump. `restore_trusted_data` obtains a TOC list, selects only `TABLE DATA` and `SEQUENCE SET` for this device's named tables and sequences, and loads that selection as `woowbk_restore`, a role with `NOSUPERUSER`, no role or database creation rights, and only narrowly granted INSERT/SELECT/UPDATE and sequence rights. The schema pre-data and post-data come from the trusted device snapshot. `require_schema`, `require_answers` and `audit_new_cluster` check the result before export. The O-15 tests cover confirmation changes, the selected TOC, and the restore role; they use doubles, not a hostile PostgreSQL instance.

Source-review conclusion: allowing a confirmed O-15 item does not intentionally restore HA's event triggers, FDWs, functions, casts or other schema into the output. The extra exposure is the real `pg_dump` over a potentially hostile source cluster. Its isolation is the security boundary. A compromised PostgreSQL container or malicious behavior in an image library remains outside what source and unit tests prove. Keep O-15 `part` until R7 exercises the actual PostgreSQL image, its TOC, the restricted restore, and post-restore audit with a real backup. If R7 cannot include a superuser-only object, label that case separately as a synthetic lab probe rather than claiming a real-backup proof.

The text TOC selector does not cryptographically bind a displayed line to the archive entry id. A crafted object name containing a newline may make a forged-looking line in a listing, depending on PostgreSQL's escaping. The selector limits names and duplicate trusted entries; the restricted role and single transaction are further gates. R7 should include a real custom archive with such a name and inspect the selected IDs and the result. No production or external action is needed for that probe.

Follow-up: the pinned PostgreSQL 16 image was probed with real custom archives containing newline, carriage return and Tab in table names, each followed by a forged-looking entry. The listing did not create an extra line; the selector chose only the genuine trusted table and the actual restore contained only its row. The tested concern was not reproduced. The reproducible probe and fixed-event record are documented in `../parity-omnigent-r7-20261126/README.md`. O-15's complete crafted-backup confirmation and audit path remains outstanding.
