# HS-15: extra virtual tables in a Headscale backup

Product source: `6ccf7106a73af07e57f9d21a101619b3d7fa2cad`.

Headscale can now process an otherwise compatible database containing extra virtual tables, including an unavailable module. Inside the existing unprivileged, chrooted, network-isolated SQLite child, a private copy is rebuilt using this device's ordinary table/index definitions. Only corresponding ordinary rows are read. Archived virtual modules, shadow rows, triggers, views and executable definitions are omitted. The original schema names remain in the check's confirmation line; without confirmation conversion stops, and another virtual name requires a new confirmation.

Every inserted row's returned values and Python types are checked. Row identities, autoincrement sequences and user_version are retained. Generated/mismatched columns, invalid UTF-8, an unsuitable target schema and a virtual prefix that hides a required ordinary table are refused rather than silently losing data. The new copy is integrity-checked before the existing API-key/policy replacement and final verification. The original files are unchanged. Other SQLite importers retain their existing virtual-table restrictions, including Hermes's separately reviewed narrow FTS exception.

The row-copy check uses SQLite's documented [RETURNING values](https://www.sqlite.org/lang_returning.html); generated columns are detected through [table_xinfo](https://sqlite.org/pragma.html#pragma_table_xinfo). Only one row is inserted/returned at a time.
