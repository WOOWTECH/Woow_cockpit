## Implemented boundary

`emqx_mnesia_checkpoint.erl` traverses ONE OWNER-CREATED native checkpoint.
It does not import, restore, repair, modify tables, or manufacture a checkpoint
from DAT/DCD/DCL. The native owner entrypoint is `emqx_mnesia_export.escript`.
The `--owner-created-checkpoint` argument is an explicit trust precondition,
not a provenance verification mechanism. Never select this exporter based on
archive filenames/metadata and never pass arbitrary checkpoint/ETF from a user.
OTP disk_log decodes terms before callbacks validate them: typed output checks
do NOT make untrusted checkpoint deserialization safe. Native execution belongs
only in the resource-limited disposable owner process below.

Native image is immutable sha256:3f60addfad2bfc6c09400aa48cfbc1b2b2aab04fb6a64d6392c016e02d7fb57b
(EMQX 5.8.9/a8319fe, OTP26/ERTS14.2.5.11). Exporter rejects other ERTS versions.
Native abstract sources actually inspected: emqx_mgmt_data_backup, mnesia,
mnesia_backup, mnesia_bup, MRIA table creation and the five application modules.
The packaged runtime omits development headers; the module carries the pinned
OTP26 file_info record ABI verified from those native abstract sources.

Source module uses disk_log read_only + repair=false. It refuses repaired opens,
errors, unexpected reads and ALL three-element chunk/bad-byte results. This is
stricter than stock mnesia_backup, which ignores bad-byte counts. It checks the
exact native current backup header kind/version and lets native traverse also
validate the header. Success requires traverse returning after EOF, one schema
before rows, and no unexpected records anywhere, including a late unknown row.
Callback refusal uses OTP's {error,Reason} form so no linked-worker crash is
needed for ordinary unsupported input.

Exact table/record/attributes match existing TABLES. Authentication and ACL tables
must be ordered_set, admin/app set. Schema property names are pinned; duplicate
properties, unknown properties, missing/duplicate/extra/late schema, different
attributes/record/type, non-default index/backend/fragment/user properties refuse.
Only verified default/EMQX ETS concurrency storage properties are allowed. MRIA
strips rlog_shard/storage before Mnesia creation; no custom schema code is run.
Only native disc_copies schema is supported. This is structural/private-value
coverage, not validation of the business meaning of each authentication row.
Native backup TABLE tags become the validated record_name tags in typed JSON.

Typed values support only binary/base64, UTF-8 atom strings, int64, proper list,
tuple and map key/value pairs. No list_to_atom or Python ETF decoder. Fun/pid/
port/ref, float, improper list, oversized integer/binary, deep/large trees refuse.
Bounds: input checkpoint 8MiB, JSON 1MiB, binary 64KiB, 4096 rows, 8192 row term
nodes, depth16; existing Python semantic reader additionally enforces unique-value
and aggregate limits. Complete=true is emitted only after EOF and a second
size/hash/stable-inode verification of the source. Empty table is supported only
with its valid native schema.

Both source checkpoint and output must be regular owner 0600 files in owner 0700
directories, without symlink ancestors. Native owner UID is supplied by the
rootless runner, not archive metadata. Output uses exclusive .partial creation,
sync, atomic hard-link publication that cannot overwrite a destination, and
partial unlink. Private JSON reader requires nlink=1 and stable fstat across read;
crash between publication and unlink fails closed until owner resolves it.
Existing output files are preserved. JSON is bound to exact checkpoint SHA256
and byte count by `read_owned_checkpoint_export(raw, table, output_path)`; raw
bytes are used ONLY for hash/length, never decoded. Duplicate/trailing JSON,
wrong hash/table, symlink/hardlink/permissive output refuses.

## Owner invocation requirements

Use `emqx_native_runtime.run_native` to execute trusted code staged in a private
code directory containing the .erl and exporter escript. The checkpoint must have
been freshly generated by Turing's accepted pinned fixture broker; stage only that
bounded checkpoint in an otherwise private writable directory, not any production
volume. Parent code example (OWNER only, not executed on lab by this agent):

```python
with tempfile.TemporaryFile() as diagnostics:
    status = run_native(code_directory, 'emqx_mnesia_export.escript',
        ('--owner-created-checkpoint', 'emqx_authn_mnesia',
         '/work/source.checkpoint', '/work/export.json'),
        writable_directory=private_checkpoint_directory, output=diagnostics)
    # Do not publish diagnostics/JSON/private terms. status==0 is required.
```

Runner checks ONLY targeted rootless/runtime metadata (`true crun`), pins crun
and image ID, uses --pull=never --image-volume=ignore --network=none --read-only,
no capabilities, no privilege escalation, keep-id. Bounds: RAM+swap256MiB,
pids64, CPU10s, file8MiB, container15s, client20s. Native VM +t65536 caps the atom
table; +hmax8388608 caps each default process heap at 64MiB on this image. Overall
RAM cgroup remains necessary. Crash dump goes to /dev/null. These limits may
refuse large valid fixtures; they are not relaxed to force success. HOCON uses
the same hardened runner. Each invocation has a fresh random container name;
finally removes/checks only that name, including timeout/error cases. Anonymous
image volumes are disabled; no production inventory or broad volume prune occurs.

For native checkpoint creation, follow verified EMQX do_export_mnesia_tab:
activate_checkpoint with min=[Tab], allow_remote=false, then backup_checkpoint
and deactivate in an after block; ram_overrides_dump is needed for ram_copies
(but this exporter currently refuses non-disc_copies schema). Turing must serialize
with any existing broker backup and validate the exact table whitelist/record/
attributes first. Require the returned node list to be the sole expected lab node.
Retain checkpoint receipt (owner/provenance, source identity, table, native image,
size/SHA256) privately; all native JSON remains private. A per-table success does
not acknowledge unrelated source files or authorize consumer sealing.

## Cold HA source remains gated

`Capture` is deliberately unchanged: data/emqx/data/mnesia/* still raises
private-source-native-mnesia-unsupported. No default exporter is installed into
read_mnesia. Unknown original source files still refuse. This commit therefore
does NOT solve HA cold-source ingestion or establish commercial completion.

Read-only DETS/disk_log dumps alone are insufficient: schema.DAT supplies table
metadata, DCD is a dump and DCL contains change logs whose replay can change the
final records. Safe term enumeration does not prove transaction ordering, dump/log
coverage, or the consistent final view. No cold-file conversion is implemented.

A future owner conversion requires (a) authenticated open_addon EOF+finish and a
complete immutable cold-file inventory, (b) exact version/storage/schema recovery
semantics validated on synthetic dump+log mutation/truncation scenarios, and
(c) an owner-authorized disposable fixture broker recovering a COPY inside the
same restricted sandbox, never original/production volumes, with all dependencies
and network disabled. Its resulting records and every source file must be
accounted for before the owner generates checkpoints. Broker login/token tests
alone do not prove this source mapping. Until those conditions and real-source
coverage evidence exist, the cold-source gate must remain closed. This is a
future validation requirement, not a claim that broker recovery is already safe.

EOF+finish, resource/private-value limits and cold-source gates remain unchanged.
No service start or secret output is attributed to that read-only parent probe.
Hooke e38f996 is reported as MQTT native target-contract capture only; it is not
integrated or used here to acknowledge other target/source categories. All other
gates remain closed. The checkpoint tests below are synthetic, never those cold
