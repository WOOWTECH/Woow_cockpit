An instance-mode postgres item may contain `ha_database` only for app `n8n` or `litellm`. It is a PostgreSQL database name matching exactly one non-template item in `databases`; LiteLLM requires `litellm`. The complete globals file and all database payloads are still mandatory. Older instance archives omit the optional marker and retain their behavior. Database-scope items reject the field.

For converted HA n8n/LiteLLM archives, conversion reads the actual app DB separately from the catalog's normalized maintenance DB (`postgres`). Existing n8n encryption/credential conversion and LiteLLM salt binding, trusted schema comparison, restricted row loading, migration/count/schema checks remain active.

For HA inplace restore of a marked item, retain the existing PG data volume and every live role/password. Read the application database's current owner, replace only that database, and load under that owner; missing database/owner or changed ownership at readback is a refusal/failure. Other databases (including postgres), additions/deletions, changed owners, and role/password changes after conversion remain current. Archived globals are not replayed. The existing pre-restore safety capture remains a complete instance with all roles/passwords and full current digests; failed import rolls back from that unmarked safety snapshot and verifies its digests. A marked conversion payload cannot itself be passed as an automatic rollback source.

Fresh HA restore explicitly uses the full conversion-time instance snapshot (roles/passwords included) and requires the normal freshly initialized-cluster guard. It does not merge with later state. Ordinary restores and old/unmarked HA instance restores retain the complete-instance restore path. Converted manifests contain no source-device data digest; this does not weaken app conversion checks, health checks, or safety/rollback digest comparisons.

No flows.py/kept.py contract change is needed. No host install, host container/service command, real-device change, or real acceptance claim in this patch.

Selective HA inplace import also retains current declared application secrets so a database password rotated after conversion still matches the retained live roles. LiteLLM's salt is the exception: it is replaced with HA's salt because it encrypts the imported rows. Fresh restores and ordinary restores keep their existing archived-secret behavior.

The same selective boundary retains every current declared config file: EnvironmentFile entries, database URLs and referenced password files must keep matching those live roles. LiteLLM's HA salt remains a separate declared secret replacement. Fresh, ordinary and safety rollback restore config files from their respective full snapshots as before.

Review P2: a marked instance may additionally carry validated `ha_access` facts (database/schema/data-object owners, direct table/sequence/column privileges including grant options, and installed extension names/versions/schemas). Only n8n public or LiteLLM public/woow_platform are accepted. The facts contain no SQL or program definitions. Selective restore captures these facts again from current live data; fresh HA restore uses captured conversion facts and refuses older marked conversions without them until reconverted. Ordinary and unmarked restores retain their prior behavior.

Before selective DROP, verify all required roles and installed extension control definitions/expected versions/dependencies and a bounded dump TOC. Preseed installed extensions through fixed administrator commands in the new empty database, remove only their definitions/preseeded schema creation from the ordinary-role dump load, and suppress archive comments/security labels. Extension COMMENT statements cannot fail under an ordinary DB owner. After load, restore access only for intersecting legitimate moved data objects and verify owners/ACLs/extensions plus reads as the granted roles. Never recreate LiteLLM L-38 omitted schemas/tables or replay program definitions to recover their access. Full unmarked current safety rollback still restores all original data/owners/ACLs/roles/passwords and verifies its complete digest.

New table/sequence names with no established current ownership/access policy refuse BEFORE DROP; they do not inherit guessed grants or PUBLIC access. New columns can use current table-wide rights, including inherited rights. Ambiguous column-only grants refuse before DROP. A same-name ordinary/partitioned relation-kind change fails after load and invokes full current safety rollback instead of silently filtering ownership/access checks. Actual granted-role SELECT * probes and exact ownership/ACL/extension comparisons remain active.

Before conversion and selective restore, establish the running app endpoint and bind its host/port to the trusted declared local backend. Before safety backup or ordinary restore stops anything, use a short TempObjects lifecycle to prepare a stopped app and its declared dependencies and read its connection. Preregister stop intent before any start; cleanup completes on success/error/cancel and BEFORE later restore restarts services, preserving initially running dependencies. Unresolved cleanup blocks continuation. n8n consumes Nash's single vendor resolver/unique main selector. LiteLLM reads the actual proxy DATABASE_URL plus bounded declared YAML/CLI overrides, not POSTGRES_DB initialization settings; unknown overrides refuse.

Independently compare next-start inputs against conversion inputs. Only known password-only changes in declared Quadlets/config/EnvironmentFiles or known password secret/file targets are retained. An applied database change and an unapplied database/host/user/file-reference change both require applying settings and reconversion before mutation. Password rotations proceed; a running endpoint alone is never claimed to validate unapplied files. Full fresh restore uses captured roles/access/config by explicit snapshot semantics and never merges stale archived roles into an existing live instance. Ordinary single-DB/unmarked restore behavior is unchanged.

The trusted safety handover is recorded explicitly even when its stopped-unit list is empty (an application already stopped before preflight). Only the marked HA cache branch consumes that receipt, once. It rechecks next-start inputs and reuses the established endpoint instead of starting/re-probing the app after safety capture. Ordinary handover/restart behavior stays unchanged. Both apps have an actual adapter preflight→empty handover→restore regression proving no late endpoint read/start and no deferred callback stopping the restored app.
