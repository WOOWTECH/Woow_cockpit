# Podman 備份與還原：實作團隊執行交接

> 2026-11-13 補充：本文是 2026-11-12 的規劃與交接文件，保留作為紀錄，內容以當時的視角撰寫。第一階段已實作並在兩台實驗室設備驗證（單一加密備份檔、下載與跨設備上傳還原、還原前備份與自動回復、背景作業、緊急金鑰），實際做法、限制與驗證結果見 [backup.md](../backup.md)、[CONTRACT.md](CONTRACT.md) 與 [current-state.md](../current-state.md)。
>
> 原始狀態：規劃，尚未實作。更新時間：2026-11-12。產品範圍為 Podman 應用套件；既有的 Cockpit「備份還原設計預覽（示意）」只模擬畫面，沒有備份後端。此文件可交給另一個團隊執行；不應把示意頁、單元測試或既有應用腳本誤稱為完整產品。

## 已確認需求

- 客戶可從 Cockpit 獨立頁面選擇已支援的 Podman 應用，建立備份，預設儲存在本機；可以下載**一個可獨立攜帶的備份檔**。
- 客戶可在原設備，或在另一台**相容設備**，選取／上傳該檔，先了解內容與影響，再完成還原；先做單個應用的完整閉環，再逐應用擴充。
- 參考 HA backup 的清楚流程，不引入 HA Supervisor 對 add-on／整機的假定。線上升版及裸機重建不是第一階段。
- 必須提供品牌一致的 RWD 頁面、權限、明確錯誤、背景進度；一個 Podman 應用可以包含多容器、資料庫、檔案、密鑰、網路及依賴。
- 要設計並驗證單檔加密與金鑰保管；不可把 restic repository 裡的一個快照當成可獨立下載的完整備份。

## 執行原則與基線

1. 本機現況為 Ubuntu 24.04、Podman 4.9.3、Cockpit 362；正式安裝後續以執行當時實測版本為準，不能以本文件取代調查。
2. 所有設計及測試先在臨時測試帳號、容器、volume 與隔離網路或獨立 VM 執行，禁止拿正式應用當故障注入對象。正式機現存 Podman 擁有者、Quadlet、資料卷與 timer 不得作未經設計的批次遷移或 prune。
3. 從實際 unit、UID、容器 image digest／mount 和 repo commit 建立已核實清單，需遮蔽憑證；查不到的應用標「未支援／未確認」，不得讓使用者誤以為有完整保護。
4. 以原生 DB 備份或經證實的停寫流程取得資料一致性；不要直接把運作中的 PostgreSQL 目錄打包，或將一般 volume export 誤稱為應用一致備份。
5. 交付以端到端行為與證據為準：建立、下載、帶到獨立目標、上傳、驗證、還原、啟動、讀取業務資料。成功備份、checksum 正確及容器 running 各自不能代表已完成完整還原。

## 團隊拆工與依賴

| 工作 | 邊界與交付 | 可併行／依賴 |
| --- | --- | --- |
| A 協調與規格 | 維護本清單、狀態、受測版本矩陣、app manifest/schema、API 與安全責任；整合其他工作並決定一次提交範圍。 | 最先凍結接口，持續整合；避免多人同改安裝器。 |
| B 應用盤點與 adapter | 從實際執行的 unit／image／volume 找到真實來源；選一套可用測試資料的多組件應用，定義固定命令、備份前後、資料一致性、健康／業務測試與失敗恢復。既有腳本需逐段審核，不能任意從備份檔執行。 | P0 可與 C/D/E 並行；第一個 adapter 依 A 的 manifest、C 的執行介面。 |
| C 後端工作引擎 | 後端 job 與本機儲存、受控 privileged helper、操作審計、應用／儲存庫互斥鎖、持久作業狀態、啟動後異常恢復；禁用使用者任意 shell。 | 和 B/D/E 並行；先確立 A 的契約。 |
| D 可攜檔案與安全 | 比較現成審查過的加密與封裝方案，設計版本化 manifest、驗證和受限制安全解包；實作無原 repository 的單檔下載／上傳與封存風險測試。 | 可先做獨立 PoC；與 C 定義串流、私有暫存、錯誤及 key 介面。 |
| E Cockpit 頁面 | 以現有設計示意為視覺參考，建立**與示意頁分離**的正式 package，接入已核定 API；上傳下載、大檔處理、預檢、確認、進度、結果、斷線重連、無權限狀態與 RWD。 | 使用 A 契約和 mock 並行開發；最終必須接 C/D 以真正資料測試。 |
| F 驗證／安全審查 | 建立獨立來源與目標、測試資料及版本紀錄；驗證資料可用與破壞情境；審查安全及測試證據。 | 與設計並行制定測試；端對端需 B–E 完成。 |
| G 整合與發布 | 收斂檔案清單、安裝/升級/回退、bootstrap 依賴、授權 NOTICE、文件與 CI，合併前校驗來源與部署；由單一整合者持有 `scripts/manage.py` 等共享檔案。 | 依賴各工作結果；先在乾淨測試設備演練，正式發布再按實際授權範圍操作。 |

上述為職責而非預先指定人員。分派時使用獨立分支或工作目錄，先公告檔案寫入邊界與 API 版本；代理不要同時改同一個共享檔案。交接每一成果需包括 commit、已測版本、執行方式、結果和未測項。

## 施工順序與凍結契約

### 0. 確認與測試環境

- P0-1：不輸出機密地盤點這台機器各應用的部署定義、owner、DB、volume、bind mount、image、相依、現有備份和 timer；確認候選 repo 確實對應部署。
- P0-2：準備兩個隔離的 Ubuntu／Podman 環境（兩台機器、兩個 VM，或能證明獨立儲存／使用者命名空間／無原 repository 的環境）；明確註記模擬環境與真實跨機界線。
- P0-3：挑選包含資料庫及檔案的代表性應用，使用合成資料與明確可核驗的 sentinel；確認適合複製、無外部觸發／付款／通知與可接受的測試操作。尚未選定應用，不可暗示所有套件均已適配。
- P0-4：訂定相容矩陣（OS／CPU／Podman／DB／應用版本、image 取得、UID/GID、檔案權限、架構、網路與 secret）。新機可使用不同 UID，但其映射必須測通；不宣稱任意不同架構自動可用。

### 1. API、資料模型與安全契約

- 應用 adapter 由受信任安裝包提供並以固定識別子註冊；至少定義版本、偵測、預檢、備份、恢復、清理、健康與功能驗收、失敗可回退／停機條件。不得從使用者上傳的備份檔執行任何程式或 adapter。
- 受控 helper 的每個請求只接受固定操作、已註冊 app ID、受控備份／作業 ID 和有界輸入；作業返回穩定 JSON 狀態及錯誤代碼。身份及提權沿用 Cockpit，後端逐次驗證，UI 隱藏按鈕不構成授權。
- 作業狀態至少包含 ID、使用者、目標、階段、開始／更新時間、已取消或需人工處理、實際錯誤碼與脱敏紀錄；確保單一應用並發互斥、同一請求去重。不要在監管鎖之外同時操作既有備份 timer。
- 區分 `備份成功`、`格式／解密認證通過`、`資料完整性通過`、`隔離還原演練通過` 與 `應用功能通過`。只有實際取得的證據才可顯示。
- API 凍結需記錄請求/回應 JSON schema、作業狀態圖、錯誤碼、上傳/下載流與權限、manifest 版本、adapter 責任，並含正反例與相容性政策。先核實 Cockpit 可用傳輸能力與 CSP，不承諾無法驗證的下載上傳方法。

### 技術決策紀錄：單檔優先與映像

目前規劃有兩條候選路徑，技術尚未定案：

| 路徑 | 優點 | 需要證明的代價 |
| --- | --- | --- |
| 直接一致性資料集 → 壓縮 → 經審查工具加密 → 本機單檔 | 成品直接可下載、目標不依賴來源備份庫，符合首版核心流程。 | 每份完整檔的容量及耗時；要驗證大檔、加密/認證、斷點、格式演進與安全解包。可將 `tar + zstd + age` 作其中一個 PoC 候選，而非指定為已定案格式。 |
| restic 儲存庫快照 → 讀回一致性資料集 → 匯出加密單檔 | 利用快照及去重；適合以後評估排程與保留。 | 增加資料讀回、佔用空間與維運複雜度；快照本身不是自含單檔。 |

建議先以直接單檔完成受控 PoC，同時用同一組資料量比較 restic 路徑，按真實效能、成本與安全審查選擇；不可把建議誤認為功能已實作。[age](https://github.com/FiloSottile/age)、[restic 還原文件](https://restic.readthedocs.io/en/stable/050_restore.html)。

首輪目標以已測試的同 OS 家族、同 CPU 架構與相容應用／資料庫版本為基線。測試無網路狀態，將受試應用必要映像封存於備份檔或事先交付到目標，並記錄選擇；缺映像時預檢不得說明可離線還原。跨 CPU 為另行驗證範圍，OCI index 與個別平台映像 digest 須分別處理，不能以 tag 相同就保證可用。[OCI image index](https://github.com/opencontainers/image-spec/blob/main/image-index.md)。

下載檔的解密材料需獨立保管；加密認證可偵測檔案遭修改，但不自動證明來自可信設備。必要時應另設可信簽章及發行／輪替流程。對外來檔案即使能解密也維持不可信輸入；**完整認證與預檢通過前不可切換正式資料**。

### 現有框架的安全缺口：先驗證、再依賴

- 既有服務管理依 Cockpit 提權執行 root helper；這不構成管理員之間的租戶資料隔離。若需逐使用者或逐 app 隔離，必須先定義與測試授權模型。
- 不得信任前端送來的 username 作為稽核身分。既有服務稽核未證明可追溯原始登入者；下一團隊應先驗證可用的 Cockpit／系統授權上下文，確保可歸屬的審計；無法證明時不得宣稱完整稽核。
- 既有 helper 的鎖只協調遵循同一協議的操作，無法阻止其他頁面、手動指令或 timer。必須整合或阻擋相同一致性群組的外部操作；不能聲稱此鎖自動保護全部路徑。
- 安裝器既有逐檔備份和回退不等於整體交易及斷電原子性；執行團隊需複核安裝／回退並行鎖、來源樹信任、symlink 與 TOCTOU 競態、父目錄同步和意外中斷測試。不要把低權限可修改的 checkout 直接當作 root 信任根。
- 上傳採不透明 ID 與受限私有暫存、逐使用者及全機容量／數量／時限限制；下載只提供已核定且重新授權的固定物件。驗證是否能在 Cockpit 362 安全串流大檔；若需另設端點，須同等落實驗證、授權和 CSRF 防護。
- 惡意封存解析要限制檔案數、檔案大小、解壓總量／比例／層數、時間、記憶體及 KDF 成本；目錄 FD／不跟隨連結等防競態機制須依實際系統驗證。備份來源內的應用設定、資料或資料庫還原可能在日後啟動時執行行為，因此先隔離網路與正式外部服務驗證，不能承諾惡意資料絕對無害。

### 2. 先完成第一個可攜閉環

1. 受管理 adapter 對測試應用進行資料一致備份，得到設定、DB、持久資料與依賴清單；必要步驟失敗時不得發布成成功檔。
2. 以現有可靠工具設計版本化、加密且具認證的自含檔；格式和安全工具先以 PoC 比較，避免自行設計密碼學。加密密碼不出現在 URL、命令列、日誌、環境持久狀態或 Git。
3. 本機保存，僅在已驗證的臨時檔完成及安全發布後列出；測試權限、容量、缺空間、中斷、清理及對瀏覽器下載的實際支援。
4. 將產生的檔**下載後實際傳到獨立目標**；不依賴來源 repository 和來源目錄，於新目標上傳，核對格式、解密、認證、檔案完整性、需求、空間、image、UID/GID、外部依賴與覆寫影響。
5. 在隔離測試環境建立新空卷和新 DB；拒絕非預期的路徑、符號鏈接、硬連結、裝置檔、路徑穿越、解壓炸彈及未知版本。依 adapter 確定的順序還原，完成資料和應用實際驗收。
6. 必須測試錯密碼、偽造／截斷檔案、缺 key／image、版本不符、權限不足、空間不足、服務無法停止／啟動、DB dump 失敗、取消及中斷；結果需要可解釋，不能誤報成功。

### 3. 原位還原與 UI 產品化

- 取得明確目標與覆寫影響；產生還原前保護點並確認可讀。還原到新空卷／新 DB，依應用可驗證方式切換；若無法安全取得保護點或不能判定目標，拒絕開始。
- 備份／還原時保持原始服務運行狀態有明確契約，系統異常後能明確恢復或要求人工處置。切換後已經發生新寫入、外部通知或交易時，禁止假定舊卷回指可無損撤銷。
- 使用固定帳號和 rootless UID 對映；避免將宿主機憑證及未必要資料帶入其他設備或展示在網頁；跨機必須處理 hostname、ports、外部資料與身分衝突。
- 先使用 fixture 測 UI，再用測試應用連接真正後端；以不同管理權限、桌面／平板／手機、網路中斷重連、大檔與短視窗走完整流程。不能把 mock 結果當作真實備份。

### 4. 擴大支援應用

每個 app 需要一份受審核清單與端到端還原證據，狀態逐項顯示：`未盤點`、`僅可偵測`、`可建立`、`原位驗證通過`、`跨設備驗證通過`。n8n queue/Valkey 與加密金鑰、Odoo DB/filestore、Nextcloud DB/data、LiteLLM DB/金鑰、Hermes 必要 DB dump 失敗、Omnigent 共享代理狀態等需各自設計；此處為待驗證重點，不代表現有腳本已可靠。

## 各應用的優先研究與已發現風險

以下是對**候選 checkout 的靜態檢查**，不等於現行正式設備已受影響，也不是成功還原證據。先對應實際部署和目前 timer 的來源 commit，再決定是否修正原應用 repo。建議同時先檢查 Odoo 業務 DB 覆蓋風險，並以 LiteLLM 或其他具備隔離測試條件的應用作為首個單檔 PoC；選擇以資料能否完整偵測和安全測試為準。

| 應用 | 必要盤點和待驗證風險 | 驗收重點 |
| --- | --- | --- |
| Odoo | 候選 `Woow_podman_odoo` 的腳本看起來只 dump 名為 `postgres` 的 DB，但先前盤點的 timer 指向另一份 `migration-w2/Woow_podman_odoo`，不得混為一談；核對真實業務 DB 名稱、每庫 filestore、addons、roles。 | 至少兩個不同名稱業務 DB 與附件；逐庫缺失或 dump 失敗不得顯示成功。 |
| LiteLLM | 既有候選 restore 有直接重建 DB、缺 checksum／salt 僅警告的風險；確認正在執行的版本與 DB、設定、必要金鑰配對。 | 隔離新 DB，驗證路由與受保護資料解密；錯 salt、缺必要 key、restore 失敗需阻擋。 |
| n8n | queue、DB、Valkey、runners、密鑰、自訂節點和外部 binary data 的一致性；停容器不等於佇列排空。 | 工作流程、憑證與測試佇列一致；排空逾時及外部副作用不得誤報成功。 |
| Nextcloud | 多個 checkout，先確認實際來源；維護模式、cron、Office、DB、data、config、apps／外部儲存的寫入者及版本。 | 測試登入、文件、檔案與資料庫一致性；必要 config/data 缺失不可視為完整備份。 |
| Hermes | 候選腳本對 DB dump 失敗可能只警告，還原可能留下混合世代；確認 SQLite、volume 真實名稱及 PostgreSQL／Redis 是否為必要狀態。 | 缺必要項須失敗；還原 SQLite、workspace、秘密配對，禁止跨世代混搭。 |
| Omnigent | 需核對 PostgreSQL、server 資料、runner 與其他服務共享的 pi-agent 資料／skills／sessions，以及全部寫入者。 | 無法協調共享卷寫入者時不得宣稱完整還原；以隔離身分驗證 runner、任務和 artifact。 |

以上風險的程式來源與更完整候選清單見 [詳細設計](design-research.md)；若審查發現有另一份實際部署，應按其程式與實測結果重評，不得將候選腳本的結果直接套到正式環境。

## 驗收與交付檢核

- 在來源測試應用寫入已知 DB 記錄和檔案；透過正式頁建立備份、實際下載；於另一台相容目標上傳該檔，無來源目錄和 repository，輸入正確還原材料，啟動並比對 DB、檔案與至少一個真實使用者流程。
- 來源與目標的 CPU、OS、Podman、DB／應用版本、磁碟、UID/GID、網路與 image 取得均記錄；測量資料量、耗時、峰值空間、停機與 RPO/RTO，結果僅對受測環境有效。
- 在來源目標均為測試環境時執行失敗注入及惡意檔測試；出現不完整 dump 或認證失敗，UI 與 job 都不得標成成功，正式服務不受影響。
- 驗證背景作業在瀏覽器關閉後仍可查，重連不重送；中途重啟後能辨識先前狀態，不自動重播破壞性操作；測權限與敏感資訊洩漏。
- 安裝器 `plan/install/verify/rollback`、缺少依賴和既有設定處理均在隔離新設備驗證；CI 包含上述可自動化的安全與回歸測試。記錄開源依賴授權，尤其若重用 GPL UI 程式碼須審查重新散布義務。
- 示意頁不得在正式頁被誤認為真實備份；上線時要處理示意入口的移除、保留或標示。

## 已知問題、工作假設與不阻擋的選項

- 確定：本機預設保存、單檔下載、另一相容設備匯入還原、Podman 為主。NAS、雲端、保留份數、排程策略均非已確認的第一版承諾；可先規劃但不要擋第一個可還原閉環。
- Restic 是評估候選，非既定唯一方案；本機目前未找到 restic 執行檔。需先比較可信任的可攜檔案格式和儲存引擎、套件來源、安全更新和離線復原方式。
- 2026-11-12 只讀檢查根分割區約剩 35 GiB；空間會變動，實際工作前重新查詢，估算來源、加密輸出、暫存、新舊卷和還原保護點的峰值需求。
- 為保障資料，本機備份檔可下載到獨立位置；備份與源資料在同一顆磁碟時，不能抵抗該磁碟故障。此為保存位置的實際限制，不應把「可下載」誤說成已完成異地備份。
- 待設計而非阻擋啟動：加密 key 生命週期、具體可攜格式、哪些映像須納入或能離線取回、相容矩陣、第一個 app、各服務 RPO/RTO、可接受停機、排程和既有 timer 遷移。用測試資料先建立 PoC，在正式承諾前再以實際證據定案。

## 指揮用交接提示詞

> 請以本文件及 `reports/Podman備份還原設計.md`（現為 [design-research.md](design-research.md)）為規格，建立並協調多代理團隊，明確分配 A–G 工作、共用 API 與檔案寫入邊界。目標是在 Ubuntu/Cockpit 管理 Podman 應用：預設本機備份，可下載一個完整加密檔，並可在另一台相容設備上傳還原。先在兩個隔離環境以一個含資料庫與檔案的測試應用完成真實端到端閉環及故障測試，再逐應用擴充。不得對正式資料做破壞性測試，不得將示意 UI、單純快照或 checksum 宣稱為完整還原成功。請持續報告各團隊成果、實際驗證、未驗證範圍與剩餘工作；對未支援 app 明示限制。不要直接執行備份檔中所含程式或將密碼寫入日誌／Git。明確記錄版本、測試資料、檔案存取及開源授權。需要正式切換或可能影響現行服務時先根據當前授權與實際影響判斷，提出具體可審查方案。
