# Cockpit Podman 應用備份與還原中心規劃

日期：2026-11-12；狀態：設計提案，尚未實作或完成備份／還原演練。

## 1. 結論、邊界與假設

建議以獨立 Cockpit package 提供「備份與還原」介面，以受控工作執行器及**應用 adapter** 組織 Podman 多服務備份；先以 restic 做儲存引擎 PoC。使用者已確認預設儲存在本機，並要求可下載單一可攜帶的加密備份檔，在另一台相容設備上傳、匯入並還原；體驗參考 Home Assistant backup。此需求列為第一階段核心驗收，具體格式與實作方式仍待 PoC，尚未實作。還原以預檢、還原前保護、建立新資料位置、受控切換、健康驗證及可操作的失敗復原為主線。可借鏡 Home Assistant 的內容選擇、儲存目的地、還原體驗與 integration 備份協作；不能把 HA Supervisor 當成提供跨應用交易回滾的產品，也不能假設 Cockpit package 本身提供服務編排。

**焦點是 Podman 應用備份與還原，不是線上更新。** 不承諾覆蓋整機作業系統、開機磁碟、任意容器、雲端服務、無法取得的映像或所有外部依賴；版本升級、資料庫跨大版移轉及異質架構轉換另案設計。保留擴充性不等於第一期支援。

現有 [roadmap](../docs/roadmap.md) 已指出此套件尚待實作；[architecture](../docs/architecture.md) 描述的服務管理與既有 Cockpit 品牌整合不包含備份引擎。參考主機記錄 Podman 4.9.3、Cockpit 362、cockpit-podman 124，僅作 PoC 相容基準，與新版本文件的功能必須逐項核對，不能假設支援所有新 CLI／Quadlet 能力（[現況](../docs/current-state.md)、[服務管理](../docs/services.md)）。既有跨使用者 helper 的權限、固定命令與實際切換 UID 方式可供設計參考，但新的 API、權限與執行器須另行建置及審查。

## 2. 官方資料與產品比較

### 2.1 Home Assistant 借鏡

[Home Assistant Backups](https://www.home-assistant.io/common-tasks/general/backups/) 描述可選備份內容、不同備份位置、備份加密和還原操作；[integration backup 開發文件](https://contributors.home-assistant.io/core/integrations/backup/) 描述讓整合參與備份／還原生命週期。適合借鏡「使用者選內容 → 看見目的地與時間 → 預檢 → 還原 → 確認結果」，以及由各應用定義資料處理。具體做法仍須依本產品的 Podman 應用、備份引擎及驗證結果設計。HA 熱備可能涉及分時點與整合各自的處理，不能宣稱多服務跨系統為同一瞬間的交易一致快照；還原後健康與業務驗證仍是本設計責任。

## 4. 整體架構與應用契約

```text
Cockpit TLS / 登入 / 管理員授權
  └─ 獨立備份還原頁 → 受控 helper（驗證請求、授權、工作 ID）
      └─ systemd 受控背景工作 → 協調器 + 鎖 + 持久日誌/狀態
           ├─ 受審核應用 adapter → 固定執行檔、systemd、Podman、原生 DB 工具
           ├─ 秘密管理與暫存空間
           └─ 儲存引擎介面 → restic PoC repository / 未來目的地
```

- 靜態 Cockpit 套件使用獨立 manifest；頁面利用 [Cockpit package 機制](https://docs.cockpit-project.org/cockpit-guide/362/guide/packages.html) 和正式 API，沿用登入與管理員提升權限。資料路徑、helper、受信 adapter 目錄與工作狀態不放 Web 靜態目錄；沿用 CSP、離線本地資產。
- 請求以已註冊 `app_id`、目標及工作 ID 指向 root 擁有且不可由應用帳號改寫的配置；拒絕客戶端直接提供 shell、任意命令、任意 uid、任意路徑、unit 或 hook。後端獨立做授權、來源及關聯檢查，不能只信前端。固定執行檔及參數陣列，限制環境變數、工作目錄與網路存取；需要跨使用者時確實切換 UID，使用正確 user systemd runtime／D-Bus。
- systemd 工作單元與持久紀錄使瀏覽器關閉／斷線後仍可查詢；不等於關機或主機故障可自動從任意階段繼續。操作、重新連線和重送使用 idempotency key，避免重複破壞；偵測未完成工作並進入明確的人工／可重試狀態。記錄操作者、應用、快照、階段、時間、退出結果與關聯 ID，不記錄密碼、secret、原始敏感環境、DB dump。
- 使用每應用及共用依賴鎖，並對目的地維護、prune、匯入切換建立適當互斥；鎖涵蓋排程、手動、還原與既有腳本的並行風險。第三方腳本不受此鎖保護時，排程整合須先解決，無法保證就阻擋。
- rootless 與 rootful 的 Podman storage、卷及 systemd 是不同範圍；絕不以 root Podman 查詢當成所有使用者盤點。[Podman Quadlet 文件](https://docs.podman.io/en/latest/markdown/podman-systemd.unit.5.html) 列出 rootless/rootful 不同來源；實際 4.9.3 的可用性以目標機測試。

### Adapter 最小契約（提案）

每個受審核 adapter 帶版本與簽核紀錄，至少定義：`app_id`、支援的應用／資料庫／adapter 版本、擁有者、來源與服務清單、共享相依圖、必要與選用資料、秘密分類、相容矩陣、排程與預估停機；`discover` 唯讀盤點、`preflight`、`quiesce`、`capture`、`resume`、`restore-to-staging`、`validate`、`cutover`、`recover`。此為介面設計，非現存 API。

每項輸出標示必需性、世代 ID、資料時間範圍、方法、一致性等級、大小／雜湊、退出碼與錯誤；禁止以 partial 或 skipped 標示完整成功。共享 DB／卷要有資源所有權及一致性群組，不能因兩個 adapter 互相覆蓋而各自宣稱成功。可選項缺失顯示降級並依政策決定是否可還原；必要項缺失或版本未知為硬阻擋。

相依圖需包含 ingress、app、worker、queue、DB、volume、外部系統；停寫通常先停止入口及 worker、排空佇列，再處理 DB；啟動通常反向並在啟動入口前驗證。實際順序由 adapter 的實測依賴決定，不能只憑 systemd `active`。停止超時、排空失敗或依賴不明均不得繼續改寫資料。

## 5. 備份格式：持續快照與可攜單檔分開

### 5.1 A：持續備份 repository 快照

restic repository 是加密的多檔儲存庫，含索引、資料物件、快照及必要 metadata；依 repository 去重，單個快照並非可獨立搬移的單一完整檔。應用 adapter 先產生一致性資料集，成功後交給引擎寫入，並以 manifest 對應快照 ID、應用與世代。瀏覽快照時展示 repository 位置、最後成功時間、相依內容及驗證狀態；備份即使有快照 ID，也需對必要輸出成功與庫可讀性做檢查。保留及 prune 有獨立鎖、容量與刪除確認；進行中快照與還原保護點不得被誤刪。

### 5.2 B：可攜帶單檔（第一階段核心驗收；格式待設計、待 PoC）

設計獨立格式，例如暫稱 `.woowbackup`，**不是把某個 restic 快照檔改副檔名**。從指定 A 快照完整讀回經驗證的內容，產生一個自含的、版本化、加密且具完整性／認證保護的封裝；另一路徑可由一致性資料集直接封裝。選擇現成經審查的串流封裝與認證加密工具，不自行發明密碼學；格式、加密原語、大小上限、可用程式與兼容策略均待 PoC 和安全審查。未經審查不要宣稱產品格式已定或能離線還原。

建議邏輯內容（不是既定目錄標準）：外層最小版本標頭與加密參數；密文內含 `manifest.json`、各必要資料檔、清單雜湊、adapter 和相依版本、來源時間範圍、匯出工具／格式版本、應用 ID、來源架構／OS／Podman、映像 digest／取得方式、UID/GID 映射需求、密鑰指紋和還原前提。隱藏敏感名稱與機密於密文；即使不加註來源主機名，檔案大小與時間仍可能洩漏資訊。密碼不寫入 manifest，摘要須涵蓋所有資料並由經認證封裝保護；單純 SHA-256 只能檢查誤損，不能證明來源可信。格式支援版本拒絕與明確遷移策略，不默默猜測。

匯出流程：選單一已完成快照及完整應用集 → 預估讀回、暫存、單檔輸出空間 → 以限權位置讀回與檢查 → 串流加密寫臨時檔 → 完整 close/fsync、核驗 → 同檔案系統原子改名發布 → 管理者下載／保存。取消或失敗不發布完整檔；清理明文 staging 並記錄殘留風險。匯入流程：限額上傳到隔離 staging → 檢查外層與版本、解密認證、內部 manifest 和每項雜湊 → 安全解包與相容預檢 → 使用相同還原協調器；可選導入 repository 作為新快照，但不要求它才能直接還原，具體設計待實驗。傳輸應可中斷續傳或清楚失敗；輸入檔不可執行腳本或自帶 adapter。

**第一階段 PoC 核心驗收**：從本機產生並下載單一加密備份檔，在另一台相容的隔離設備上傳、匯入；目標設備無原 repository、無網路，但預先具備可信還原工具及必要映像，使用單檔與獨立保管金鑰解密、列出內容、驗證並還原代表性應用，核對應用及資料；檔案截斷、竄改、錯密碼、未知版本、空間不足和中斷均明確失敗；測量耗時及暫存峰值。工具本身、映像、OS 與硬體是否需打包尚待決，不應稱「單檔包含完整主機」。

### 5.3 一致性與資料項目

至少記錄應用識別、資料時間點或區間、檔案清單、卷及 bind mount 定義、service/Quadlet 來源、映像 digest／架構與可取得性、網路依賴、DB 名稱與版本、UID/GID、SELinux/ACL/xattr 需求、adapter 版本、校驗與必要 secrets 之納入／排除。私鑰是否隨包按政策選擇；排除時明示無法完成還原及需另行提供的秘密。絕不盲目備份整個 rootless storage 目錄或相信 container image 含持久資料。

標示三種等級：**應用一致**（adapter 已按應用契約停寫／原生快照並驗證）、**停機一致**（所有寫入者確實停止後擷取，但仍須驗證資料相依）、**檔案／崩潰一致或未知**（不保證 DB 與多來源一致，預設不可標為可自動還原）。資料來源跨區間時記錄各自擷取時間；避免用單個時間戳掩蓋差異。PostgreSQL `pg_dump` 針對單一 DB 提供一致匯出，但不會自動涵蓋其他 DB、檔案、角色或外部 queue，須另做協調（[PostgreSQL 官方文件](https://www.postgresql.org/docs/current/app-pgdump.html)）。

## 7. 預檢、安全與金鑰

預檢分「阻擋」「需處置／明確確認」「資訊」。結果綁定**來源快照、目標、映像、掛載與設定指紋**和時效；執行前重新驗證，狀態變更即失效，防止確認後被替換。

1. 身分與範圍：操作者已授權；app/adapter 來源受信、目標擁有者、unit、卷及 bind mount 已確認；共享依賴、來源版本和必要資料齊全。外部 API 或硬體依賴不可用時明示並阻擋受影響作業。
2. 來源：解密認證、格式版本、完整性、manifest 與各項雜湊；repository 檢查與快照讀回按政策執行；必需組件／世代不得混合。已知不相容、未知版本、secret 缺失、映像 digest 不存在或 CPU 架構不符為阻擋；不可靜默使用 latest。匯入備份可作為不可信資料，不能由其指定受信指令、覆寫 adapter 或決定目的端路徑。
3. 容量：逐檔案系統計算「上傳檔／解密暫存／新資料卷／DB 還原／還原前保護／引擎暫存／安全餘裕」峰值，避免以壓縮大小估算還原容量；同一檔案系統合計、重複計數清楚。無法估算時保守阻擋或明示需人工提供可靠估值；執行中監測 ENOSPC。
4. 權限與執行環境：rootless UID/GID 及 subuid/subgid、volume driver、檔案權限、ACL/xattr、SELinux label、工具版本、user manager、網路與埠占用；確保容器實際可讀寫。遠端目的地與下載速度需測，來源或管理網路不可用時有明確路徑。
5. 還原前保護：先取得新鮮、同一致性群組、可讀且完成必要檢查的現況保護點；無足夠容量或保護失敗則阻擋一般原位還原。若故障設備無法建立保護點，只提供獨立災難復原流程：明示無保護點與不可逆性、需權限及人工書面／介面確認、隔離新目標；不將此例外包裝成自動回滾。
6. 救援通道：若操作可能中斷 Tunnel、Cockpit、網路或驗證系統，預先驗證本地終端／獨立管理通道；缺少通道時阻擋該類操作。

**封存安全**：解包前限制檔案數、總解壓大小、壓縮比、深度、名稱長度與時間；拒絕絕對路徑、`..`、重複衝突項、指向邊界外的 symlink／hardlink、裝置節點與不允許的特殊檔案；以隔離目錄、不可跟隨連結及 descriptor 相對路徑安全建立。經驗證前不改正式資料，不信任封存內 ownership／權限/執行內容，必要屬性經 adapter 白名單重建。檢查實作與工具需專門安全測試。

**金鑰生命週期**：repository 與單檔都需加密；密鑰取得只透過受保護的互動輸入或 OS 憑證管理機制，使用最小權限、限時可讀的受控 FD 等方式傳遞，避免命令列、URL、一般環境變數、日誌及瀏覽器持久儲存。備份與復原金鑰分開保管，建立離線保管、至少兩名授權保管人或其他經核定流程；密碼遺失表示加密資料無法恢復，介面應明示。規劃新增／撤銷／輪替金鑰及歷史備份的恢復測試，不能假定更改密碼就完成舊檔輪替。備份檔含客戶資料與秘密，下載權限和審計應等同高權限資料；備份加密無法保護已遭入侵、正在解密的主機。

## 8. 執行流程與失敗復原

### 8.1 備份

`已建立 → 預檢 → 鎖定 → 停寫/排空 → 擷取必要資料 → 驗證輸出 → 恢復原工作負載 → 寫入本機 repository 或封裝 → 驗證並發布 → 完成`。第一階段須能從已驗證資料集或快照產生可下載的單一加密備份檔；具體路徑待 PoC。

記錄進入維護模式前的原始執行狀態；所有退出路徑都嘗試依序恢復**原本在執行**的服務及排程，而非盲目啟動原先停止的服務。允許在一致性擷取成功後盡快恢復應用、再進行較長的儲存作業，但僅當 staged 資料本身完整且受保護。必要 dump、卷封存或檢查失敗時記為失敗，刪除或隔離未發布暫存；不得因單一 shell 指令成功而掩蓋 pipeline 的先前失敗。若恢復原服務失敗，顯示「備份失敗／服務需處置」，提供明確狀態與人工處理，不能只顯示備份完成。

### 8.2 還原

1. 選來源與目標 → 解密、預檢 → 顯示應用、目標、預期資料回到的時間、保護點建立方式及服務中斷 → 授權確認。
2. 取得互斥鎖、再次檢查來源與目標指紋 → 封鎖入口／停 worker／排空 → 按 adapter 相依順序停止需要停止的服務 → 建立並檢查現況保護點；失敗則不切換正式目標並嘗試恢復原服務。保護點完成後維持停寫直到切換，若重新開放寫入則保護點可能過期，必須重新建立或重新評估並確認資料損失範圍。
3. 在隔離的新 DB／新空卷／新目錄還原同一世代，檢查必要資料與權限。Podman [volume export](https://docs.podman.io/en/latest/markdown/podman-volume-export.1.html) 只是輸出卷內容；[volume import](https://docs.podman.io/en/latest/markdown/podman-volume-import.1.html) 匯入既有 volume 時不清空現有內容，因此不可用它覆寫舊卷並假設舊檔消失。使用新空卷，且由已審核 adapter 修改服務指向並測試；不同 Podman 版本與卷 driver 須實測。DB 邏輯還原也需建立新庫或依專案提供可驗證的取代流程，不能將 merge 誤認為 replace。
4. 驗證 staging 的資料、版本與設定；在停寫條件下以受控步驟切換引用，記錄每一變更的前後值並落盤，依相依順序啟動 DB、應用與入口；驗證進程、應用健康及代表性業務資料。不同卷與 DB 的切換不是原子交易，逐步寫入操作日誌，故障後可能處於中間態。
5. 完成後顯示「已還原／健康驗證通過」及驗證範圍，保留舊卷與保護點至核准清理；如僅服務 active 或缺少業務檢查，顯示「還原已執行、驗證不完整」，不得顯示全面成功。恢復入口與排程前確認不重放外部動作，例如 queue、通知、付款或 webhook。

### 8.3 失敗與中斷策略

| 時機／事件 | 預定行為與界線 |
| --- | --- |
| 預檢／保護點失敗 | 預檢失敗時不開始停寫；建立保護點可能需要停寫或停止服務，若失敗則不切換並嘗試恢復原服務狀態；列原因及安全重試條件。 |
| 停寫或擷取期間失敗 | 不發布可還原成功；嘗試解除維護並恢復原狀，對無法恢復者告警與提供本地處置。 |
| 來源解密／完整性錯誤或空間耗盡 | 停止寫入，保留有用證據並隔離或清理暫存；舊資料未切換則保留。 |
| staging 還原／驗證失敗 | 不切換；保留原資料，依記錄恢復原服務狀態。 |
| 切換中斷、開機重啟、服務啟動失敗 | 啟動恢復檢查器讀取持久 journal、鎖與實際狀態；禁止盲目重播或自動宣告成功。若尚未產生外部／新資料寫入且 adapter 已證明補償可行，才可依操作日誌回指舊資料；否則隔離服務、保留新舊卷與保護點，要求人工決定。 |
| 切換後已接收寫入或外部副作用 | 回指舊卷可能丟棄新寫入，也無法撤銷外部通知或交易；停止自動回退並呈現衝突、處置選項與資料損失範圍，必要時由人員執行補償／從保護點復原。 |
| 瀏覽器斷線／工作被取消 | 後端工作持續；重連只查狀態不重送。取消只在明確安全檢查點生效；切換等危險階段顯示不可立即取消。主機斷電不等同工作仍在執行。 |
| 原保護點也不可用／管理通道中斷 | 保留現場與日誌，使用替代管理通道或災難復原流程；不得承諾一定能自動回復。 |

## 9. 排程、保留與 RPO／RTO

排程可由 systemd timer 驅動，由協調器持續記錄結果；需處理錯過排程、時區／夏令時間、重疊、維護視窗、離線目的地與通知。新的排程不得與既有腳本同時寫相同應用／庫；遷移既有 timer 前要先確認負責人與替代方案。保留規則須先預覽將刪清單，至少保留可讀的已知良好點與尚在使用的保護點；修剪後抽查，避免以快照數量取代恢復能力。目的地實作和保留數量均待確認。

**示例而非 SLA**：PoC 可比較「每日一次一致性備份，目標 RPO ≤ 24 小時」「代表性單應用還原 RTO ≤ 2 小時」，僅作測量基準。RPO 是事故發生至最新**可用且一致**備份資料時間點的最大資料損失；24 小時排程遇到備份耗時、失敗或離線可能超標。RTO 從事件確認／啟動復原計時，到應用與約定業務檢查通過；須明訂是否含取回金鑰、設備準備、下載映像及人工核准。每次演練記錄資料規模、來源時間、故障時間、啟動／完成、讀寫吞吐、停機、失敗與人工作業；以資料實測後由各服務負責人核定目標。Queue、外部事件和非同步資料應單列最大損失與重放政策。

## 10. 分期、交付與驗收門檻

每一期只在前置條件成立時進入下一期。已確認預設本機儲存，且第一階段須驗收單一加密備份檔的下載、另一台相容設備上傳匯入及跨機還原演練；排程目的地及具體相容條件仍待決。以下是**規劃**，目前皆未完成。

| 階段 | 工作範圍 | 最低可驗收證據 |

## 11. 待決問題與建議順序

1. **儲存細節與故障域**：預設本機已確認；本機目錄、容量、保留週期、排程目的地、是否支援 USB、NAS、S3 或其他目的地，以及目的地數量、頻寬、不可變／離線副本、成本與保管人仍待決。同機資料與備份遭同一故障時無法提供異地保護。
2. **跨設備相容條件**：首階段跨機上傳匯入還原已確認；目標硬體與映像架構、OS、Podman 版本、使用者 UID/GID、主機名稱、網路與外部服務如何對應？離線環境及映像攜帶或取得方式如何支援？
3. **優先應用與資料所有人**：哪個應用可做低風險 PoC、哪個多服務套件代表 MVP？逐一確認 12 項 repo→部署鏈、必要資料、業務驗收人與可接受停機。
4. **一致性及外部副作用**：哪些 queue 要排空、保留或丟棄？外部資料庫、第三方 API、通知／付款和遠端儲存是備份範圍還是人工復原？哪些服務可接受短暫停機？
5. **金鑰與授權**：密鑰納入備份的範圍、復原密碼保管、輪替、失密流程、操作分權、授權保管與稽核保留多久？
6. **RPO／RTO 與排程**：各服務可承受損失與停機時間、維護時段、演練頻率、備份失敗通知接收者？現有 timer 如何遷移？
7. **還原語意**：是否允許覆寫現有應用？保護點無法建立時，誰能啟動災難復原；切換後產生新寫入如何裁決？外部設備、網路、DNS 及 Tunnel 的替代控制通道是什麼？
8. **格式及維護**：單檔格式的封裝／加密工具、最大檔案大小、相容政策、離線還原工具、供應鏈與授權義務如何核定？是否需匯入 repository？

建議先選定第一個驗證應用、明確定義跨機相容條件與排程目的地，再依 P0 蒐證及設計測試環境。預設本機儲存及跨機單檔匯入還原是已確認需求；具體技術與驗收結果仍待 PoC。
