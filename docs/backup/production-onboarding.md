# 正式應用接入備份的評估（下一階段）

> 2026-11-13 以唯讀方式盤點參考主機 `~/.config/containers/systemd/` 的 Quadlet 定義（未讀取任何密鑰內容，未變更服務）。本文件說明哪些正式應用可以直接使用目前的 `quadlet-postgres` 方式、哪些需要先擴充，以及建議的接入順序。目前**沒有任何正式應用已啟用備份**；每個應用都需要經過審查的目錄項目（catalog entry）與實驗室演練。

## 目前方式已支援的結構

- 由同一個 Linux 帳號以 rootless Podman 執行的 Quadlet 應用。
- PostgreSQL 放在**具名資料卷**，備份時以 `pg_dump` 匯出**單一資料庫**。
- 其他資料放在**具名資料卷**；設定檔是 `~/.config/` 或 `~/.local/share/` 下的**單一檔案**；Podman secrets。
- 備份時只暫停會寫入的服務（`writer_units`），資料庫保持執行以便匯出。
- 全新設備還原時，使用設備上已安裝、經審查的 Quadlet 範本；備份檔本身的 Quadlet 檔只作比對，不會直接安裝。

## 各應用盤點

| 應用 | PostgreSQL | 其他資料 | 主機資料夾掛載 | 本機建置映像 | 評估 |
| --- | --- | --- | --- | --- | --- |
| LiteLLM | 1 個資料庫，具名資料卷 | 無 | 僅 `config.yaml` 檔 | 有 | **可直接接入**：資料庫、設定檔、5 個 secrets；跨設備需含映像 |
| n8n | 1 個資料庫，具名資料卷 | n8n 資料、Valkey 共 2 個資料卷 | 2 個設定檔 | 無 | **可直接接入**：主服務、worker、webhook、runners、Valkey 都列為寫入服務 |
| Hermes | 1 個資料庫，具名資料卷 | 2 個資料卷（含 Redis） | 無 | 有 | **可直接接入**；Redis 列為寫入服務 |
| Omnigent | 1 個資料庫，具名資料卷 | 2 個資料卷 | 無 | 有 | **大致可接入**；先確認 pi 資料卷是否與其他應用共用，共用者需一併暫停 |
| EMQX | 無 | 資料、日誌 2 個資料卷 | 3 個設定檔 | 無 | **可直接接入**（不需資料庫）；對外綁定 192.168.2.46，只適合在已安裝 EMQX 的設備原位還原 |
| Odoo | 以 `postgres` 超級使用者執行，實際業務資料庫由 Odoo 建立，可能有多個 | filestore 資料卷 | 自訂模組資料夾 `~/.local/share/odoo18/addons` | 有 | **需擴充**：資料庫「整個叢集」模式、主機資料夾備份 |
| Headscale | 無（SQLite 在資料卷） | 2 個資料卷 | 設定**資料夾**與入口設定檔 | 有 | **需擴充**：主機資料夾備份；對外埠位址需在目標設備調整 |
| Home Assistant | 無 | Matter 資料卷 | 整個設定資料夾 `~/homeassistant/config-preinstalled` | 有 | **需擴充**：主機資料夾備份；資料量需實測 |
| Nextcloud | 資料庫資料放在**主機資料夾** | 無 | html、data、postgres、redis 共 4 個資料夾 | 有 | **需擴充**：主機資料夾備份、資料庫資料夾重建；使用者檔案量大 |
| Immich | 資料庫資料放在**主機資料夾** | 模型快取 | 相片庫與資料庫資料夾 | 無 | **需擴充**：同 Nextcloud；相片庫可能非常大 |
| OpenDesign | 無 | 2 個資料卷 | 4 個設定檔 | 有 | **可直接接入**（不需資料庫） |
| code-server | 無 | 3 個資料卷 | 含 `~/.ssh`、`~/.gitconfig`、`~/Desktop` | 無 | **暫不建議**：涉及登入金鑰與整個桌面資料夾，需先決定備份範圍 |

說明：目前目錄格式要求每個應用至少一個 Quadlet 檔與服務單元；PostgreSQL 項目可為零，因此 EMQX、OpenDesign 這類沒有資料庫的應用在格式上可以描述，但「沒有資料庫」的應用目前**尚未實測**，接入時需先在實驗室演練。表中「可直接接入」指結構相符，仍須依下方步驟審查與演練。

## 需要的擴充（依優先順序）

1. **主機資料夾（bind mount）**：新增 `data_dirs` 類型。以應用擁有者身分匯出成 tar、還原時以新資料夾取代舊內容；路徑限制在擁有者家目錄內且需列在本機目錄；排除快取等可重建內容；大小與空間預檢。Odoo、Headscale、Home Assistant、Nextcloud、Immich 都需要。
2. **PostgreSQL 整個叢集模式**：`pg_dumpall --globals-only` 加上逐一匯出每個非範本資料庫；還原時重建叢集、還原角色與所有資料庫。Odoo 需要。
3. **資料庫資料放在主機資料夾**：還原時以擁有者身分重建資料夾後讓 PostgreSQL 重新初始化，再匯入。Nextcloud、Immich 需要；也可評估改用具名資料卷。
4. **以 SQL 核對資料**：許多應用的 HTTP 介面需要登入，新增唯讀的資料筆數核對（例如表格列數），用於還原後比對。
5. **主機相關設定**：對外綁定 IP、網域等不能直接帶到另一台設備。正式應用的跨設備還原建議流程為「先在新設備安裝該應用套件，再原位還原資料」；只有範本與主機無關的應用才使用全新部署模式。

## 建議接入順序與每個應用的步驟

1. LiteLLM → 2. n8n → 3. Hermes → 4. Omnigent → 5. EMQX → 6. OpenDesign → 7. Odoo（擴充 1、2）→ 8. Headscale、Home Assistant（擴充 1）→ 9. Nextcloud、Immich（擴充 1、3，並評估資料量）。

每個應用：

1. 由該應用的 repository 提供目錄項目與（若需要）全新部署範本，依 [app-catalog.md](app-catalog.md) 審查。
2. 在實驗室設備部署該應用的正式映像與測試資料，完成同機還原、跨設備還原、失敗回復三項演練。
3. 經同意後在正式主機執行第一次備份（寫入服務會短暫暫停，需選維護時段），確認備份檔可在實驗室設備完整驗證。
4. 若要以正式資料演練還原，需先同意將含客戶資料與密鑰的備份帶到實驗室設備，演練後刪除。
