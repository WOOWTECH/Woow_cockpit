# 備份與還原（管理者指南）

Cockpit「備份與還原」頁為 rootless Podman Quadlet 應用建立備份，預設加密（管理員可選擇不加密，見「加密選擇」）。備份預設保存在這台設備，可下載成一個 `.tar` 檔（2026-11-13 之前建立的備份是 `.woowbackup`），再上傳到同一台或另一台相容設備還原。原位還原前會先建立「還原前自動備份」，還原失敗時用它自動回復（例外見「無法建立還原前備份時」）。作業在背景執行，關閉瀏覽器也會繼續。

> **現況：** 第一階段在兩台隔離的實驗室設備（Ubuntu 24.04、Cockpit 362、Podman 4.9.3、x86_64）以示範應用 `woowbk-demo` 完成端到端驗證；「主機資料夾」（應用擁有者家目錄中、以 bind mount 掛進容器的資料夾）也在實驗室完成情境 D1–D7。2026-11-13 經負責人同意，在參考主機為 19 個正式應用（含 Odoo、Home Assistant、Nextcloud 的主機資料夾）實測備份與原位還原。2026-11-14 以 2026.11.14.1 再實測全部已接入的應用，並接入 Omnigent 與 Cloudflare Tunnel，共 21 個目錄項目，全部通過。結果與各應用使用的方式見 [production-onboarding.md](backup/production-onboarding.md)。
>
> **2026-11-13 之後的加強**：Home Assistant 式的備份檔與加密選擇、內建資料核對、較短的停機、PostgreSQL「整個執行個體」方式、逐項檢查內容的「驗證」、「應用設定」（產生目錄項目）與「清理備份」。這些已在實驗室設備與頁面測試驗證（見最後一節），**尚未在參考主機以正式應用重新實測**。本文的時間與大小都來自實驗室與少量測試資料，只供參考。

工程規格見 [CONTRACT.md](backup/CONTRACT.md)；應用如何加入備份見 [app-catalog.md](backup/app-catalog.md)；安裝、維護與測試見 [deployment.md](deployment.md)、[operations.md](operations.md)、[testing.md](testing.md)。

## 目前可備份的應用

頁面只列出設備上裝有「受信任應用目錄項目」（catalog entry，`/etc/woowtech-cockpit/backup/apps/<應用 ID>.json`）的應用。目錄項目明確列出應用的擁有者帳號、服務、資料庫、資料卷、主機資料夾、應用機密與設定檔；備份只包含這些項目，不會自動備份其他容器。

- 一般安裝（`manage.py install`）不含任何目錄項目，頁面會顯示「尚未設定可備份的應用」。
- 目錄項目可以在頁面「應用設定」由應用的 Quadlet 檔產生草稿，審查後安裝（見「應用設定：產生與安裝目錄項目」），或由管理者手動放置（見 [app-catalog.md](backup/app-catalog.md)）。
- 示範應用 `woowbk-demo` 只能用 `--backup-demo-catalog` 安裝到實驗室設備，**不可用於客戶設備**。
- **正式應用沒有預先提供目錄項目。** 每個應用的目錄項目都要經過審查，並在實驗室完成同機還原、跨設備還原與失敗回復演練後才使用。參考主機上 19 個正式應用的接入紀錄與順序見 [production-onboarding.md](backup/production-onboarding.md)。

此階段不包含：排程備份、NAS 或雲端目的地、root（系統層級）Quadlet 應用、多節點應用、整機或裸機還原。保留策略只有「每個應用保留最新幾份手動備份」（見「清理備份與保留原則」）。

## 開啟頁面與權限

從 Cockpit 側欄開啟「備份與還原」。此頁會讀取所有應用的資料與加密金鑰，所以**只有取得管理員存取權限後才能使用**。未取得權限時只顯示「需要管理員權限」，不載入資料、不執行任何動作；在 Cockpit 頂端開啟「管理員存取權限」後，頁面會自動重新載入。

頁面有六個分頁：「總覽」「備份列表」「從檔案還原」「應用設定」「加密金鑰」「活動紀錄」。「總覽」顯示可備份的應用與狀態（執行中、已停止、部分執行、未部署、異常）、各應用的備份空間、最近的備份、本機儲存空間、金鑰與「預設加密備份」的狀態。「備份列表」的每份備份都標示「已加密」或「未加密」，並有「清理備份」入口。

狀態「異常」表示應用需要處理，原因列在應用下方，例如：

- 應用擁有者的使用者服務管理器沒有啟動（沒有啟用 linger）；
- Quadlet 檔不完整或含有符號連結，或找不到服務；
- 服務被先前沒有完成的還原暫時停用（見「已中斷的作業」）；
- 服務都在執行，但快速健康檢查沒有通過（每個檢查最多等 3 秒，只看回應狀態碼）。

狀態「異常」或「未部署」的應用不能選來建立備份。目錄項目有問題而被略過時，總覽上方會出現「備份設定提示」。

**第一次使用請先到「加密金鑰」建立金鑰並保存緊急金鑰**，否則無法建立加密備份（預設）。不加密的備份不需要金鑰，但內容以明文保存，見「加密選擇」。

## 備份包含什麼

每份備份只包含目錄項目列出的內容：

| 項目 | 內容與取得方式 |
| --- | --- |
| PostgreSQL 資料庫（單一資料庫） | 目錄列出的資料庫以 `pg_dump` 自訂格式匯出；匯出後完整讀取一次，確認可以還原。只包含該資料庫本身，不含角色等叢集層級設定。備份詳情標示「單一資料庫」 |
| PostgreSQL 資料庫（整個執行個體） | 目錄以 `"scope": "instance"` 列出資料庫時：以 `pg_dumpall --globals-only` 保存所有角色（含密碼雜湊）與成員關係，再以 `pg_dump` 匯出每個可連線、不是範本的資料庫；備份時資料庫保持執行。備份詳情標示「整個執行個體」，列出資料庫、擁有者與角色數量（不顯示密碼） |
| PostgreSQL 資料庫（冷備份） | 目錄沒有列出要匯出的資料庫，而是把資料庫的資料卷或主機資料夾整份列入時：資料庫服務也列為寫入服務，備份期間一起停止，資料檔隨該資料卷或主機資料夾整份備份。整個執行個體（所有資料庫、角色、密碼、擁有者與權限）都保留；還原的設備，PostgreSQL 主版本必須與備份時相同。備份詳情中這種應用的「資料庫」顯示「沒有以 pg_dump 匯出的資料庫」 |
| 資料卷 | 目錄列出的具名 Podman 資料卷（`podman volume export`）。匯出後依還原時的規則完整檢查，見「備份檔的內部檢查」 |
| 主機資料夾 | 目錄列出、應用擁有者家目錄中的資料夾（容器以 bind mount 使用的資料夾）。寫入服務暫停期間，以應用擁有者的身分、在他的 rootless 使用者命名空間內整份打包：保留容器內看到的檔案擁有者、權限、修改時間、符號連結與硬連結，以及可保留的延伸屬性；不跟隨符號連結到資料夾外。整個資料夾都會備份，沒有排除規則 |
| 應用機密 | 目錄列出的 Podman secrets 原始內容（例如資料庫密碼、應用金鑰） |
| 設定檔 | 目錄列出、位於擁有者 `~/.config/<應用 ID>/` 或 `~/.local/share/<應用 ID>/` 之下的單一檔案；權限依目錄宣告（最多 0644） |
| Quadlet 定義 | 應用 Quadlet 檔的副本，僅供紀錄；還原時不會安裝備份檔中的 Quadlet（見「還原以這台設備的設定為準」） |
| 容器映像（選用） | 勾選「包含容器映像」時，以 `podman save` 匯出應用使用的映像 |
| 資料核對 | 目錄設定了核對時：應用自己的摘要端點（`http-json`，例如筆數、內容雜湊），以及引擎自己計算的**資料摘要**：資料庫每個資料表與序列的筆數與內容雜湊（`postgres-digest`）、資料卷或主機資料夾每個項目的類型、權限、擁有者、大小、連結目標與 SHA-256（`files-digest`）。資料摘要在寫入服務停止期間計算，與備份內容是同一個時間點 |
| 備份資訊 | 建立時間、來源主機名稱與 CPU 架構、作業系統、Podman 與備份元件版本、備份時暫停寫入的秒數、每個項目的大小與 SHA-256 |

不包含目錄未列出的任何東西，例如目錄沒有列出的主機資料夾、其他帳號的資料、作業系統與 Cockpit 設定，以及加密金鑰本身。以 `pg_dump` 匯出的資料庫執行個體中若還有目錄未宣告的資料庫或角色，作業紀錄會註明它們不在備份中。

### 下載的備份檔是什麼檔

自 2026-11-13 起，一份備份是**一個一般的 tar 檔（格式 2，副檔名 `.tar`）**，和 Home Assistant 的備份類似，任何支援 tar 的工具都能打開。依序包含：

1. `backup.json`：方便閱讀的說明（備份 ID、建立時間、類型、備註、備份元件版本、來源主機名稱、CPU 架構、作業系統與 Podman 版本、是否加密與金鑰 ID，以及每個應用的名稱、擁有者帳號、映像、資料庫、資料卷、主機資料夾、應用機密與設定檔的**名稱**和封存檔大小）。不含任何機密。這份說明**沒有經過驗證**：還原時只以各應用封存檔內、經過驗證的內容清單為準，兩者不一致時視為檔案損毀。
2. `README.txt`：中英文說明，包括在 Cockpit 還原的步驟，以及手動解開的指令。
3. 每個應用一個封存檔：加密時是 `apps/<應用 ID>.tar.zst.age`（以 [age](https://github.com/FiloSottile/age) X25519 加密的 zstd 壓縮 tar），不加密時是 `apps/<應用 ID>.tar.gz`。封存檔裡第一個項目是該應用的 `manifest.json`（內容清單：備份 ID、建立時間、來源設備、這個應用的資料庫、資料卷、主機資料夾、映像，以及每個項目的大小與 SHA-256），之後依清單是資料庫匯出、資料卷與主機資料夾的 tar、應用機密、設定檔、Quadlet 檔，以及勾選時的容器映像（OCI 封存）。

加密的備份只有建立它的設備的金鑰（或該金鑰的緊急金鑰）能解開，`README.txt` 寫有用緊急金鑰手動解開的指令（`age -d -i <緊急金鑰>.txt apps/<應用 ID>.tar.zst.age | zstd -d -c | tar -x`，需要 age 與 zstd）。要還原，請在這台或另一台設備的「從檔案還原」上傳；頁面會完整驗證後才還原，不需要、也不建議手動解開（解開後的內容含應用機密）。每個應用的封存檔各自獨立：只還原其中一個應用時，不會讀取或解密其他應用的封存檔。瀏覽器下載時的檔案類型是 `application/octet-stream`。

下載檔名為 `woowtech-backup-<主機名稱>-<YYYYMMDD-HHMMSS>.tar`，時間為 UTC，含秒數；「下載未加密版本」建立的未加密副本，檔名結尾是 `-unencrypted.tar`。上傳的檔案若符合這些格式（或下面舊格式的檔名）且副檔名與檔案格式相符就保留原檔名，否則改名為 `woowtech-backup-uploaded-<備份建立時間>.tar`。

**舊格式（格式 1，`.woowbackup`）**：2026-11-13 之前建立的備份是本專案自訂的加密檔，開頭兩行文字檔頭（`WOOWTECH-BACKUP/1` 與一行 JSON），之後是 age 加密的 zstd 壓縮 tar，不能直接用解壓縮軟體打開。舊備份會一直可以檢視、驗證、下載與還原，檔名維持 `woowtech-backup-<主機名稱>-<YYYYMMDD-HHMMSS>.woowbackup`。

### 加密選擇

「加密金鑰」頁「加密設定」中的「預設加密備份」預設開啟；建立備份時的「加密此備份」預設依這個設定。關閉時會出現對話框說明風險，勾選「我了解未加密的備份會以明文保存與下載資料庫密碼、API 金鑰與存取權杖」後才會關閉；重新開啟不需要確認。每份備份在列表與詳情都標示「已加密」或「未加密」。

- **加密（預設）**：用這台設備的金鑰加密，下載與保存的檔案都需要金鑰或緊急金鑰才能讀取。
- **不加密**：不需要設備金鑰，任何工具都能直接打開，但**資料庫密碼、API 金鑰與存取權杖等應用機密會以明文保存與下載**，任何取得檔案的人都能讀取，也無法確認檔案在設備以外是否被修改過。關閉「預設加密備份」，或在設定開啟時取消勾選某一份的「加密此備份」，都需要另外勾選確認這項風險。設定的變更會記錄在系統日誌。
- 「還原前自動備份」依「預設加密備份」的設定加密或不加密；設定開啟時，原位還原需要這台設備的金鑰。
- 從其他地方**上傳的未加密備份**無法驗證來源與完整性：預檢會提示，列表標示「來源未驗證」，確認還原時要再勾選「我確認信任這個未加密備份檔的來源」。

設定檔 `/etc/woowtech-cockpit/backup/settings.json` 不存在、損毀、不是由 root 擁有或可被其他帳號修改時，一律視為「加密」。

## 備份如何保持資料一致

1. **先檢查空間。** 保存位置的可用空間須至少為預估資料量的 2.2 倍再加 512 MiB。不足時，作業在暫停任何服務之前就停止（`insufficient-space`）。
2. **讀取資料核對快照**（有設定時）。
3. **短暫暫停寫入服務。** 停止之前先確認沒有不會被停止的執行中容器以可寫入方式掛載應用的資料卷或主機資料夾；有的話備份不會開始（請把它的服務加入寫入服務，或只讀取的容器改用 `:ro` 唯讀掛載）。只停止目錄列為寫入服務（`writer_units`）且正在執行的服務，**以一次** `systemctl --user stop` 停止：systemd 依 Quadlet 的 `After=` 決定先後，其餘同時停止（不再逐一等待；n8n 的 task runner 每個要約 50 秒才停止）。以 `pg_dump` 匯出的資料庫（單一資料庫或整個執行個體）保持執行，以便匯出。冷備份的資料庫本身也列為寫入服務，會一起停止；設定了它的資料摘要時，資料庫在摘要讀完後才停止。
4. **匯出與資料摘要。** `pg_dump` 匯出資料庫並完整讀取檢查（整個執行個體另外保存角色定義，並檢查還原時是否接受它），接著匯出資料卷與主機資料夾、應用機密、設定檔與 Quadlet 檔。目錄設定了資料摘要時，每項摘要在這段暫停期間**讀兩次**，把它要證明的匯出夾在中間（資料庫在匯出前後各讀一次、檔案在匯出前後各讀一次、冷備份的資料庫在停止前連讀兩次）。兩次相同才保存，代表匯出的內容就是摘要描述的內容；兩次不同（例如有目錄沒有停止的服務、排程或資料庫內的工作在寫入），這份備份不保存這一項摘要，作業紀錄會寫出「資料摘要 … 兩次讀取的結果不同」與原因，備份仍會完成，日後還原時這一項顯示「未比對」。以前會保存讀取時間不同的摘要，讓這份備份的每次還原（以及用它當還原前備份時的自動回復）都比對失敗。摘要要多讀一次資料，寫入暫停會比只讀一次長。
5. **立即恢復。** 無論匯出成功或失敗，都會重新啟動剛才暫停的服務：依 Quadlet 的 `After=`、`Requires=` 與 `BindsTo=` 分組（Quadlet 不會為 `Requires=` 自動加上 `After=`，所以需要的服務也會先啟動），可以同時啟動的一起啟動，沒有寫明依賴的服務依目錄的順序；服務沒有啟動時再試一次。匯出失敗、且資料庫在過程中停止時，也會嘗試重新啟動資料庫，再重新啟動寫入服務讓它們重新連線。
6. **檢查資料卷匯出。** 每個資料卷的匯出檔都以還原時相同的規則完整檢查。含有還原時無法匯入的內容（例如指向資料卷外的相對符號連結、裝置檔、應用擁有者的使用者命名空間對應不到的擁有者），或超過 2,000,000 個項目時，備份失敗，訊息指出資料卷與項目；這時應用已恢復執行。
7. **再次確認核對快照**（有設定時）。服務恢復後再讀一次，和暫停前相同才保存；應用在備份前只部分執行時，這次讀取最多等到目錄設定的健康檢查逾時。兩次不同時（例如仍有寫入進行中，或有尚未套用的設定在服務重新啟動時才生效），這份備份不保存快照，日後還原時略過資料比對（結果顯示「未比對」），作業紀錄會說明。
8. **映像在服務恢復後才匯出**，不會延長暫停時間。映像若在備份期間被更換，備份失敗並要求重做。
9. **封裝、驗證後才列出。** 備份檔先寫在私有暫存區（加密時用這台設備的金鑰），再完整讀取（加密時解密）並逐項核對大小與 SHA-256，通過後才移到保存位置、出現在列表。未通過驗證的備份不會被列出。

暫停時間會記錄在備份中，備份詳情顯示為「備份時暫停應用寫入 N 秒」。選擇多個應用時逐一處理，每個應用只在自己的匯出期間暫停。備份完成的結果頁另外列出每個應用的**寫入暫停**（服務停止到全部再次執行）與**無法使用**（第一個服務停止到所有健康檢查通過）的秒數；先前只記錄寫入暫停，例如參考主機上 LiteLLM 記錄的暫停是 15 秒，實際到服務就緒約 70 秒。

參考數字：最終回歸中，示範應用 142 MB 的含映像備份暫停寫入 2 秒，健康檢查端點最長約 2.5 秒無法回應；資料卷約 600 MiB 時暫停 9 秒，最長約 10 秒無法回應。冷備份還要加上資料庫停止與啟動的時間：示範應用的資料庫資料卷冷備份暫停約 4 秒。改為一次停止與分組啟動後，實驗室以兩個各需 15 秒才停止的寫入服務（模擬 n8n 的 task runners）加上 300 MB 主機資料夾，與前一版引擎在同一台設備、同一份資料上量測（2026-11-14）：輔助服務在 Quadlet 檔寫明 `After=<主服務>.service`（參考主機 n8n-runners 的寫法）時，備份的寫入暫停由 39 秒降為 22.6 秒，主服務自己的中斷維持約 6.5 秒；沒有寫明時寫入暫停由 38 秒降為 24.2 秒，但所有服務同時停止、主服務一開始就停，它自己的中斷由 6.6 秒變成 22.9 秒。停止很慢的輔助服務請在 Quadlet 檔寫明 `After=<主服務>.service`，systemd 就會先停它們、最後才停主服務。主機資料夾在暫停期間整份打包，資料夾越大暫停越久：參考主機上 Home Assistant 的設定資料夾（3,344 個項目）與 Nextcloud 的 4 個資料夾（約 970 MB）見 [production-onboarding.md](backup/production-onboarding.md)。

應用在備份前沒有完整執行時，備份後不等待健康檢查；沒有任何寫入服務需要暫停時，暫停時間記為 0。

## 備份保存在哪裡

備份保存在這台設備的 `/var/lib/woowtech-backup/archives/`（只有 root 可存取）：每份備份是一個 `<備份 ID>.tar` 檔（舊格式為 `.woowbackup`），加上一個列表用的 `.json` 索引。「下載未加密版本」建立的未加密副本暫時放在 `/var/lib/woowtech-backup/exports/`（只有 root 可讀），15 分鐘後自動刪除。「總覽」的「本機儲存空間」顯示保存位置、可用空間與備份佔用量，「各應用的備份空間」依應用分計備份的份數與大小（一份備份含多個應用時，依各應用封存檔的大小分攤；舊格式的備份平均分攤並標示「估計」）。其他執行資料的位置見 [operations.md](operations.md)。

**本機備份與應用資料通常在同一顆磁碟，無法防範磁碟故障或設備遺失。** 重要的備份請下載保存到其他位置。

| 列表中的類型 | 來源 |
| --- | --- |
| 手動 | 從「建立備份」建立 |
| 還原前備份 | 原位還原前由系統建立的「還原前自動備份」（不含映像）。每個應用保留最近 3 份，較舊的在之後的原位還原成功後自動刪除；失敗或中斷的還原仍需要的還原前備份不會被自動刪除 |
| 上傳 | 從「從檔案還原」上傳的檔案 |

手動備份可以設定每個應用保留最新幾份，上傳的備份只在「清理備份」中勾選時才刪除；見「清理備份與保留原則」。

## 建立備份

1. 按「建立備份」。
2. 勾選要備份的應用，可一次選多個。狀態為「未部署」或「異常」的應用不能選（頁面會說明原因）。
3. 決定是否勾選「包含容器映像」（見下方），以及「加密此備份」（預設依「預設加密備份」設定，見「加密選擇」）。
4. 可填寫備註（最多 200 字，不可包含換行或 Tab）。
5. 按「開始備份」（不加密時按鈕為「開始備份（不加密）」，「預設加密備份」開啟時還要先勾選確認風險）。頁面會轉到作業進度；可以關閉瀏覽器，稍後到「活動紀錄」查看。完成的結果頁列出備份大小、是否加密、寫入暫停與每個應用的無法使用時間；保留原則刪除了較舊的手動備份時也會列出。

建立備份需要：應用已部署且資料庫服務正在執行、沒有其他作業進行中；加密的備份還需要這台設備已建立加密金鑰。沒有設備金鑰時，頁面上方的提醒不會阻止建立**不加密**的備份。

**何時包含容器映像：** 要還原到無法連網、或取不到相同映像的設備時必須包含。以 `localhost/` 開頭的本機建置映像無法從映像庫下載，要在沒有這個映像的設備還原就一定要包含。包含映像會讓檔案明顯變大：實驗室示範應用含兩個映像約 142 MB，不含映像約 0.15–0.4 MB（依測試資料量）。

## 檢視、驗證、下載與刪除

在「備份列表」或備份詳情可以：

- **檢視內容**：讀取（加密時解密）備份的內容清單，列出格式與加密方式、應用、資料庫與 PostgreSQL 方式（單一資料庫、整個執行個體及其資料庫與角色數量；冷備份的資料庫隨資料卷或主機資料夾）、資料卷、主機資料夾（以 `~/` 開頭的路徑，`~` 是應用擁有者的家目錄；有說明或大小時一併顯示）、映像是否包含、應用機密與設定檔數量、資料核對項目（應用摘要與資料摘要的筆數）、每個應用封存檔的大小，以及與這台設備的相容性檢查。不會變更任何資料。
- **驗證**：在背景完整讀取（加密時解密）整個檔案，逐項核對大小與 SHA-256，**並以還原時相同的規則檢查每個項目的內容**：資料卷、主機資料夾與映像封存（備份內的 tar 檔）、資料摘要清單、資料庫角色定義、資料庫匯出檔與應用機密的大小。結果頁列出各應用檢查了哪些項目（例如「資料卷 1、資料庫匯出 1、應用機密 2」），以及還原時無法保留的內容（例如 setuid 位元）。資料庫匯出檔在驗證時只確認是 pg_dump 的匯出格式（結果頁標示「只檢查格式」）：這台設備建立備份時已由 `pg_restore` 完整讀取過一次，還原時會再完整讀取；上傳的備份則要到還原時才完整讀取資料庫匯出的內容。讀取暫存檔時發生的本機錯誤（例如磁碟 I/O 錯誤）不會把備份標成驗證未通過，作業以錯誤結束、驗證狀態不變。驗證與建立未加密副本時應用都在執行，所以這兩種作業會保留較多的可用空間給應用（檔案系統的 5%，至少 2 GiB、最多 10 GiB），空間不足時作業以 `insufficient-space` 停止，備份本身與它的驗證狀態都不變。通過後列表顯示「已驗證（內容已逐項檢查）」；建立時的驗證或較舊版本的驗證只顯示「已驗證（檔案完整）」。「已驗證（內容已逐項檢查）」代表還原時的內容檢查也會通過；只有與這台設備有關的檢查（應用擁有者的 ID 範圍、這台設備需要的映像名稱、PostgreSQL 版本、目錄項目）仍在還原的「相容性檢查」進行。驗證未通過的備份請勿用來還原。舊格式（`.woowbackup`）的備份也以相同方式驗證。
- **下載**：瀏覽器經由 Cockpit 的加密連線下載備份檔，內容與保存的檔案完全相同（加密的仍是加密的）。「下載」按鈕旁的選單（向下箭頭）列出下載方式：預設是「下載加密的備份檔（.tar）」，與按鈕相同。
- **下載未加密版本**（選單中，只有加密的備份）：對話框說明風險，勾選「我了解下載的檔案沒有加密…」後才會開始：系統在背景解密並驗證，建立一份未加密的暫時副本（每個應用一個 `.tar.gz`，檔名結尾 `-unencrypted.tar`），完成後自動開始下載；這台設備沒有該備份的金鑰時，會先要求輸入緊急金鑰。副本只有 root 可讀，15 分鐘後自動刪除（已開始的下載不受影響），到期前可在作業結果或備份詳情再次下載或「立即刪除」；建立、下載與刪除都記錄在系統日誌。副本中的資料庫密碼、API 金鑰與存取權杖都是明文。
- **刪除**：確認後刪除，無法復原，並記錄在系統日誌；需要保留請先下載。刪除「還原前自動備份」後，就無法再用它回到那次還原之前的狀態。正被作業使用的備份不能刪除；還原作業進行中時，任何還原前備份都不能刪除（失敗時可能需要它自動回復）。

**檢視內容很快，不做內容檢查。** 檢視只讀取每個應用的內容清單；完整的內容檢查由「驗證」與還原作業進行。2026-11-13 之前的版本中，「已驗證」只代表外層完整，刻意改造過資料卷的備份也會顯示已驗證；現在的驗證會發現這種備份（實驗室實測，見「實驗室驗證紀錄」）。

加密的下載檔內含資料庫、檔案與應用機密，請和緊急金鑰分開存放；未加密的檔案請當成密碼一樣保管。見「安全須知」。

## 在同一台設備還原（原位還原）

在「備份列表」選擇備份的「還原」，依序完成：

1. **金鑰**：只有這台設備沒有該備份的金鑰時，才會要求輸入緊急金鑰。
2. **預檢**：顯示整體檢查與每個應用的檢查結果。選擇要還原的應用；未通過檢查的應用無法選擇。預檢不會變更任何資料，也不檢查資料卷與映像封存的內部內容（還原作業會檢查）。
3. **確認**：頁面列出受影響的應用、停機影響與還原前備份的做法；應用有主機資料夾時，另列出會被整個取代的資料夾（`~` 是這台設備上應用擁有者的家目錄）。勾選「我了解還原會停止並覆寫上列 N 個應用的資料」後按「開始還原」。
4. **進度與結果**：結果頁列出健康檢查、**停機時間**（每個應用的服務停止秒數，以及從第一個服務停止到所有健康檢查通過的「無法使用」秒數）、「注意事項」（還原無法保留的內容，例如被移除的檔案權限），以及「備份時」與「還原後」的**資料核對表**：應用摘要逐欄比對；資料摘要每項一列，列出備份時與還原後的筆數（資料表、資料列；檔案、資料夾、大小）與「一致」「不一致」「未比對」。表格上方統計共幾項、幾項一致；不一致的項目可展開查看差異（遺失、多出或不同的資料表或檔案，最多 20 筆）。從這個頁面開始的還原，結果頁也會列出這些應用在備份中的主機資料夾；重新整理頁面後，改以作業訊息與作業紀錄為準。

上傳的**未加密**備份在確認頁多一個勾選項「我確認信任這個未加密備份檔的來源」（見「加密選擇」）。

還原作業依序執行：

1. **解密並驗證**：只讀取所選應用的封存檔（加密時解密）到私有暫存區，逐項核對大小與 SHA-256。
2. **相容性檢查**：內容同預檢，另外完整檢查備份中的資料卷、主機資料夾與映像封存。單一資料庫方式確認資料庫執行個體中沒有目錄未宣告的資料庫（重建資料卷會讓它們遺失）；整個執行個體方式確認備份的方式與目錄相同、備份中的資料庫帳號是可登入的超級使用者、目錄的資料庫帳號是執行個體的初始超級使用者、目前的執行個體沒有不接受連線的資料庫（它們不在任何備份中），以及映像有每個資料庫用到的擴充功能。備份來自另一個帳號的應用時，以「注意」提醒還原後資料會屬於這台設備的帳號。未通過時作業停止，沒有任何變更，也不建立還原前備份。資料庫服務沒有執行而無法確認時，會在啟動資料庫後、任何變更之前再確認。
3. **預先寫入主機資料夾**（有主機資料夾的應用）：應用仍在執行時，以應用擁有者身分把每個資料夾寫到同一層的新資料夾 `<路徑>.woowbk-new-<作業 ID>`；既有的資料都沒有改變。之後只要在停止服務前失敗，這些新資料夾都會被移除。沒有主機資料夾時這個階段顯示「略過」。
4. **保存還原前資料**：停止受影響應用的寫入服務，把它們目前的資料複製到保存位置的 `pending/<作業 ID>/`（不含映像），每個檔案寫入磁碟後才記錄下來；之後才開始變更，所以即使斷電，這份資料也完整。停止的寫入服務**不再重新啟動，直接交給還原**，應用只停止一次。這份資料要等應用恢復執行後（第 11 步）才封裝成「還原前自動備份」，封裝與驗證不算在停機時間內（2026.11.14.2；正式主機上 Hermes 可少停約 66 秒、Nextcloud 約 35 秒）。因為應用一直停著，還原前的資料無法再確認應用回報的核對值（http-json）：只以 http-json 核對、沒有資料摘要的應用，還原失敗而自動回復時只以健康檢查確認回復結果、不比對資料；預檢會以「注意」說明，回復完成時結果的注意事項也會寫出「未比對資料」。需要回復時也比對資料，請為應用加入資料摘要。保存失敗時作業停止，服務恢復，應用資料不做任何變更（見「無法建立還原前備份時」）。資料庫服務沒有執行時，會先嘗試啟動它。接著確認保存位置的空間足以在還原後把這份資料封裝成還原前備份；不足時作業停止、服務恢復、刪除已保存的資料，不做任何變更。
5. 變更前的準備：再次確認資料庫執行個體，有未宣告的資料庫或無法列出時拒絕還原（單一資料庫方式）。接著載入備份中的映像，或從映像庫下載缺少的映像；若映像在備份後更新過，映像標籤會指回備份時的版本（備份包含該映像，或這台設備仍保留該版本時）。這一步失敗時，映像標籤會改回還原前的版本，服務恢復。
6. **停止應用**：以一次 `systemctl --user stop` 停止應用其餘的服務，並暫時停用（`systemctl --user mask`）資料庫以外的服務：資料匯入完成前，它們不會被自動啟動（包括開機時）。
7. **還原資料**：重建應用機密、寫入設定檔、刪除並重建資料卷，刪除資料庫的資料卷。資料卷與映像都以引擎重新產生的乾淨 tar 交給 Podman。主機資料夾與第 3 步寫好的新資料夾對調：原資料夾改名為 `<路徑>.woowbk-old-<作業 ID>`、新資料夾改為原名；原本的內容保留到整個還原成功後才刪除。有檔案的資料摘要時，在這時就與備份時比對。
8. **啟動資料庫並匯入**：先只啟動資料庫，讓它重新初始化。單一資料庫方式以單一交易匯入；整個執行個體方式先確認資料庫確實是新建立的執行個體（初始化時間晚於刪除資料卷）、這台設備的 PostgreSQL 主版本不低於備份時，再還原所有角色（映像建立的超級使用者不重建，而是套用備份時的屬性與密碼雜湊；之後確認它仍是可登入、可寫入的超級使用者），並逐一建立與匯入每個資料庫，包括 `postgres` 與映像初始化程式建立的資料庫（保留擁有者、編碼、語系、權限與範本標記；備份之後才建立的資料庫會被移除）。冷備份的資料庫直接以還原的資料檔啟動。有資料庫的資料摘要時，在其他服務啟動前比對。**任何資料摘要不一致，應用都不會啟動**，作業自動回復；不一致時會再讀一次，兩次讀到的也不同，表示有目錄沒有停止的寫入者還在寫入（例如其他容器或排程），這一項改為「未比對」並列入注意事項，不讓還原與自動回復因為移動中的資料而失敗。
9. **啟動應用**：恢復被暫時停用的服務並啟動：依 Quadlet 的 `After=`、`Requires=` 與 `BindsTo=` 分組，可以同時啟動的一起啟動，沒有寫明依賴的依目錄順序。
10. 健康檢查與應用摘要比對。
11. **封裝還原前備份**：應用已恢復執行後，把第 4 步保存的資料加密（依「預設加密備份」）、封裝並完整驗證成「還原前自動備份」，再刪除保存的資料。封裝前會再確認空間（應用執行中，除了封裝所需，另外保留至少 2 GiB 給應用自己寫入）。封裝失敗、空間不足或作業被要求停止時，還原仍算完成，結果的注意事項會寫出資料保存的位置；系統會在下一次開啟頁面或執行作業時再試一次（空間不足時不寫入，等到有空間才封裝），仍失敗時保留資料，需人工處理（不會自動刪除）。

停止應用（第 6 步）之前失敗時，應用資料沒有被變更：預先寫入的新資料夾被移除，還原前備份停止的服務重新啟動。**第 6 步開始後的任何失敗都會自動回復：** 系統直接用第 4 步保存的資料（先逐項核對大小與 SHA-256）把應用回到還原前的狀態，再把這份資料封裝成還原前備份，作業顯示「已自動回復」（資料夾直接移回原內容，不重新解開）。自動回復不會從映像庫下載映像，需要的映像版本必須仍在這台設備上。若自動回復也沒有完成，作業顯示「失敗」與「需人工處理」，並列出還原前備份 ID，可用它再次還原。

注意事項：

- 還原後，應用回到備份當時的資料；備份之後才寫入的資料會被覆寫（仍保留在這次的還原前備份中）。
- 單一資料庫方式的原位還原，會以備份中的單一資料庫重建整個資料庫資料卷。資料庫執行個體中有目錄未宣告的資料庫時，預檢與還原都會拒絕並列出資料庫名稱；無法列出時也會拒絕（例外見下一小節）。資料庫角色與權限設定，以及執行個體 `postgres` 資料庫中的資料表、函式或排程工作不會保留，預檢以「注意」列出。整個執行個體方式保留角色與所有資料庫；備份之後才建立的資料庫會被移除，預檢會以「注意」列出（還原前備份保留它們）。
- 「預設加密備份」開啟時，原位還原需要這台設備已建立加密金鑰，用來建立加密的還原前備份；設定關閉時，還原前備份不加密，不需要金鑰。
- 主機資料夾是**整個取代**，不是合併：資料夾回到備份時的內容，之後新增的檔案會被移除（仍在還原前備份中）。還原期間新舊兩份內容同時存在，應用擁有者家目錄所在的磁碟需要放得下兩份，還原前會檢查空間。
- 參考數字：最終回歸中，示範應用的原位還原（含建立還原前備份）約 30 秒，健康檢查端點最長約 6.3 秒無法回應；資料卷約 600 MiB 時約 156 秒，最長約 40 秒無法回應。改為預先寫入主機資料夾、一次停止與交接還原前備份的服務後，實驗室以 300 MB 主機資料夾與兩個停止很慢的寫入服務量測（2026-11-14，與前一版引擎比較）：輔助服務寫明 `After=` 時，還原作業 120.6 秒降為 75.5 秒，應用的中斷由三段（合計 30.3 秒、分散在 71.7 秒內）變成一段 26.6 秒；沒有寫明時還原作業 114.8 秒降為 70.0 秒，應用的中斷由兩段（合計 29.0 秒、分散在 70.1 秒內）變成一段 37.6 秒。實際時間取決於資料量與映像。

### 無法建立還原前備份時

還原前備份建立失敗時，還原會停止且不做任何變更，結果頁說明「還原在變更任何資料前失敗，應用維持原狀」。這通常是因為應用已經無法運作（例如資料庫無法啟動），所以也無法備份它。

- **還原的就是一份還原前自動備份時**（例如先前的還原中斷後，用它回到還原前的狀態）：系統仍會先嘗試建立新的還原前備份；建立不了就直接還原，不需另外選擇。確認頁會先說明可能沒有新的還原前備份，結果頁註明這次沒有建立。實驗室已在強制終止與重新開機兩種中斷後實測這條路徑，資料都與還原前相同。
- **還原其他備份時**：失敗的結果頁會提供「不建立還原前備份，直接還原…」。按下後回到還原精靈，確認頁多一個勾選項「我了解這次還原可能沒有還原前備份，失敗時無法自動回復」，勾選後才能開始。作業仍會先嘗試建立還原前備份，建立不了才直接還原；「作業內容」記錄這個選擇。

風險：沒有還原前備份時，還原失敗**無法自動回復**，應用可能只還原了一部分。資料庫沒有執行時，系統也無法確認執行個體中是否還有其他資料庫；這時仍會重建整個資料庫資料卷，其中若有其他資料庫將會遺失，結果頁的「注意事項」會寫明。只在應用已經無法運作、又沒有可用的還原前備份時使用。「不建立還原前備份，直接還原」這個選項目前只有單元測試與頁面測試，未在實驗室設備上實測。

## 在另一台設備還原

### 目標設備須符合

| 條件 | 說明 |
| --- | --- |
| CPU 架構相同 | 來源與目標架構不同時預檢會提示；備份內含其他架構的映像時預檢失敗。實驗室只驗證過 x86_64 |
| 系統版本 | 已驗證的組合為 Ubuntu 24.04、Cockpit 362、Podman 4.9（4.9.3）；其他組合未驗證 |
| 已安裝本專案 | 含「備份與還原」套件，以及 age 與 zstd（`bootstrap-ubuntu.sh` 會安裝），見 [deployment.md](deployment.md) |
| 已安裝該應用的目錄項目 | 應用 ID 與來源相同。應用尚未部署時，目錄項目還要提供部署範本。**還原以這台設備的目錄項目為準** |
| 應用擁有者帳號 | 這台設備目錄項目指定的帳號必須存在；UID 可以與來源不同（實驗室由 UID 1001 還原到 1007）。帳號要能執行 rootless Podman（已設定 subuid／subgid），並已啟用 linger，使用者服務管理器正在執行。備份中資料卷與主機資料夾的檔案擁有者（容器內的 UID／GID）都必須在這個帳號的 subuid／subgid 對應範圍內，還原作業在「相容性檢查」階段、任何變更之前確認（主機資料夾：實驗室 D2 由 UID 1001、另一個 subuid 範圍還原到 1007） |
| 映像取得得到 | 備份包含映像、這台設備已有同名映像（備份時的版本已不在時，使用設備上現有的版本），或可從映像庫下載。`localhost/` 映像無法下載，這台設備沒有時必須包含在備份中 |
| PostgreSQL 版本 | 10 以上；備份的 PostgreSQL 主版本不可高於這台設備資料庫映像的主版本。整個執行個體方式另外需要映像有資料庫用到的每個擴充功能（例如 pgvector） |
| 可用空間 | 保存位置：上傳需要檔案大小再加 512 MiB，解開備份需要備份內容大小再加 512 MiB；應用擁有者家目錄所在磁碟：約為該應用在備份中的資料量（含映像）的 2 倍再加 512 MiB。原位還原主機資料夾時，新舊兩份內容會同時存在，還原前會另外檢查 |
| PostgreSQL（冷備份） | 這台設備資料庫映像的 PostgreSQL 主版本必須與備份時相同，CPU 架構也要相同；預檢不檢查這一點 |
| 金鑰 | 加密的備份：建立備份那台設備的緊急金鑰，或已匯入這台設備的同一把金鑰。不加密的備份不需要金鑰 |

### 步驟

1. 在來源設備下載備份檔。
2. 在目標設備開啟「從檔案還原」，拖放或選擇 `.tar`（或舊格式 `.woowbackup`）檔並開始上傳。上傳只把檔案放進私有暫存區，不會變更任何應用，過程中可以取消。檔案由瀏覽器分頁傳送，上傳完成前請保持分頁開啟（要離開頁面時會先詢問）。傳送完成後，設備會讀取整個檔案、嚴格檢查外層結構（`.tar` 的每個應用封存檔都和 `backup.json` 記錄的大小與 SHA-256 核對）並計算 SHA-256（這不是完整驗證：內容要到「驗證」或還原時才完整解密核對）；若頁面等候逾時，檔案仍保留在設備上，按「重新確認」即可取得結果。完成後這份備份會以「上傳」類型留在「備份列表」，之後可再還原或刪除。上傳的**未加密**備份無法驗證來源，預檢會提示，確認時要另外勾選信任這個檔案。
3. 加密的備份在頁面要求金鑰時，貼上以 `AGE-SECRET-KEY-1` 開頭的整行金鑰，或讀取緊急金鑰 `.txt` 檔（檔案只在瀏覽器讀取，不會上傳）。勾選「保存此金鑰到這台設備」，日後同一把金鑰的備份就不必再輸入；金鑰要先確認能解開這份備份才會保存，錯誤的金鑰不會被存下。不勾選時，金鑰只交給這次作業使用，作業結束即刪除。
4. 預檢、確認、進度與結果同原位還原。

### 全新部署或原位還原

| 目標設備狀況 | 還原方式 |
| --- | --- |
| 沒有該應用的任何 Quadlet 檔 | **全新部署**：用這台設備上受信任的範本建立服務，再還原應用機密、設定檔、資料卷、主機資料夾與資料庫。這台設備已有同名的資料卷、資料庫資料卷、應用機密或設定檔（例如先前移除應用時留下的），或目錄列出的主機資料夾已存在且不是空的時，預檢失敗，請先移除；這可避免還原失敗時把它們一併刪除。主機資料夾的上層資料夾不存在時，以應用擁有者身分建立（實驗室 D2、D6 已驗證） |
| 該應用的 Quadlet 檔都在 | **原位還原**：同上一節，先建立還原前備份 |
| 只有部分 Quadlet 檔，或其中有符號連結 | 無法判斷，預檢失敗；請先修復部署 |

全新部署失敗時，系統會移除這次新建立的 Quadlet 檔、服務、資料卷、應用機密、設定檔與網路，並把這次載入映像時移動的映像名稱改回原本的映像（原本沒有該名稱時就移除它），作業顯示「已自動回復」。作業被強制終止或斷電時的處理見「已中斷的作業」。

設定檔會原樣寫入。若其中含有來源設備特有的值（例如 IP、網域），還原後需自行確認。

實驗室已驗證：

- dev-a 的備份經頁面下載、上傳到 dev-b（應用擁有者 UID 不同、應用未部署），全新部署後資料摘要與備份時相同，應用也能寫入新資料。
- 資料卷中 27 個測試項目（涵蓋絕對、相對與懸空的符號連結、硬連結、超過 100 bytes 的檔名與超過 255 bytes 的路徑、空目錄、setgid 與 sticky 目錄、user.* 延伸屬性、非 UTF-8 檔名、FIFO、不同擁有者）：原位還原與跨設備全新部署後，在應用容器內看到的類型、擁有者、權限、大小、修改時間、連結目標、內容雜湊、延伸屬性與硬連結都與備份時相同；只有次秒的修改時間被截到整秒（tar 格式只存到秒）。
- 目標設備已有同名的應用機密、設定檔、資料卷或資料庫資料卷時（逐一測試），預檢與還原都拒絕，沒有刪除或建立任何東西。

### 還原以這台設備的設定為準

備份檔只提供資料內容。要寫入哪些應用機密、設定檔路徑、資料卷、資料庫與服務，一律由**目標設備**的目錄項目決定：

- 備份中有、但這台設備目錄未列出的項目，會被略過並在預檢提示。
- 這台設備目錄要求、但備份缺少的項目，會讓預檢失敗。
- 備份檔中的 Quadlet 檔從不安裝；全新部署只用目標設備上 root 擁有的範本。
- 備份檔不能攜帶任何程式；如何備份、還原由設備上安裝的備份元件決定。

## 應用設定：產生與安裝目錄項目

「應用設定」分頁幫管理者為新的應用建立目錄項目，不必從零手寫。詳細規則見 [app-catalog.md](backup/app-catalog.md) 的「用「應用設定」產生與安裝」。

1. **已安裝的應用設定**：列出這台設備目前的目錄項目，可「移除…」（先預覽，勾選確認後才移除；應用本身與它的備份都不會被變更，但在重新安裝設定之前無法備份或還原它）。
2. **掃描應用擁有者**：選擇帳號後按「掃描 Quadlet 服務定義」。系統以該帳號的身分讀取 `~/.config/containers/systemd/`，依相依關係、網路、資料卷與標籤把容器分組成應用，產生草稿。只會讀取，不會變更任何服務；不讀取環境變數檔，也不顯示 `Environment=` 的值。
3. **審查草稿**：每個草稿列出掃描到的容器、PostgreSQL 備份方式（預設冷備份，可切換為整個執行個體或單一資料庫）、「這份設定會備份什麼」，以及需要注意的地方：沒有列入的敏感或禁止路徑（例如 `~/.ssh`、桌面）、權限超過 0644 的設定檔、直接寫在 `Environment=` 的機密、猜測的資料庫名稱等。草稿也會加入內建資料核對。
4. **編輯與預覽**：可以直接編輯 JSON；格式錯誤會立即標出行數，停止輸入後以這台設備的規則檢查，並顯示與目前安裝的設定之間的差異、對既有備份的影響（例如新增資料卷後，舊備份在新設定下無法還原），以及這個應用已有幾份備份。
5. **安裝**：檢查通過後按「安裝應用設定…」（取代既有設定時為「取代已安裝的設定…」），在對話框勾選「我已審查上面的內容、差異與影響」。設定檔以 root 擁有、權限 0644 寫入；被取代的舊設定保留在 `/etc/woowtech-cockpit/backup/apps-history/`（每個應用最近 10 份）。安裝與移除都記錄在系統日誌，作業進行中時不能安裝或移除。
6. **ID 與擁有者**：草稿的 ID 已被另一個帳號的應用設定使用時，草稿標為無法安裝，請先把 `id` 改成其他名稱；已安裝的應用設定也不能直接改成另一個帳號（它的備份會被還原到新的帳號，並計入那個帳號的保留份數），確實要搬移時請先移除再以新帳號安裝。還原時若備份來自另一個帳號，相容性檢查會提醒。
7. **健康檢查網址**：草稿只沿用 `HealthCmd=` 網址的路徑；網址中 `?` 之後的查詢參數（可能含有存取權杖）不會寫進設定，因為應用設定檔所有帳號都能讀取，需要時請自行加入。設定檔路徑不可位於 `~/.config/fish/`、`~/.config/git/` 等殼層或 git 的設定目錄。

安裝只寫入目錄項目，不會建立全新部署用的範本（`quadlet.template_dir`）；沒有範本的應用只能原位還原。草稿是起點，正式應用仍需依 [app-catalog.md](backup/app-catalog.md) 的審查清單審查並在實驗室演練。備份元件較舊、不提供這些指令時，分頁會說明「這台設備尚不支援應用設定掃描」。

## 清理備份與保留原則

「總覽」的「各應用的備份空間」與「備份列表」都有「清理備份」入口：

- **各應用的備份空間**：每個應用的備份份數（手動、還原前、上傳）、佔用空間、最新備份時間與目前的保留原則。
- **保留原則**：預設與每個應用可以設定「全部保留」或「保留最新幾份」（1–1000），只計算與刪除**手動**備份；一份備份含多個應用時，要超出每個應用的保留份數才會刪除。「驗證」未通過的備份無法還原，不計入保留份數，本身也會列為可刪除（原因「驗證未通過」），所以保留的是最新幾份沒有驗證失敗的備份。還原前自動備份維持原規則（每個應用最新 3 份），上傳的備份只會在你勾選時刪除。
- **預覽清理**：變更原則後先按「預覽清理」，列出會刪除的備份與原因（例如「示範筆記應用」第 7 新，保留最新 5 份）與可釋放的空間；可以取消勾選，也可以在「其他備份」另外勾選要刪除的備份（例如舊的上傳）。
- **受保護的備份**：正被作業使用的備份、還原作業進行中時的還原前備份，以及失敗或中斷的還原仍需要的還原前備份與它的來源備份（沒有還原前備份、但已經變更了應用的失敗還原，也保護它的來源備份），一律不會被刪除，頁面列出原因。有作業紀錄無法讀取時，全部備份暫時受保護（那份紀錄可能就是需要保護的還原）。
- **確認**：按「刪除 N 份備份…」（或只變更原則時「儲存保留原則…」），在對話框勾選「我了解這些備份刪除後無法復原」。刪除時若有備份剛好變成受保護，系統會略過並說明原因。儲存的原則之後在每次手動備份成功時自動套用，結果頁會列出依原則刪除的備份。每一筆刪除與原則變更都記錄在系統日誌。

原則保存在 `/etc/woowtech-cockpit/backup/retention.json`（root 擁有）；檔案不存在時全部保留，檔案損毀或權限不安全時頁面會提示，並且不會自動刪除任何備份。

## 加密金鑰與緊急金鑰

### 設備金鑰

每台設備有一把備份金鑰（age X25519），在這台設備建立的備份都用它加密。在「加密金鑰」按「建立加密金鑰」建立；金鑰保存在 `/etc/woowtech-cockpit/backup/keys/`，只有 root 可讀取。金鑰以 `XXXX-XXXX-XXXX-XXXX` 格式的金鑰 ID 識別，備份詳情會顯示該備份是用哪一把金鑰加密。

### 緊急金鑰

建立金鑰後，頁面顯示金鑰 ID 與完整金鑰，並提供「下載緊急金鑰」與「複製金鑰」。緊急金鑰檔名為 `woowtech-backup-key-<主機名稱>-<金鑰 ID>.txt`，內含金鑰 ID、建立時間、建立設備、以 `AGE-SECRET-KEY-1` 開頭的金鑰，以及在其他設備還原的步驟。

保存後勾選「我已將緊急金鑰保存到這台設備以外的安全位置」，再按「完成」。確認之前，頁面會持續提醒；離開「加密金鑰」頁時，頁面上的金鑰內容會被移除，需要時再按「顯示並下載緊急金鑰」。

確認後頁面不再顯示金鑰內容。需要另一份時，在「加密金鑰」按「重新下載緊急金鑰…」：頁面先以對話框說明這個檔案可以解開這台設備的所有備份，以及保管方式，按對話框中的「下載緊急金鑰」才下載。下載的檔案同樣含有完整金鑰；檔案在瀏覽器中產生，金鑰不會顯示在頁面上。

**遺失緊急金鑰的後果：** 這台設備故障或重新安裝時，設備上的金鑰會一起消失。沒有緊急金鑰，用它加密的備份將**永遠無法還原**，任何人（包括 woowtech）都無法找回或重設。

請保存在密碼管理器、加密隨身碟，或列印後上鎖保管。不要用電子郵件、聊天訊息或公開雲端分享傳送，也不要和備份檔放在同一處：同時取得金鑰與備份檔的人，可以讀取備份中的資料庫、檔案與應用機密。

### 匯入其他設備的金鑰

這台設備需要經常還原另一台設備的備份時，可在「加密金鑰」的「匯入其他設備的金鑰」貼上金鑰或讀取緊急金鑰檔，或在還原時勾選「保存此金鑰到這台設備」。匯入的金鑰只用於解密，不會用來加密這台設備的新備份。

目前不提供更換（輪替）設備金鑰，也不能從頁面移除已匯入的金鑰。

## 作業與進度

備份、還原與驗證都以背景作業執行（systemd 暫時單元 `woowtech-backup-<作業 ID>.service`）。關閉瀏覽器或連線中斷都不影響作業；重新開啟頁面會回到進行中的作業。「活動紀錄」列出最近 50 筆作業，每筆可查看階段、進度與最近 200 行紀錄；紀錄不含金鑰與應用機密內容。設備保留最近 200 筆已結束作業的紀錄與日誌，更舊的自動刪除（仍需處理的紀錄另外保留，見 [operations.md](operations.md)）。

**同一時間只能有一個作業。** 已有作業進行中時，新的要求會被拒絕（`busy`），頁面會連到進行中的作業。重複送出同一個要求（例如逾時後再按一次）會回到同一個作業，不會重複執行。

### 階段

| 作業 | 階段 |
| --- | --- |
| 備份 | 準備 → 檢查空間與應用 → 暫停應用寫入 → 匯出資料庫 → 匯出資料卷與設定 → 恢復應用 → 加密封裝（未加密的備份為「封裝（未加密）」）→ 驗證備份 |
| 還原 | 準備 → 解密並驗證檔案 → 相容性檢查 → 預先寫入主機資料夾 → 保存還原前資料 → 停止應用 → 還原資料 → 啟動應用 → 健康與資料核對 → 封裝還原前備份；失敗時加上「自動回復」（其中也會封裝還原前備份） |
| 驗證 | 準備 → 解密並驗證檔案（逐項檢查內容）→ 核對結果 |
| 建立未加密副本 | 準備 → 解密並驗證檔案 → 封裝未加密副本 → 驗證副本 |

沒有主機資料夾時，「預先寫入主機資料夾」顯示「略過」；全新部署，或沒有建立新的還原前備份時，「保存還原前資料」與「封裝還原前備份」顯示「略過」；還原已完成但封裝失敗時，「封裝還原前備份」顯示「失敗」，之後系統補做成功時改為完成。資料摘要在「匯出資料庫」「匯出資料卷與設定」期間計算，還原時在「還原資料」（檔案）與「啟動應用」（資料庫，其他服務啟動前）期間比對。「活動紀錄」中「建立未加密副本」的作業類型顯示為「未加密副本」。

### 狀態

| 狀態 | 意思 |
| --- | --- |
| 等待開始 | 已排入，尚未開始 |
| 執行中 | 正在執行 |
| 已完成 | 成功。還原時代表健康檢查通過，且資料核對一致或沒有可比對的快照 |
| 失敗 | 沒有完成。備份失敗不會留下備份檔；還原若在變更資料前失敗，應用未被變更。顯示「需人工處理」時，代表自動回復也沒有完成 |
| 已自動回復 | 還原在開始變更後失敗，系統已用還原前備份（全新部署則移除新建立的項目）回到還原前的狀態；錯誤訊息說明失敗原因 |
| 已中斷 | 作業程序意外結束（例如被強制終止、斷電、重新開機），見下方 |
| 已取消 | 依要求在安全的檢查點停止：備份不會列出、寫入服務已恢復；還原在變更任何資料前就停止 |

### 取消

只能在不會留下不完整狀態的階段取消：

- **備份**：「暫停應用寫入」之前，以及「加密封裝」「驗證備份」期間（未完成的備份檔會被丟棄，服務在這之前已恢復）。從暫停寫入到恢復應用之間不能取消。
- **還原**：只能在「相容性檢查」結束之前取消（之後開始預先寫入主機資料夾與建立還原前備份）。
- **驗證**與**建立未加密副本**：隨時可以取消（設備上的資料不會改變）。

不能取消時頁面顯示「目前階段無法取消」（`not-cancellable`），作業會繼續到完成或自動回復。取消要求一旦被接受，作業一定在進入下一個不能取消的階段之前停止，不會接受取消之後又暫停寫入或開始變更資料。

### 已中斷的作業

作業程序被強制終止、斷電或系統重新開機時，作業無法自行收尾。之後開啟頁面（讀取狀態、作業或活動紀錄）時，系統會把它標為「已中斷」，並且：

- 清除它的暫存資料與暫時金鑰；
- 重新啟動備份時被暫停、還沒恢復的寫入服務；
- 清除沒有完成的全新部署（見下方）；
- 整理主機資料夾旁留下的 `<路徑>.woowbk-new-<作業 ID>` 與 `<路徑>.woowbk-old-<作業 ID>`：`<路徑>` 不見而原本的內容還在時把它移回，移除沒寫完的新內容，絕不刪除僅存的一份，結果寫在作業訊息中（實驗室 D4 以三種時間點的強制終止驗證）。請勿自行刪除或改名這些資料夾；
- **不會自動重做**任何作業。

系統關機或重新開機時，若還原已開始變更資料，作業不嘗試自動回復，而是自己結束為「已中斷」，保存的還原前資料留在原處；開機後第一次開啟頁面或執行作業時，系統會先把它封裝成還原前備份（大型應用約需一分鐘，頁面這段時間會等待），作業結果再寫出還原前備份 ID，之後依下方方式處理。作業被強制終止或斷電時也一樣。

還原期間被暫時停用的服務，在作業中斷後仍保持停用，開機後也不會自動啟動，避免應用在只還原一半的資料上執行（資料庫服務不受影響，可能仍在執行）。這時管理者會看到：

- **總覽**：應用狀態「異常」，說明「服務 … 已被暫時停用，表示先前的還原沒有完成；請使用還原前備份或同一份備份再次還原」。這個應用暫時不能建立備份。
- **作業結果**：「作業意外中斷」與「接下來怎麼做」；還原已開始變更資料、且有還原前備份時，提供「使用還原前備份還原」。
- **再次還原時的預檢**：以「注意」提示服務因先前的還原沒有完成而被暫時停用，這次還原完成後會恢復。

處理方式：

- **備份中斷**：到「總覽」確認應用已恢復執行，再重新建立備份。中斷的備份不會被列出。
- **原位還原中斷**：按「使用還原前備份還原」，把應用回到這次還原開始前的狀態。應用處於異常狀態時，系統通常無法再建立新的還原前備份；因為還原的是還原前自動備份，會直接還原（失敗時無法自動回復，見「無法建立還原前備份時」），完成後被停用的服務會恢復。不要手動解除停用（`unmask`）後啟動。若在建立還原前備份之前就中斷，應用資料應未被變更；確認應用狀態後再決定是否重新還原。
- **全新部署中斷**：系統判定中斷時會清除未完成的部署（Quadlet 檔、服務、資料卷、應用機密、設定檔與網路），結果訊息說明是否完整清除；清除完成後可再次還原同一份備份，未能完整清除時依訊息列出的項目人工處理。資料匯入已完成、服務已解除停用或正在執行的部署可能已有新資料，系統不會自動移除，訊息會要求人工確認。**映像名稱不會改回**：作業載入映像時移走的既有名稱（例如設備上舊版的 `localhost/<應用映像>:<標籤>`）之後仍指向備份中的映像；原本的映像只剩其他名稱，沒有其他名稱時會變成無名稱映像。只有作業自己執行的自動回復會把映像名稱改回。
- 不確定應用狀態時，先到「服務管理」檢查服務，或聯絡系統管理員。主機端的處理方式見 [operations.md](operations.md)。

實驗室已驗證（2026-11-13 最終回歸）：

- 在「還原資料」階段強制終止（SIGKILL）原位還原：作業「已中斷」並列出還原前備份 ID；用它還原（12.7 秒，系統沒有再建立新的還原前備份）後，資料與中斷前完全相同。
- 還原進入「啟動應用」階段時重新啟動設備：開機後作業為「已中斷」並列出還原前備份 ID，應用服務沒有啟動、總覽顯示「異常」；用還原前備份還原（約 15 秒）後，資料與還原前完全相同。
- 全新部署在「啟動應用」階段被強制終止：復原移除整個部署，同一帳號的其他資料卷、應用機密、設定檔、網路與映像名稱都沒有變；之後再做全新部署成功。
- 備份在暫停寫入、匯出資料庫、匯出資料卷、加密封裝與驗證備份各階段被強制終止：作業「已中斷」；在寫入服務暫停期間被終止時，由復原流程重新啟動它們；暫存清除，沒有留下未列出的備份檔，下一次備份成功。

## 錯誤代碼

頁面顯示中文訊息；代碼供回報問題時使用。

| 代碼 | 意思與常見原因 | 處理方式 |
| --- | --- | --- |
| `invalid-request` | 輸入或請求不正確，例如金鑰不是以 `AGE-SECRET-KEY-1` 開頭的完整一行、建立不加密的備份或關閉預設加密時沒有確認風險、還原上傳的未加密備份時沒有確認信任來源、應用設定沒有通過檢查或在預覽之後被改過（請重新預覽）、備註含換行、上傳檔案大小與宣告不符（上傳未完成）、這台設備已有同 ID 但內容不同的備份；應用目錄項目格式錯誤也使用此代碼 | 依訊息修正後重試；金鑰請完整複製一行；上傳不完整請重新上傳；目錄項目錯誤請交給應用套件維護者（見 [app-catalog.md](backup/app-catalog.md)） |
| `not-found` | 找不到備份、作業或上傳工作（可能已刪除，或未完成的上傳超過 24 小時已被清除）；或找不到應用的設定檔 | 重新整理列表；重新上傳；確認應用部署完整 |
| `busy` | 已有作業進行中（作業進行中也不能安裝或移除應用設定、清理備份）；已有 4 個尚未完成的上傳；要刪除的備份正被作業使用，或在還原作業進行中刪除還原前備份 | 等進行中的作業或上傳完成後再試，頁面會連到進行中的作業 |
| `key-required` | 這台設備沒有加密這份備份的金鑰 | 輸入建立備份那台設備的緊急金鑰，或先匯入金鑰 |
| `wrong-key` | 提供的金鑰不是加密這份備份的那一把，或金鑰無效 | 核對備份顯示的金鑰 ID 與緊急金鑰檔上的金鑰 ID 是否相同 |
| `no-device-key` | 這台設備尚未建立備份金鑰；建立加密的備份，以及「預設加密備份」開啟時的原位還原（建立加密的還原前備份）都需要它 | 到「加密金鑰」建立金鑰並保存緊急金鑰 |
| `not-a-backup` | 檔案不是 woowtech 備份檔 | 確認選擇的是下載的 `.tar`（或舊格式 `.woowbackup`）檔，且下載完整 |
| `unsupported-format` | 備份檔格式版本較新，或加密、壓縮方式不受支援 | 將這台設備的備份元件更新到不舊於建立備份的版本 |
| `corrupt-archive` | 檔案損毀或遭修改，例如被截斷、位元錯誤、內容與清單不符 | 不要用它還原；改用另一份備份，或從原設備重新下載 |
| `invalid-manifest` | 備份的內容清單格式不正確 | 同上；若確定來源可信，保留檔案並回報 |
| `limit-exceeded` | 超出安全限制：超過 4000 個項目、內容清單超過 1 MiB、總量超過 2 TiB、資料卷超過 2,000,000 個項目；設定檔、部署範本、目錄項目過大；或指令輸出超過上限 | 本版本無法處理此檔案或設定；設定過大時請應用套件維護者調整 |

| `not-deployed` | 應用尚未部署在這台設備（無法備份），或找不到目錄列出的資料卷 | 確認應用已部署並啟動，資料卷名稱與目錄項目一致 |

| `not-cancellable` | 作業已進入不能中斷的階段 | 等作業結束；還原失敗時會自動回復 |
| `job-failed` | 作業步驟失敗：服務無法停止或啟動、資料庫匯出或匯入失敗、資料摘要與備份時不一致（應用不會啟動，作業自動回復）、資料卷含有還原時無法匯入的內容、健康檢查未通過、資料核對不一致、無法建立還原前備份等；「已中斷」的作業也記錄此代碼 | 查看結果訊息與作業紀錄最後幾行；到「服務管理」檢查服務；出現「需人工處理」時，用列出的還原前備份再次還原 |
| `internal-error` | 未預期的錯誤，例如備份元件安裝不完整或權限不安全、缺少 age 或 zstd、無法啟動背景作業 | 用 `manage.py verify` 檢查、`install` 修復，確認 age 與 zstd 已安裝；查看系統日誌（見 [operations.md](operations.md)） |

頁面另有幾種非代碼狀態：「找不到備份管理程式」表示這台主機未安裝或未完整安裝備份元件；「管理連線已中斷」時按「重新連線」，已送出的背景作業會繼續、不會重送；「操作回應逾時」時先重新整理確認狀態，再決定是否重試。

## 備份檔的內部檢查（資料卷、主機資料夾與映像封存）

備份中的資料卷與映像各是一個 tar 檔。Podman 匯入 tar 時會跟隨封存內先放入的符號連結：實驗室在設備上的 Podman 4.9.3 實測，直接執行 `podman volume import` 或 `podman load`，都會經由植入的絕對路徑符號連結，把檔案寫進應用擁有者家目錄中的其他位置。所以這兩種 tar 一律先完整檢查，再由引擎依檢查過的項目重新產生乾淨的 tar 交給 Podman，Podman 從不讀取備份檔裡原本的位元組。主機資料夾的 tar 也以資料卷相同的規則檢查並重新產生，再以應用擁有者身分解到新的資料夾（實驗室 D5 以多種惡意資料夾 tar 驗證：都在任何變更之前被拒絕）。

- **資料卷**：只接受一般檔案、目錄、FIFO、符號連結，以及指向前面非目錄項目的硬連結；拒絕絕對路徑或含 `..` 的名稱、重複項目、位於符號連結或其他非目錄項目之下的項目、從連結所在目錄解析後會離開資料卷的符號連結、裝置檔與其他類型、超過 2,000,000 個項目，以及應用擁有者的使用者命名空間對應不到的擁有者（UID／GID）。
- **重新產生時不保留的內容**：非目錄檔案的 setuid／setgid 位元，以及 `user.*` 以外的延伸屬性（例如 file capabilities）。還原結果的「注意事項」與作業紀錄會列出受影響的檔案數與例子。
- **映像**：必須正好是 `podman save` 產生的 OCI 封存，只含一個映像，其設定摘要等於備份記錄的映像 ID，名稱對應這台設備範本需要的映像。載入時映像名稱由這台設備決定，封存不能指定要移動哪個名稱。

檢查的時機：建立備份時檢查每個資料卷匯出（不合規就不建立備份）；「驗證」作業以相同的規則檢查每個資料卷、主機資料夾與映像封存（不檢查與這台設備有關的應用擁有者 ID 範圍與映像名稱）；還原作業在「相容性檢查」階段、建立還原前備份之前再完整檢查一次（含這台設備的 ID 範圍與需要的映像名稱），不合規就停止，設備沒有任何變更。「檢視內容」不做這項檢查。

實驗室已驗證（2026-11-14，格式 2）：把一份新備份的資料卷 tar 加上離開資料卷的符號連結、以設備公鑰重新封裝（所有大小與 SHA-256 都正確）後上傳，「驗證」作業以「備份檔已損毀」失敗並點名資料卷，索引記錄驗證未通過；還原在任何變更之前被拒絕，應用資料不變。

實驗室已驗證：在資料卷 tar 與映像封存的所有真實項目之後，各植入指向家目錄的符號連結與其下的項目，再以設備金鑰重新加密。還原作業在相容性檢查就拒絕，錯誤分別點名容器映像與資料卷；過程中沒有任何 Podman 映像或資料卷事件，沒有建立還原前備份，應用資料、部署檔與映像名稱都沒有變，整台設備找不到植入的檔案。

## 安全須知

- **只有管理員可以使用。** 頁面以 Cockpit 管理員權限呼叫 root helper；helper 在非 root 身分下拒絕執行。任何能在 Cockpit 取得管理員權限的帳號，都能檢視、下載、還原與刪除所有應用的備份；管理員之間沒有分權。
- **備份含有應用機密。** 資料庫、檔案、Podman secrets（例如資料庫密碼與應用金鑰）與設定檔都在備份中。下載的加密檔仍請像保管密碼一樣保管，並與緊急金鑰分開存放。**不加密的備份與「下載未加密版本」建立的副本以明文存放這些機密**，任何取得檔案的人都能讀取；只有管理員明確確認風險後才會建立，副本 15 分鐘後自動刪除，每次建立、下載與刪除（包括過期、被新副本取代）都記錄在系統日誌（`journalctl -t woowtech-cockpit-backup`）；下載未加密的備份與刪除任何備份也會記錄。設備重新開機後，自動刪除的計時器不會保留：已過期的副本在下次開啟備份頁面或執行任何作業時刪除。
- **本機加密不防 root。** 本機備份與設備金鑰在同一台設備上，具有 root 權限的人可以解密本機備份。加密主要保護下載到其他位置的檔案。
- **作業期間有明文暫存（殘留風險）。** 備份與還原過程中，資料庫匯出、資料卷內容與應用機密會以未加密形式暫存在 `/var/lib/woowtech-backup/staging/<作業 ID>/`（只有 root 可存取），作業結束或被判定中斷時刪除。刪除後的資料區塊可能留在磁碟上直到被覆寫，系統不做安全抹除；需要防範磁碟被取出讀取時，請使用整碟加密。
- **金鑰只經標準輸入傳遞。** 輸入的金鑰經 Cockpit 加密連線送到 helper 的標準輸入，不會出現在網址、命令列參數、作業紀錄或日誌。只供單次作業使用的暫時金鑰檔放在 `/run/woowtech-backup/`（記憶體檔案系統，0600），作業結束即刪除。最終回歸以兩台設備的作業紀錄、日誌、索引與 journal，以及主機上 1144 個測試證據檔，比對應用機密、設備金鑰與 age 金鑰格式，沒有任何命中。
- **資料摘要不執行資料庫中的自訂程式。** 計算資料表摘要的帳號通常是資料庫的超級使用者，而資料表可能屬於其他帳號；摘要以資料列型別本身的輸出函式讀取內容（`record_out`），不會執行資料表擁有者可以自訂的型別轉換（以前的寫法會以超級使用者身分執行它，實驗室已重現並確認修正）。
- **只還原可信來源的備份。** 上傳的檔案在完整驗證前一律視為不可信：外層結構、加密認證、每個項目的大小與雜湊都要通過，路徑穿越、連結、多出或缺少的項目都會被拒絕；資料卷與映像封存另外完整檢查並重新產生（見上一節）。`.tar` 備份裡的 `backup.json` 只是說明，還原只以各應用封存檔內經過驗證的內容清單為準。但能解密只證明檔案在加密後沒有被修改，不能證明它來自哪一台設備；**未加密的上傳檔連這一點也無法證明**，所以還原前要另外確認信任它。還原的資料庫內容與設定檔會被應用直接使用。請只還原自己保管的備份檔。

## 已知限制

- **一次只能執行一個作業。** 備份、還原、驗證與建立未加密副本互斥；作業進行中也不能安裝或移除應用設定、不能刪除備份；同時進行中的上傳最多 4 個。
- **沒有排程備份、NAS 或雲端目的地。** 保留原則只有「每個應用保留最新幾份手動備份」：在手動備份成功後套用，或在「清理備份」預覽後確認刪除；上傳的備份只在勾選時刪除；還原前自動備份每個應用保留 3 份。
- **本機備份不防磁碟故障。** 備份與應用資料通常在同一顆磁碟，請下載保存到其他位置。
- **上傳與下載速度。** 實驗室經真正的 Cockpit 362 以瀏覽器上傳 142 MB 的備份：目前的預設（每段 512 KiB、最多 4 MiB 未確認）6 次中位數 12.8 MB/s（9.8–16.8 MB/s），舊設定（64 KiB、2 MiB）為 6.7 MB/s；量測時主機負載很高（4 核心，1 分鐘平均負載約 8–20）。最終回歸中，從按下上傳到出現金鑰步驟（含傳送後的檢查）共 11.6 秒，下載 4.2 秒。以 12.8 MB/s 推算，1 GB 約需 1.3 分鐘、10 GB 約 13 分鐘；多 GB 的檔案未實測，實際速度取決於網路與設備。
- **未套用的設定變更。** 備份與還原前備份都會重新啟動寫入服務。若應用的設定檔已修改、但尚未重新啟動套用，這次重新啟動會讓新設定生效；如果因此改變了核對值，這份備份不保存資料核對快照，日後用它還原（包括失敗時的自動回復）都無法比對資料。請先套用（重新啟動）或撤回設定修改，再備份或還原。「快照在備份期間改變就不保存」由單元測試驗證；以未套用的設定變更觸發的情況沒有在實驗室設備重現。
- **PostgreSQL。** 支援 PostgreSQL 10 以上。三種方式的限制：
  - 單一資料庫：只備份目錄列出的資料庫，不含角色等叢集層級設定；匯入時所有物件改由目錄指定的資料庫帳號擁有，不還原原本的擁有者與授權；資料庫執行個體中有目錄未宣告的資料庫時，不能原位還原；目標設備的主版本不可低於備份時。
  - 整個執行個體：目錄的資料庫帳號必須是映像建立的初始超級使用者（`POSTGRES_USER`），還原時新建的執行個體只有這個帳號；備份 template0、template1 以外的每個資料庫（範本資料庫也保留）；有不接受連線的資料庫時無法備份，原位還原的相容性檢查也會拒絕（它們不在任何備份中，還原後會永久遺失），請先允許連線或改用冷備份；template1 中自訂的物件不保留（相容性檢查會提醒）；不保留非預設的表空間；目標設備的主版本不可低於備份時，映像必須有資料庫用到的每個擴充功能（例如 pgvector）。映像的初始化程式（例如 postgis、timescaledb）在新的執行個體建立的資料庫，還原時以備份內容重建。
  - 冷備份：還原的設備必須是相同的 PostgreSQL 主版本與 CPU 架構，預檢不檢查版本。
  - 實驗室只驗證過 PostgreSQL 16 還原到 16。
- **資料摘要的範圍。** `postgres-digest` 涵蓋一般資料表與序列，不涵蓋暫存表、擴充功能自己的物件、檢視、具體化檢視、外部資料表與大型物件；`files-digest` 不比對 socket、資料卷最上層資料夾本身，以及資料卷中檔案的 setuid／setgid，清單最大 1 GiB（約 200 萬個項目）。每項摘要在備份時完整讀兩次資料，會延長寫入暫停。兩次讀取之間被寫入又改回原值的資料看不出來；冷備份的資料庫在第二次讀取之後、停止之前的寫入也看不出來，所以仍要把所有會寫入的服務列為寫入服務。PostgreSQL 11 以前讀取的摘要與 12 以後讀取的不比對（浮點數的文字格式不同）。
- **支援的資料形態有限。** 支援具名資料卷（還原時以預設選項重建）、應用自己設定目錄下的單一設定檔（每個最大 16 MiB，權限最多 0644）、Podman secrets（每個小於 512,000 bytes）。主機資料夾（每個應用最多 16 個，整個資料夾備份、沒有排除規則，還原時整個取代）與資料放在主機資料夾的資料庫（冷備份）已在實驗室（D1–D7）與參考主機驗證。冷備份的資料庫只能還原到 PostgreSQL 主版本相同的設備。資料卷中非目錄檔案的 setuid／setgid 與 `user.*` 以外的延伸屬性不保留，修改時間只保留到秒。
- **還原會停機並覆寫資料。** 還原期間應用停止服務；原位還原會覆寫備份之後寫入的資料（保留在還原前備份中）。
- **跨設備範圍。** 只驗證相同架構（x86_64）與上述系統版本；兩台實驗室設備是同一台實體主機上的獨立容器，尚未在兩台實體設備之間演練。
- **金鑰管理。** 不能輪替設備金鑰，也不能從頁面移除已匯入的金鑰。
- **停止的先後。** 寫入服務一次停止，沒有在 Quadlet 寫明 `After=` 的服務會同時停止，主服務可能一開始就停（見「備份如何保持資料一致」的量測）。
- **尚未實測的情境。** 冷備份還原到 PostgreSQL 主版本不同的設備；整個執行個體方式的跨主版本還原與 ICU 語系資料庫在實驗室設備上的還原（ICU 只在一次性容器中試過；pgvector 映像的原位與全新部署還原已在實驗室設備實測）；多 GB 備份與超過 8 GiB 的單一項目；不同 CPU 架構；兩台實體設備之間的還原；「不建立還原前備份，直接還原」選項（只有單元與頁面測試）；在真正的 Cockpit 頁面上按「建立加密金鑰」（實驗室設備的金鑰是在較早的整合輪直接呼叫 helper 建立，之後都沿用它）。這一版頁面上的新流程（加密選擇、下載未加密版本、資料核對與停機時間的結果、應用設定、清理備份）除了頁面 fixture 測試，也已經由兩台實驗室設備上真正的 Cockpit 頁面操作實測，見最後一節。
- **正式應用需逐一接入。** 每個應用需先完成目錄項目審查與實驗室演練；參考主機上已接入的 19 個應用見 [production-onboarding.md](backup/production-onboarding.md)。

| 停機 | 見「備份如何保持資料一致」與「在同一台設備還原」的量測（兩種 `After=` 寫法、與前一版引擎比較） |
| 既有情境 | `format_e2e.py`（格式 2、加密選擇、舊格式仍可驗證與還原）105 項、`dirs_e2e.py`（主機資料夾 D1–D7）256 項、`cli_e2e.py`（同機、跨設備、故障、回復、中斷、取消、洩漏）122 項全部通過（2026-11-14 更正：`dirs_e2e.py` 的 `prep` 會把 woowbk-dirs 的目錄項目換回不含資料摘要的夾具，所以 D1–D7 實際上沒有資料摘要核對；woowbk-dirs 的資料摘要由 `strengthen_e2e.py digests` 涵蓋）；`hardening.py`（惡意封存檔 28 種、空間不足、資料庫匯出失敗、各階段強制終止、還原中重新開機、約 600 MiB 的資料卷、安裝與回退、巢狀 tar 的符號連結攻擊、檔案保真度、全新部署的殘留物與中斷、洩漏）全部通過；格式 2 的惡意案例在設備內重新封裝，巢狀 tar 被改造的備份現在在「驗證」就失敗。完整的安裝回退鏈在實驗室安裝紀錄中曾被實驗室專用修補改過的那一筆被安裝程式正確拒絕，改以一組乾淨的安裝紀錄驗證 |

### 2026-11-14 審查修正與最終回歸

整合後的安全與正確性審查指出的問題都已修正，各有單元測試或實驗室測試（細節見 [CONTRACT.md](backup/CONTRACT.md) 開頭的修訂說明與第 13 節）。實驗室的重點結果：

| 項目 | 結果 |
| --- | --- |
| 資料摘要不再執行資料庫中的自訂程式 | 一次性的 PostgreSQL 16 容器中，沒有超級使用者權限的資料表擁有者定義了自訂型別轉換；修正前的摘要寫法以超級使用者身分執行它（在資料庫容器內寫出檔案），引擎的寫法不會；沒有自訂轉換的資料表摘要與修正前完全相同 |
| 備份期間有寫入者 | 目錄沒有停止的容器與資料庫容器內的工作持續寫入時：備份兩次讀取的資料庫摘要不同，不保存這一項；在寫入時還原失敗的備份，還原前備份同樣不保存，自動回復完成、應用沒有停在暫時停用；寫入者仍在時還原一份正常的備份，資料仍在變動的那一項顯示「未比對」，還原完成 |
| 整個執行個體方式 | 重寫後的還原（每個資料庫都以備份內容重建，包括 `postgres` 與映像建立的資料庫；以初始化時間確認是新的執行個體；套用角色定義後再確認管理帳號）在原位與另一台設備的全新部署都通過：角色與密碼雜湊、成員、設定、擁有者、定序、權限、註解、內容與索引都等於備份時 |
| 既有情境 | `cli_e2e.py` 122 項、`hardening.py` 551 項、`format_e2e.py` 105 項、`dirs_e2e.py` 255 項、頁面 fixture 52 項、真正頁面 68 項全部通過；單元測試三種環境各 856 項 |

實驗室中也遇到一次失敗：用來模擬寫入者的另一個容器，在應用容器停止後有幾秒連不上資料庫，還原前備份兩次讀取剛好相同而保存了摘要，自動回復時它又寫入兩列，回復因此失敗，應用停在暫時停用；之後以那份還原前備份再次還原就恢復了。這次失敗促成了「還原時摘要不一致會再讀一次」的修改。正式主機沒有安裝這一版。
