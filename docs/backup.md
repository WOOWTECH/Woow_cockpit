# 備份與還原（管理者指南）

Cockpit「備份與還原」頁為 rootless Podman Quadlet 應用建立備份，預設加密（管理員可選擇不加密，見「加密選擇」）。備份預設保存在這台設備，可下載成一個 `.tar` 檔（2026-11-13 之前建立的備份是 `.woowbackup`），再上傳到同一台或另一台相容設備還原。原位還原前會先建立「還原前自動備份」，還原失敗時用它自動回復（例外見「無法建立還原前備份時」）。也可以開啟「排程備份」，在選定的日子與時間自動建立備份（2026.11.17.1 起，見「排程備份」）。作業在背景執行，關閉瀏覽器也會繼續。

> **現況：** 第一階段在兩台隔離的實驗室設備（Ubuntu 24.04、Cockpit 362、Podman 4.9.3、x86_64）以示範應用 `woowbk-demo` 完成端到端驗證；「主機資料夾」（應用擁有者家目錄中、以 bind mount 掛進容器的資料夾）也在實驗室完成情境 D1–D7。2026-11-13 經負責人同意，在參考主機為 19 個正式應用（含 Odoo、Home Assistant、Nextcloud 的主機資料夾）實測備份與原位還原。2026-11-14 以 2026.11.14.1 再實測全部已接入的應用，並接入 Omnigent 與 Cloudflare Tunnel，已部署的 20 個應用全部通過（當時共 21 個目錄項目；未部署的 `vk-mcp-admin` 之後依負責人指示移除）。結果與各應用使用的方式見 [production-onboarding.md](backup/production-onboarding.md)。
>
> **2026-11-13 之後的加強**：Home Assistant 式的備份檔與加密選擇、內建資料核對、較短的停機、PostgreSQL「整個執行個體」方式、逐項檢查內容的「驗證」、「應用設定」（產生目錄項目）與「清理備份」。這些已在實驗室設備與頁面測試驗證（見最後一節），**尚未在參考主機以正式應用重新實測**。本文的時間與大小都來自實驗室與少量測試資料，只供參考。
>
> **2026.11.17.1 的「排程備份」**：驗證範圍與結果見 [current-state.md](current-state.md) 與 [testing.md](testing.md)。

工程規格見 [CONTRACT.md](backup/CONTRACT.md)；應用如何加入備份見 [app-catalog.md](backup/app-catalog.md)；安裝、維護與測試見 [deployment.md](deployment.md)、[operations.md](operations.md)、[testing.md](testing.md)。

## 目前可備份的應用

頁面只列出設備上裝有「受信任應用目錄項目」（catalog entry，`/etc/woowtech-cockpit/backup/apps/<應用 ID>.json`）的應用。目錄項目明確列出應用的擁有者帳號、服務、資料庫、資料卷、主機資料夾、應用機密與設定檔；備份只包含這些項目，不會自動備份其他容器。

- 一般安裝（`manage.py install`）不含任何目錄項目，頁面會顯示「尚未設定可備份的應用」。
- 目錄項目可以在頁面「應用設定」由應用的 Quadlet 檔產生草稿，審查後安裝（見「應用設定：產生與安裝目錄項目」），或由管理者手動放置（見 [app-catalog.md](backup/app-catalog.md)）。
- 示範應用 `woowbk-demo` 只能用 `--backup-demo-catalog` 安裝到實驗室設備，**不可用於客戶設備**。
- **正式應用沒有預先提供目錄項目。** 每個應用的目錄項目都要經過審查，並在實驗室完成同機還原、跨設備還原與失敗回復演練後才使用。參考主機上 19 個正式應用的接入紀錄與順序見 [production-onboarding.md](backup/production-onboarding.md)。

此階段不包含：把備份自動複製到設備以外（NAS 或雲端目的地）、root（系統層級）Quadlet 應用、多節點應用、整機或裸機還原。保留策略有兩種，各自計算：手動備份的「每個應用保留最新幾份」（見「清理備份與保留原則」），以及排程備份自己的「保留最新幾份排程備份」（見「排程備份」）。

## 開啟頁面與權限

從 Cockpit 側欄的「工具」群組開啟「備份與還原」，它在「應用軟體」下面（2026-11-15 之前在「系統」群組；網址仍是 `/woowtechbackup`）。此頁會讀取所有應用的資料與加密金鑰，所以**只有取得管理員存取權限後才能使用**。未取得權限時只顯示「需要管理員權限」，不載入資料、不執行任何動作；在 Cockpit 頂端開啟「管理員存取權限」後，頁面會自動重新載入。

頁面有六個分頁：「總覽」「備份列表」「從檔案還原」「應用設定」「加密金鑰」「活動紀錄」。「總覽」顯示可備份的應用與狀態（執行中、已停止、部分執行、未部署、異常）、各應用的備份空間、最近的備份、本機儲存空間（上傳的 Home Assistant 備份另外列出份數與大小）、金鑰與「預設加密備份」的狀態，以及「排程備份」卡片（開啟或關閉、下一次與上一次的時間）。排程備份的設定頁在「總覽」之下（沒有另外的分頁），也可以從「備份列表」的「排程備份」按鈕進入。「備份列表」的每份備份都標示「已加密」或「未加密」，排程建立的標示「排程」，並有「清理備份」入口。上傳的 Home Assistant 備份也列在「備份列表」，標示「HA 備份」（見「從 Home Assistant 備份匯入」）。

狀態「異常」表示應用需要處理，原因列在應用下方，例如：

- 應用擁有者的使用者服務管理器沒有啟動（沒有啟用 linger）；
- Quadlet 檔不完整或含有符號連結，或找不到服務；
- 服務被先前沒有完成的還原暫時停用（見「已中斷的作業」）；
- 服務都在執行，但快速健康檢查沒有通過（每個檢查最多等 3 秒，只看回應狀態碼）。

狀態「異常」或「未部署」的應用不能選來建立備份。目錄項目有問題而被略過時，總覽上方會出現「備份設定提示」。

**第一次使用請先到「加密金鑰」建立金鑰並保存緊急金鑰**，否則無法建立加密備份（預設）。不加密的備份不需要金鑰（即使附上金鑰也會被忽略），但內容以明文保存，見「加密選擇」。

## 備份包含什麼

每份備份只包含目錄項目列出的內容：

| 項目 | 內容與取得方式 |
| --- | --- |
| PostgreSQL 資料庫（單一資料庫） | 目錄列出的資料庫以 `pg_dump` 自訂格式匯出；匯出後完整讀取一次，確認可以還原。只包含該資料庫本身，不含角色等叢集層級設定。備份詳情標示「單一資料庫」 |
| PostgreSQL 資料庫（整個執行個體） | 目錄以 `"scope": "instance"` 列出資料庫時：以 `pg_dumpall --globals-only` 保存所有角色（含密碼雜湊）與成員關係，再以 `pg_dump` 匯出每個可連線、不是範本的資料庫；備份時資料庫保持執行。備份詳情標示「整個執行個體」，列出資料庫、擁有者與角色數量（不顯示密碼） |
| PostgreSQL 資料庫（冷備份） | 目錄沒有列出要匯出的資料庫，而是把資料庫的資料卷或主機資料夾整份列入時：資料庫服務也列為寫入服務，備份期間一起停止，資料檔隨該資料卷或主機資料夾整份備份。整個執行個體（所有資料庫、角色、密碼、擁有者與權限）都保留；還原的設備，PostgreSQL 主版本必須與備份時相同。備份詳情中這種應用的「資料庫」顯示「沒有以 pg_dump 匯出的資料庫」 |
| 資料卷 | 目錄列出的具名 Podman 資料卷（`podman volume export`）。匯出後依還原時的規則完整檢查，見「備份檔的內部檢查」 |
| 主機資料夾 | 目錄列出、應用擁有者家目錄中的資料夾（容器以 bind mount 使用的資料夾）。寫入服務暫停期間，以應用擁有者的身分、在他的 rootless 使用者命名空間內整份打包：保留容器內看到的檔案擁有者、權限、修改時間、符號連結與硬連結，以及可保留的延伸屬性；不跟隨符號連結到資料夾外。整個資料夾都會備份，沒有排除規則 |
| 應用機密 | 目錄列出的 Podman secrets 原始內容（例如資料庫密碼、應用金鑰） |
| 設定檔 | 目錄列出、位於擁有者 `~/.config/<應用 ID>/` 或 `~/.local/share/<應用 ID>/` 之下的單一檔案；權限依目錄宣告（最多 0644） |
| Quadlet 定義 | 應用 Quadlet 檔的副本，僅供紀錄；還原時不會安裝備份檔中的 Quadlet（見「還原以這台設備的設定為準」） |
| 容器映像（選用） | 勾選「包含容器映像」時，以 `podman save` 匯出應用使用的映像 |
| 應用設定（2026.11.15.2 起） | 建立備份時這個應用的目錄項目（`/etc/woowtech-cockpit/backup/apps/<id>.json` 的內容，只有名稱與路徑，不含任何機密）。還原從不自動安裝它；這台設備沒有或不同時，可以在預檢審查後安裝（見「備份附上的應用設定」）。少數手寫的設定檔含有備份無法保存的字元時，該次備份不附上設定，作業紀錄會註明 |
| 資料核對 | 目錄設定了核對時：應用自己的摘要端點（`http-json`，例如筆數、內容雜湊），以及引擎自己計算的**資料摘要**：資料庫每個資料表與序列的筆數與內容雜湊（`postgres-digest`）、資料卷或主機資料夾每個項目的類型、權限、擁有者、大小、連結目標與 SHA-256（`files-digest`）。資料摘要在寫入服務停止期間計算，與備份內容是同一個時間點 |
| 備份資訊 | 建立時間、來源主機名稱與 CPU 架構、作業系統、Podman 與備份元件版本、備份時暫停寫入的秒數、每個項目的大小與 SHA-256 |

不包含目錄未列出的任何東西，例如目錄沒有列出的主機資料夾、其他帳號的資料、作業系統與 Cockpit 設定，以及加密金鑰本身。以 `pg_dump` 匯出的資料庫執行個體中若還有目錄未宣告的資料庫或角色，作業紀錄會註明它們不在備份中。

### 下載的備份檔是什麼檔

自 2026-11-13 起，一份備份是**一個一般的 tar 檔（格式 2，副檔名 `.tar`）**，和 Home Assistant 的備份類似，任何支援 tar 的工具都能打開。依序包含：

1. `backup.json`：方便閱讀的說明（備份 ID、建立時間、類型、備註、備份元件版本、來源主機名稱、CPU 架構、作業系統與 Podman 版本、是否加密與金鑰 ID，以及每個應用的名稱、擁有者帳號、映像、資料庫、資料卷、主機資料夾、應用機密與設定檔的**名稱**和封存檔大小）。不含任何機密。這份說明**沒有經過驗證**：還原時只以各應用封存檔內、經過驗證的內容清單為準，兩者不一致時視為檔案損毀。
2. `README.txt`：中英文說明，包括在 Cockpit 還原的步驟，以及手動解開的指令。
3. 每個應用一個封存檔：加密時是 `apps/<應用 ID>.tar.zst.age`（以 [age](https://github.com/FiloSottile/age) X25519 加密的 zstd 壓縮 tar），不加密時是 `apps/<應用 ID>.tar.gz`。封存檔裡第一個項目是該應用的 `manifest.json`（內容清單：備份 ID、建立時間、來源設備、這個應用的資料庫、資料卷、主機資料夾、映像，以及每個項目的大小與 SHA-256），之後依清單是資料庫匯出、資料卷與主機資料夾的 tar、應用機密、設定檔、Quadlet 檔，以及勾選時的容器映像（OCI 封存）。

加密的備份只有建立它的設備的金鑰（或該金鑰的緊急金鑰）能解開，`README.txt` 寫有用緊急金鑰手動解開的指令（`age -d -i <緊急金鑰>.txt apps/<應用 ID>.tar.zst.age | zstd -d -c | tar -x`，需要 age 與 zstd）。要還原，請在這台或另一台設備的「從檔案還原」上傳；頁面會完整驗證後才還原，不需要、也不建議手動解開（解開後的內容含應用機密）。每個應用的封存檔各自獨立：只還原其中一個應用時，不會讀取或解密其他應用的封存檔。瀏覽器下載時的檔案類型是 `application/octet-stream`。

下載檔名為 `woowtech-backup-<主機名稱>-<YYYYMMDD-HHMMSS>.tar`，時間為 UTC，含秒數；「下載未加密版本」建立的未加密副本，檔名結尾是 `-unencrypted.tar`。上傳的檔案若符合這些格式（或下面舊格式的檔名）且副檔名與檔案格式相符就保留原檔名，否則改名為 `woowtech-backup-uploaded-<備份建立時間>.tar`。

**舊格式（格式 1，`.woowbackup`）**：2026-11-13 之前建立的備份是本專案自訂的加密檔，開頭兩行文字檔頭（`WOOWTECH-BACKUP/1` 與一行 JSON），之後是 age 加密的 zstd 壓縮 tar，不能直接用解壓縮軟體打開。舊備份會一直可以檢視、驗證、下載與還原，檔名維持 `woowtech-backup-<主機名稱>-<YYYYMMDD-HHMMSS>.woowbackup`。

### 加密選擇

「加密金鑰」頁「加密設定」中的「預設加密備份」預設開啟；建立備份時的「加密此備份」預設依這個設定。關閉時會出現對話框說明風險，勾選「我了解未加密的備份會以明文保存與下載資料庫密碼、API 金鑰與存取權杖」後才會關閉；重新開啟不需要確認。每份備份在列表與詳情都標示「已加密」或「未加密」。

- **加密（預設）**：用這台設備的金鑰加密，下載與保存的檔案都需要金鑰或緊急金鑰才能讀取。
- **不加密**：不需要設備金鑰，任何工具都能直接打開，但**資料庫密碼、API 金鑰與存取權杖等應用機密會以明文保存與下載**，任何取得檔案的人都能讀取，也無法確認檔案在設備以外是否被修改過。關閉「預設加密備份」，或在設定開啟時取消勾選某一份的「加密此備份」，都需要另外勾選確認這項風險。設定的變更會記錄在系統日誌。
- 「還原前自動備份」依「預設加密備份」的設定加密或不加密；設定開啟而這台還沒有金鑰時，開始還原（或匯入 HA 備份）會自動建立，完成後請到「加密金鑰」下載並保存。
- 「排程備份」每次執行時也依當時的「預設加密備份」加密或不加密。排程開啟時關閉「預設加密備份」，對話框會寫出排程，例如「排程備份（每天 03:00）也會不加密。」。
- 從其他地方**上傳的未加密備份**無法驗證來源與完整性：預檢會提示，列表標示「來源未驗證」，確認還原時要再勾選「我確認信任這個未加密備份檔的來源」。

設定檔 `/etc/woowtech-cockpit/backup/settings.json` 不存在、損毀、不是由 root 擁有或可被其他帳號修改時，一律視為「加密」。

## 備份如何保持資料一致

1. **先檢查空間。** 保存位置的可用空間須至少為預估資料量的 2.2 倍再加 512 MiB。不足時，作業在暫停任何服務之前就停止（`insufficient-space`）。
2. **讀取資料核對快照**（有設定時）。
3. **短暫暫停寫入服務。** 停止之前先確認沒有不會被停止的執行中容器以可寫入方式掛載應用的資料卷或主機資料夾；有的話備份不會開始（請把它的服務加入寫入服務，或只讀取的容器改用 `:ro` 唯讀掛載）。只停止目錄列為寫入服務（`writer_units`）且正在執行的服務，**以一次** `systemctl --user stop` 停止：systemd 依 Quadlet 的 `After=` 決定先後，其餘同時停止（不再逐一等待；n8n 的 task runner 每個要約 50 秒才停止）。以 `pg_dump` 匯出的資料庫（單一資料庫或整個執行個體）保持執行，以便匯出。冷備份的資料庫本身也列為寫入服務，會一起停止；設定了它的資料摘要時，資料庫在摘要讀完後才停止。
4. **匯出與資料摘要。** `pg_dump` 匯出資料庫並完整讀取檢查（整個執行個體另外保存角色定義，並檢查還原時是否接受它），接著匯出資料卷與主機資料夾、應用機密、設定檔與 Quadlet 檔。目錄設定了資料摘要時，每項摘要在這段暫停期間**讀兩次**，把它要證明的匯出夾在中間（資料庫在匯出前後各讀一次、檔案在匯出前後各讀一次、冷備份的資料庫在停止前連讀兩次）。兩次相同才保存，代表匯出的內容就是摘要描述的內容；兩次不同（例如有目錄沒有停止的服務、排程或資料庫內的工作在寫入），這份備份不保存這一項摘要，作業紀錄會寫出「資料摘要 … 兩次讀取的結果不同」與原因，備份仍會完成，日後還原時這一項顯示「未比對」。以前會保存讀取時間不同的摘要，讓這份備份的每次還原（以及用它當還原前備份時的自動回復）都比對失敗。摘要要多讀一次資料，寫入暫停會比只讀一次長。
5. **立即恢復。** 無論匯出成功或失敗，都會重新啟動剛才暫停的服務：依 Quadlet 的 `After=`、`Requires=` 與 `BindsTo=` 分組（Quadlet 不會為 `Requires=` 自動加上 `After=`，所以需要的服務也會先啟動），可以同時啟動的一起啟動，沒有寫明依賴的服務依目錄的順序；服務沒有啟動時再試一次。匯出失敗、且資料庫在過程中停止時，也會嘗試重新啟動資料庫，再重新啟動寫入服務讓它們重新連線。
6. **檢查資料卷匯出。** 每個資料卷的匯出檔都以還原時相同的規則完整檢查。含有還原時無法匯入的內容（例如指向資料卷外的相對符號連結、裝置檔、應用擁有者的使用者命名空間對應不到的擁有者），或超過 4,000,000 個項目時，備份失敗，訊息指出資料卷與項目；這時應用已恢復執行。
7. **再次確認核對快照**（有設定時）。服務恢復後再讀一次，和暫停前相同才保存；應用在備份前只部分執行時，這次讀取最多等到目錄設定的健康檢查逾時。兩次不同時（例如仍有寫入進行中，或有尚未套用的設定在服務重新啟動時才生效），這份備份不保存快照，日後還原時略過資料比對（結果顯示「未比對」），作業紀錄會說明。
8. **映像在服務恢復後才匯出**，不會延長暫停時間。映像若在備份期間被更換，備份失敗並要求重做。
9. **封裝、驗證後才列出。** 備份檔先寫在私有暫存區（加密時用這台設備的金鑰），再完整讀取（加密時解密）並逐項核對大小與 SHA-256，通過後才移到保存位置、出現在列表。未通過驗證的備份不會被列出。

暫停時間會記錄在備份中，備份詳情顯示為「備份時暫停應用寫入 N 秒」。選擇多個應用時逐一處理，每個應用只在自己的匯出期間暫停。備份完成的結果頁另外列出每個應用的**寫入暫停**（服務停止到全部再次執行）與**無法使用**（第一個服務停止到所有健康檢查通過）的秒數；先前只記錄寫入暫停，例如參考主機上 LiteLLM 記錄的暫停是 15 秒，實際到服務就緒約 70 秒。

參考數字：最終回歸中，示範應用 142 MB 的含映像備份暫停寫入 2 秒，健康檢查端點最長約 2.5 秒無法回應；資料卷約 600 MiB 時暫停 9 秒，最長約 10 秒無法回應。冷備份還要加上資料庫停止與啟動的時間：示範應用的資料庫資料卷冷備份暫停約 4 秒。改為一次停止與分組啟動後，實驗室以兩個各需 15 秒才停止的寫入服務（模擬 n8n 的 task runners）加上 300 MB 主機資料夾，與前一版引擎在同一台設備、同一份資料上量測（2026-11-14）：輔助服務在 Quadlet 檔寫明 `After=<主服務>.service`（參考主機 n8n-runners 的寫法）時，備份的寫入暫停由 39 秒降為 22.6 秒，主服務自己的中斷維持約 6.5 秒；沒有寫明時寫入暫停由 38 秒降為 24.2 秒，但所有服務同時停止、主服務一開始就停，它自己的中斷由 6.6 秒變成 22.9 秒。停止很慢的輔助服務請在 Quadlet 檔寫明 `After=<主服務>.service`，systemd 就會先停它們、最後才停主服務。主機資料夾在暫停期間整份打包，資料夾越大暫停越久：參考主機上 Home Assistant 的設定資料夾（3,344 個項目）與 Nextcloud 的 4 個資料夾（約 970 MB）見 [production-onboarding.md](backup/production-onboarding.md)。

應用在備份前沒有完整執行時，備份後不等待健康檢查；沒有任何寫入服務需要暫停時，暫停時間記為 0。

## 備份保存在哪裡

備份保存在這台設備的 `/var/lib/woowtech-backup/archives/`（只有 root 可存取）：每份備份是一個 `<備份 ID>.tar` 檔（舊格式為 `.woowbackup`），加上一個列表用的 `.json` 索引。「下載未加密版本」建立的未加密副本暫時放在 `/var/lib/woowtech-backup/exports/`（只有 root 可讀），15 分鐘後自動刪除。「總覽」的「本機儲存空間」顯示保存位置、可用空間與備份佔用量，「各應用的備份空間」依應用分計備份的份數與大小（一份備份含多個應用時，依各應用封存檔的大小分攤；舊格式的備份平均分攤並標示「估計」）。其他執行資料的位置見 [operations.md](operations.md)。

**本機備份與應用資料通常在同一顆磁碟，無法防範磁碟故障或設備遺失。** 重要的備份請下載保存到其他位置。

| 列表中的類型 | 來源 |
| --- | --- |
| 手動 | 從「建立備份」建立 |
| 排程 | 「排程備份」在設定的日子與時間自動建立，或按「立即執行一次」建立（2026.11.17.1 起）。每個應用保留最新幾份（預設 7 份），較舊的在下一次排程備份成功後自動刪除，見「排程備份」 |
| 還原前備份 | 原位還原前由系統建立的「還原前自動備份」（不含映像）。每個應用保留最近 3 份，較舊的在之後的原位還原成功後自動刪除；失敗或中斷的還原仍需要的還原前備份不會被自動刪除 |
| 上傳 | 從「從檔案還原」上傳的檔案 |

手動備份可以設定每個應用保留最新幾份，上傳的備份只在「清理備份」中勾選時才刪除；見「清理備份與保留原則」。排程備份只依「排程備份」自己的保留份數清理，手動備份的保留原則不會計算它們。

## 建立備份

1. 按「建立備份」。
2. 勾選要備份的應用，可一次選多個。狀態為「未部署」或「異常」的應用不能選（頁面會說明原因）。
3. 決定是否勾選「包含容器映像」（見下方），以及「加密此備份」（預設依「預設加密備份」設定，見「加密選擇」）。
4. 可填寫備註（最多 200 字，不可包含換行或 Tab）。
5. 按「開始備份」（不加密時按鈕為「開始備份（不加密）」，「預設加密備份」開啟時還要先勾選確認風險）。頁面會轉到作業進度；可以關閉瀏覽器，稍後到「活動紀錄」查看。完成的結果頁列出備份大小、是否加密、寫入暫停與每個應用的無法使用時間；保留原則刪除了較舊的手動備份時也會列出。

建立備份需要：應用已部署且資料庫服務正在執行、沒有其他作業進行中；加密的備份還需要這台設備已建立加密金鑰。沒有設備金鑰時，頁面上方的提醒不會阻止建立**不加密**的備份。

**何時包含容器映像：** 要還原到無法連網、或取不到相同映像的設備時必須包含。以 `localhost/` 開頭的本機建置映像無法從映像庫下載，要在沒有這個映像的設備還原就一定要包含。包含映像會讓檔案明顯變大：實驗室示範應用含兩個映像約 142 MB，不含映像約 0.15–0.4 MB（依測試資料量）。

## 排程備份

2026.11.17.1 起，「排程備份」會在你選的日子與時間自動建立備份，不必每次手動操作，類似 Home Assistant 的自動備份。**預設是關閉的。** 排程備份和手動備份一樣保存在這台設備，一樣要另外下載保存到其他位置。

### 開啟排程備份

1. 在「總覽」的「排程備份」卡片按「開啟排程備份」（設定過之後是「設定排程備份」），或在「備份列表」按「排程備份」。
2. 打開「自動建立排程備份」。「預設加密備份」開啟時，要先保存緊急金鑰：頁面會顯示「開啟排程備份前，請先保存緊急金鑰。」並提供「前往加密金鑰」（還沒有金鑰時是「請先建立加密金鑰並保存緊急金鑰」）。在「加密金鑰」完成後按「回到排程備份」，剛才的選擇都還在。原因和 Home Assistant 一樣：排程備份會在沒有人操作時建立加密的備份，萬一這台設備故障，沒有緊急金鑰就無法在其他設備還原它們。
3. 選擇「每天」或「每週指定的日子」（勾選週一到週日中的幾天），再選時間（以 5 分鐘為單位）。時間一律以**這台設備的時間**為準，頁面會寫出設備的時區，例如「Asia/Taipei，UTC+08:00」。你用的電腦時區和設備不同時，頁面會另外提醒，並寫出下一次排程在你這裡是幾點。頁面上排程的時間（下一次、上一次、沒有執行的排程、作業的排程時間）都是設備的時間；「活動紀錄」與作業頁的其他時間是你電腦上的時間，所以兩者不同時，排程的時間會標示「設備時間」。
4. 選擇「全部應用（之後新增的也會包含）」或「只備份選擇的應用」。選擇的應用目前無法備份（尚未部署或狀態異常）或已停止時，頁面會先說明：排程時若仍是這樣，這個應用會被略過（已停止的應用若有資料庫要匯出）。
5. 「包含容器映像」預設不勾選：每個映像可能有數百 MB，每天都包含會很快用掉這台設備的空間。
6. 加密跟隨「預設加密備份」，頁面只顯示目前的設定（要改請到「加密金鑰」）。
7. 「保留最新幾份排程備份」預設 7 份，也可以選「全部保留」，見下方「排程備份的保留份數」。
8. 按「儲存排程…」。頁面會先預覽，對話框列出設定、接下來 3 次排程的時間，以及下一次排程備份成功後會刪除哪些較舊的排程備份（含原因）、哪些暫時受保護而不會刪除。**在對話框按下確認之前，什麼都不會儲存。** 排程開啟且有備份會被刪除時，要先勾選「我了解下一次排程備份成功後，上列備份會被刪除」。儲存本身不會建立或刪除任何備份；每次變更都記錄在系統日誌。

要停止時關閉「自動建立排程備份」並儲存；關閉不需要金鑰，也不需要勾選刪除的確認：排程關閉後不會自動建立或刪除任何備份，已建立的排程備份會保留。對話框只提醒：之後若按「立即執行一次」，它完成後才會依保留份數刪除較舊的排程備份。

### 到了排程時間會發生什麼

- 設備每 5 分鐘檢查一次排程（頁面稱為「排程檢查」）。到了設定的時間，會在 5 分鐘內開始一個和手動備份一樣的備份作業：每個應用短暫暫停寫入（約 10–90 秒，依資料量），匯出後恢復應用，完整驗證後才列出。這段時間應用會短暫停止寫入，請把時間設在少人使用的時段（預設 03:00）。
- 加密方式依開始時的「預設加密備份」；開啟時，備份以這台設備的金鑰加密。
- **有其他作業正在進行**（例如還原或驗證）：在它結束後 5 分鐘內開始（下一次排程檢查），作業標示「等其他作業結束後開始」。如果一直到下一次排程時間都還沒結束，前一次就記為「未執行」。
- **設備當時沒有開機**（或排程檢查沒有在執行）：開機約 10 分鐘後補做一次，作業標示「補做錯過的排程」；錯過好幾次時只補最近的一次。下一次排程在 3 小時內時就不補，記為「未執行」。開機後 10 分鐘內不會開始任何排程備份。
- 時區改變在下一次檢查生效；時鐘被往回調超過一天時，排程從現在重新開始計算。
- 備份完成後，依「保留最新幾份排程備份」刪除較舊的排程備份。
- 一次只能有一個作業：排程備份進行中時，不能同時開始其他備份或還原。

### 「部分完成」、「未執行」與失敗

- **部分完成**：排程時有些應用尚未部署、狀態異常、已經不在這台設備的應用設定中，或已停止而無法備份（備份時資料庫必須在執行中；沒有資料庫要匯出的應用，停止時也能備份）。這些應用會被略過，其他應用照常備份。手動備份已停止的應用仍會失敗並說明原因。作業顯示「部分完成」，結果列出沒有包含的應用與原因，頁面上方顯示「部分完成：上次排程備份沒有包含「…」。請查看作業結果了解原因。」。一個應用都不能備份時，作業失敗。
- **未執行**：這一次排程沒有建立備份，例如設備當時沒有開機、有其他作業一直在進行、「預設加密備份」開啟但這台設備沒有加密金鑰、沒有可以備份的應用，或背景作業無法開始。「活動紀錄」把它和作業列在一起，狀態是「未執行」，並寫出原因；頁面上方也會說明，例如「… 的排程備份沒有執行：當時有其他作業一直在進行。」。
- **失敗**：作業開始了但沒有完成，例如空間不足（在暫停任何應用之前就會檢查）。頁面上方顯示「上次排程備份失敗：…」，並連到作業結果。作業意外中斷時顯示「已中斷」，處理方式和手動備份相同（見「已中斷的作業」）。
- 系統**不會自動重試**；依原因處理後，下一次排程照常執行，也可以按「立即執行一次」。

頁面上方可能出現的其他提醒：「排程備份已逾期：…」（排程時間過了 30 分鐘還沒有開始）、「排程檢查沒有在執行，排程備份不會自動開始。…」（計時器已啟動 15 分鐘仍沒有任何一次檢查時才會出現，剛安裝或重新啟動的計時器不會；請重新執行備份元件的安裝程式，見 [operations.md](operations.md)），以及排程的設定檔或紀錄檔有問題時的說明（排程會暫停，不會刪除任何備份；設定檔內容不正確時重新儲存排程即可修正，權限等其他問題請通知工程人員）。設定檔無法使用時，排程設定頁顯示的是預設值而不是上次儲存的設定，並標示「需要重新儲存」；確認每個選項後再儲存一次。「… 的排程備份正在等其他作業完成」只是說明，不是問題。

### 立即執行一次

「立即執行一次」依**已儲存的**設定馬上建立一份排程備份（排程開啟或關閉都可以），頁面會轉到作業進度，和手動備份一樣可以關閉瀏覽器。完成後同樣依保留份數清理較舊的排程備份。表單有尚未儲存的變更時，要先儲存。它和手動備份一樣，不需要先保存緊急金鑰，但加密的備份需要這台設備的加密金鑰。

### 排程備份的保留份數

- 每個應用保留最新的 N 份**排程備份**（預設 7 份），較舊的在下一次排程備份成功（或部分完成）後自動刪除。一份備份含多個應用時，要超出每個應用的份數才會刪除。驗證未通過的排程備份不算在份數內，本身也會被刪除。
- **手動備份、還原前自動備份與上傳的備份不會被刪除。** 「清理備份」的手動保留原則也不會計算或刪除排程備份；兩種份數各算各的。
- 正被作業使用，或失敗、中斷的還原仍需要的備份，不會被刪除（和「清理備份」的保護相同）。
- 「全部保留」時不會自動刪除；需要時仍可以在「清理備份」勾選刪除排程備份。
- 每一筆刪除都記錄在系統日誌（`retention-delete … reason=schedule`），作業結果也會列出被刪除的排程備份。

### 在列表中的樣子與相容性

- 「備份列表」以「排程」標示排程備份，標題是「排程備份 · <日期>」，可以用「排程」篩選；「手動」篩選只列出手動建立的備份。「總覽」與「清理備份」的各應用備份空間，分開計算手動與排程的份數。
- 「活動紀錄」中，排程備份的作業顯示為「排程備份」，並寫出它是依排程、等其他作業結束後、補做錯過的排程，還是立即執行一次。
- 排程備份的檔案和手動備份完全相同（備註為「排程備份」），2026.11.15.2 也能讀取、驗證與還原。下載後上傳到另一台設備，會是「上傳」類型，不會被那台設備自動刪除。
- 降版到 2026.11.17.1 之前的版本時，排程備份會顯示為「手動」，舊版的手動保留原則也會計算它們；降版前的注意事項見 [operations.md](operations.md)。
- 這台設備的備份元件比頁面舊、不提供排程時，頁面顯示「這台設備的備份元件不支援排程」。

## 檢視、驗證、下載與刪除

在「備份列表」或備份詳情可以：

- **檢視內容**：讀取（加密時解密）備份的內容清單，列出格式與加密方式、應用、資料庫與 PostgreSQL 方式（單一資料庫、整個執行個體及其資料庫與角色數量；冷備份的資料庫隨資料卷或主機資料夾）、資料卷、主機資料夾（以 `~/` 開頭的路徑，`~` 是應用擁有者的家目錄；有說明或大小時一併顯示）、映像是否包含、應用機密與設定檔數量、資料核對項目（應用摘要與資料摘要的筆數）、每個應用封存檔的大小，以及與這台設備的相容性檢查。不會變更任何資料。
- **驗證**：在背景完整讀取（加密時解密）整個檔案，逐項核對大小與 SHA-256，**並以還原時相同的規則檢查每個項目的內容**：資料卷、主機資料夾與映像封存（備份內的 tar 檔）、資料摘要清單、資料庫角色定義、資料庫匯出檔與應用機密的大小。結果頁列出各應用檢查了哪些項目（例如「資料卷 1、資料庫匯出 1、應用機密 2」），以及還原時無法保留的內容（例如 setuid 位元）。資料庫匯出檔在驗證時只確認是 pg_dump 的匯出格式（結果頁標示「只檢查格式」）：這台設備建立備份時已由 `pg_restore` 完整讀取過一次，還原時會再完整讀取；上傳的備份則要到還原時才完整讀取資料庫匯出的內容。讀取暫存檔時發生的本機錯誤（例如磁碟 I/O 錯誤）不會把備份標成驗證未通過，作業以錯誤結束、驗證狀態不變。驗證與建立未加密副本時應用都在執行，所以這兩種作業會保留較多的可用空間給應用（檔案系統的 5%，至少 2 GiB、最多 10 GiB），空間不足時作業以 `insufficient-space` 停止，備份本身與它的驗證狀態都不變。通過後列表顯示「已驗證（內容已逐項檢查）」；建立時的驗證或較舊版本的驗證只顯示「已驗證（檔案完整）」。「已驗證（內容已逐項檢查）」代表還原時的內容檢查也會通過；只有與這台設備有關的檢查（應用擁有者的 ID 範圍、這台設備需要的映像名稱、PostgreSQL 版本、目錄項目）仍在還原的「相容性檢查」進行。驗證未通過的備份請勿用來還原。舊格式（`.woowbackup`）的備份也以相同方式驗證。
- **下載**：瀏覽器經由 Cockpit 的加密連線下載備份檔，內容與保存的檔案完全相同（加密的仍是加密的）。「下載」按鈕旁的選單（向下箭頭）列出下載方式：預設是「下載加密的備份檔（.tar）」，與按鈕相同。
- **下載未加密版本**（選單中，只有加密的備份）：對話框說明風險，勾選「我了解下載的檔案沒有加密…」後才會開始：系統在背景解密並驗證，建立一份未加密的暫時副本（每個應用一個 `.tar.gz`，檔名結尾 `-unencrypted.tar`），完成後自動開始下載；這台設備沒有該備份的金鑰時，會先要求輸入緊急金鑰。副本只有 root 可讀，15 分鐘後自動刪除（已開始的下載不受影響），到期前可在作業結果或備份詳情再次下載或「立即刪除」；建立、下載與刪除都記錄在系統日誌。副本中的資料庫密碼、API 金鑰與存取權杖都是明文。
- **刪除**：確認後刪除，無法復原，並記錄在系統日誌；需要保留請先下載。刪除「還原前自動備份」後，就無法再用它回到那次還原之前的狀態。正被作業使用的備份不能刪除；還原作業進行中時，任何還原前備份都不能刪除（失敗時可能需要它自動回復）。

**檢視內容很快，不做內容檢查。** 檢視只讀取每個應用的內容清單；完整的內容檢查由「驗證」與還原作業進行。2026-11-13 之前的版本中，「已驗證」只代表外層完整，刻意改造過資料卷的備份也會顯示已驗證；現在的驗證會發現這種備份（實驗室實測，見「實驗室驗證紀錄」）。

加密的下載檔內含資料庫、檔案與應用機密，請和緊急金鑰分開存放；未加密的檔案請當成密碼一樣保管。見「安全須知」。

## 在同一台設備還原（原位還原）

在「備份列表」選擇備份的「還原」，依序完成：

1. **金鑰**：只有這台設備沒有該備份的金鑰時，才會要求輸入緊急金鑰。
2. **預檢**：顯示整體檢查與每個應用的檢查結果。選擇要還原的應用；未通過檢查的應用無法選擇。預檢不會變更任何資料，也不檢查資料卷與映像封存的內部內容（還原作業會檢查）。
3. **確認**：頁面列出受影響的應用、停機影響與還原前備份的做法；應用有主機資料夾時，另列出會被整個取代的資料夾（`~` 是這台設備上應用擁有者的家目錄）。勾選「我了解還原會停止並覆寫上列 N 個應用的資料」後按「開始還原」。
4. **進度與結果**：結果頁列出健康檢查、**停機時間**（每個應用的服務停止秒數，以及從第一個服務停止到所有健康檢查通過的「無法使用」秒數）、「注意事項」（還原無法保留的內容，例如被移除的檔案權限），以及「備份時」與「還原後」的**資料核對表**：應用摘要逐欄比對；資料摘要每項一列，列出備份時與還原後的筆數（資料表、資料列；檔案、資料夾、大小）與「一致」「不一致」「未比對」。表格上方統計共幾項、幾項一致；不一致的項目可展開查看差異（遺失、多出或不同的資料表或檔案，最多 20 筆）。從這個頁面開始的還原，結果頁也會列出這些應用在備份中的主機資料夾；重新整理頁面後，改以作業訊息與作業紀錄為準。

上傳的**未加密**備份在確認頁多一個勾選項「我確認信任這個未加密備份檔的來源」（見「加密選擇」）。

還原作業依序執行：

1. **解密並驗證**：只讀取所選應用的封存檔（加密時解密）到私有暫存區，逐項核對大小與 SHA-256。
2. **相容性檢查**：內容同預檢，另外完整檢查備份中的資料卷、主機資料夾與映像封存。單一資料庫方式確認資料庫執行個體中沒有目錄未宣告的資料庫（重建資料卷會讓它們遺失）；整個執行個體方式確認備份的方式與目錄相同、備份中的資料庫帳號是可登入的超級使用者、目錄的資料庫帳號是執行個體的初始超級使用者、目前的執行個體沒有不接受連線的資料庫（它們不在任何備份中），以及映像有每個資料庫用到的擴充功能。備份來自另一個帳號的應用時，以「注意」提醒還原後資料會屬於這台設備的帳號。未通過時作業停止，沒有任何變更，也不建立還原前備份。資料庫服務沒有執行而無法確認時，會在啟動資料庫後、任何變更之前再確認。
3. **預先寫入主機資料夾**（有主機資料夾的應用）：應用仍在執行時，以應用擁有者身分把每個資料夾寫到同一層的新資料夾 `<路徑>.woowbk-new-<作業 ID>`；既有的資料都沒有改變。之後只要在停止服務前失敗，這些新資料夾都會被移除。沒有主機資料夾時這個階段顯示「略過」。
4. **保存還原前資料**：停止受影響應用的寫入服務，把它們目前的資料複製到保存位置的 `pending/<作業 ID>/`（不含映像），每個檔案寫入磁碟後才記錄下來；之後才開始變更，所以即使斷電，這份資料也完整。停止的寫入服務**不再重新啟動，直接交給還原**，應用只停止一次。這份資料要等應用恢復執行後（第 11 步）才封裝成「還原前自動備份」，封裝與驗證不算在停機時間內（2026.11.14.2；正式主機上 Hermes 可少停約 66 秒、Nextcloud 約 35 秒）。因為應用一直停著，還原前的資料無法再確認應用回報的核對值（http-json）：只以 http-json 核對、沒有資料摘要的應用，還原失敗而自動回復時只以健康檢查確認回復結果、不比對資料；預檢會以「注意」說明，回復完成時結果的注意事項也會寫出「未比對資料」。需要回復時也比對資料，請為應用加入資料摘要。保存失敗時作業停止，服務恢復，應用資料不做任何變更（見「無法建立還原前備份時」）。資料庫服務沒有執行時，會先嘗試啟動它。**在停止任何服務之前**，先依預估的資料量決定在哪裡封裝：
   - **應用恢復後封裝**（第 11 步）：可用空間要放得下保存的資料（預估量多算一成）、它的封裝檔，以及留給執行中應用的空間（磁碟的 5%，至少 2 GiB、最多 10 GiB）。還原後會刪除的解開資料（原位還原應用的資料，不含映像，最多算到預估量）可以抵用。
   - **停機期間封裝**：空間不夠在恢復後封裝，或這次還原也會全新部署應用（部署後的資料量無法事先估算）時採用，停機時間會比較長，作業紀錄與結果都會說明。做法和 2026.11.14.1 完全相同：需要的空間是預估量的 2.2 倍加 512 MiB；封裝、驗證並登記還原前備份後，刪除保存的資料，所以還原時的剩餘空間和先前版本相同；還原失敗時，自動回復會解開這份還原前備份。只有空間不夠解開它時，才保留保存的資料，供自動回復直接讀取。2026.11.14.1 能還原的，這一版都不會拒絕。
   - **兩種都放不下**：不停止任何服務就拒絕還原，錯誤會寫出較小的那個需要量（無條件進位）。還原的就是還原前備份，或已選擇不建立還原前備份時，和先前一樣直接還原，失敗時無法自動回復。
   - **資料保存後再確認一次**：保存的資料比預估多，或備份中的資料庫比目前的大（還原後資料庫會變大）時，若應用恢復後可能放不下封裝，就改在停機期間封裝。之後不會因為封裝空間不足而拒絕還原：停機期間也放不下封裝時，改在應用恢復後封裝，保存的資料留給自動回復使用。
   - **唯一的例外**：保存後可用空間少於設備保留的 512 MiB 時，還原可能用盡磁碟，失敗時也無法自動回復，所以在任何變更前拒絕，並刪除保存的資料。
5. 變更前的準備：再次確認資料庫執行個體，有未宣告的資料庫或無法列出時拒絕還原（單一資料庫方式）。接著載入備份中的映像，或從映像庫下載缺少的映像；若映像在備份後更新過，映像標籤會指回備份時的版本（備份包含該映像，或這台設備仍保留該版本時）。這一步失敗時，映像標籤會改回還原前的版本，服務恢復。
6. **停止應用**：以一次 `systemctl --user stop` 停止應用其餘的服務，並暫時停用（`systemctl --user mask`）資料庫以外的服務：資料匯入完成前，它們不會被自動啟動（包括開機時）。
7. **還原資料**：重建應用機密、寫入設定檔、刪除並重建資料卷，刪除資料庫的資料卷。資料卷與映像都以引擎重新產生的乾淨 tar 交給 Podman。主機資料夾與第 3 步寫好的新資料夾對調：原資料夾改名為 `<路徑>.woowbk-old-<作業 ID>`、新資料夾改為原名；原本的內容保留到整個還原成功後才刪除。有檔案的資料摘要時，在這時就與備份時比對。
8. **啟動資料庫並匯入**：先只啟動資料庫，讓它重新初始化。單一資料庫方式以單一交易匯入；整個執行個體方式先確認資料庫確實是新建立的執行個體（初始化時間晚於刪除資料卷）、這台設備的 PostgreSQL 主版本不低於備份時，再還原所有角色（映像建立的超級使用者不重建，而是套用備份時的屬性與密碼雜湊；之後確認它仍是可登入、可寫入的超級使用者），並逐一建立與匯入每個資料庫，包括 `postgres` 與映像初始化程式建立的資料庫（保留擁有者、編碼、語系、權限與範本標記；備份之後才建立的資料庫會被移除）。冷備份的資料庫直接以還原的資料檔啟動。有資料庫的資料摘要時，在其他服務啟動前比對。**任何資料摘要不一致，應用都不會啟動**，作業自動回復；不一致時會再讀一次，兩次讀到的也不同，表示有目錄沒有停止的寫入者還在寫入（例如其他容器或排程），這一項改為「未比對」並列入注意事項，不讓還原與自動回復因為移動中的資料而失敗。
9. **啟動應用**：恢復被暫時停用的服務並啟動：依 Quadlet 的 `After=`、`Requires=` 與 `BindsTo=` 分組，可以同時啟動的一起啟動，沒有寫明依賴的依目錄順序。
10. 健康檢查與應用摘要比對。
11. **封裝還原前備份**：（在停機期間封裝時這一步已完成。）應用已恢復執行後，把第 4 步保存的資料加密（依「預設加密備份」）、封裝並完整驗證成「還原前自動備份」，再刪除保存的資料。封裝前會再確認空間（應用執行中，除了封裝所需，另外保留磁碟的 5%、至少 2 GiB、最多 10 GiB 給應用自己寫入）。封裝失敗、空間不足或作業被要求停止時，還原仍算完成，結果的注意事項會寫出資料保存的位置。系統會在下一次開啟頁面或執行作業時處理：空間不足時不寫入，等有足夠空間才封裝（只說明一次）；其他原因再試一次，仍失敗時保留資料，需人工處理（不會自動刪除）。

停止應用（第 6 步）之前失敗時，應用資料沒有被變更：預先寫入的新資料夾被移除，還原前備份停止的服務重新啟動。**第 6 步開始後的任何失敗都會自動回復：** 系統直接用第 4 步保存的資料（先逐項核對大小與 SHA-256）把應用回到還原前的狀態，再把這份資料封裝成還原前備份，作業顯示「已自動回復」（資料夾直接移回原內容，不重新解開）。在停機期間封裝、保存的資料已刪除時，則和 2026.11.14.1 一樣解開還原前備份來回復，不再另外封裝。自動回復不會從映像庫下載映像，需要的映像版本必須仍在這台設備上。若自動回復也沒有完成，作業顯示「失敗」與「需人工處理」，並列出還原前備份 ID，可用它再次還原。

注意事項：

- 還原後，應用回到備份當時的資料；備份之後才寫入的資料會被覆寫（仍保留在這次的還原前備份中）。
- 單一資料庫方式的原位還原，會以備份中的單一資料庫重建整個資料庫資料卷。資料庫執行個體中有目錄未宣告的資料庫時，預檢與還原都會拒絕並列出資料庫名稱；無法列出時也會拒絕（例外見下一小節）。資料庫角色與權限設定，以及執行個體 `postgres` 資料庫中的資料表、函式或排程工作不會保留，預檢以「注意」列出。整個執行個體方式保留角色與所有資料庫；備份之後才建立的資料庫會被移除，預檢會以「注意」列出（還原前備份保留它們）。
- 「預設加密備份」開啟時，原位還原用這台設備的加密金鑰建立加密的還原前備份；還沒有金鑰時會自動建立（之後請下載並保存，換機或重灌前沒有保存就解不開備份）。設定關閉時，還原前備份不加密，不需要金鑰。
- 主機資料夾是**整個取代**，不是合併：資料夾回到備份時的內容，之後新增的檔案會被移除（仍在還原前備份中）。還原期間新舊兩份內容同時存在，應用擁有者家目錄所在的磁碟需要放得下兩份，還原前會檢查空間。
- 參考數字：最終回歸中，示範應用的原位還原（含建立還原前備份）約 30 秒，健康檢查端點最長約 6.3 秒無法回應；資料卷約 600 MiB 時約 156 秒，最長約 40 秒無法回應。改為預先寫入主機資料夾、一次停止與交接還原前備份的服務後，實驗室以 300 MB 主機資料夾與兩個停止很慢的寫入服務量測（2026-11-14，與前一版引擎比較）：輔助服務寫明 `After=` 時，還原作業 120.6 秒降為 75.5 秒，應用的中斷由三段（合計 30.3 秒、分散在 71.7 秒內）變成一段 26.6 秒；沒有寫明時還原作業 114.8 秒降為 70.0 秒，應用的中斷由兩段（合計 29.0 秒、分散在 70.1 秒內）變成一段 37.6 秒。實際時間取決於資料量與映像。

### 無法建立還原前備份時

還原前備份建立失敗時，還原會停止且不做任何變更，結果頁說明「還原在變更任何資料前失敗，應用維持原狀」。這通常是因為應用已經無法運作（例如資料庫無法啟動），所以也無法備份它。

- **還原的就是一份還原前自動備份時**（例如先前的還原中斷後，用它回到還原前的狀態）：系統仍會先嘗試建立新的還原前備份；建立不了就直接還原，不需另外選擇。確認頁會先說明可能沒有新的還原前備份，結果頁註明這次沒有建立。實驗室已在強制終止與重新開機兩種中斷後實測這條路徑，資料都與還原前相同。
- **還原其他備份時**：失敗的結果頁會提供「不建立還原前備份，直接還原…」。按下後回到還原精靈，確認頁多一個勾選項「我了解這次還原可能沒有還原前備份，失敗時無法自動回復」，勾選後才能開始。作業仍會先嘗試建立還原前備份，建立不了才直接還原；「作業內容」記錄這個選擇。

風險：沒有還原前備份時，還原失敗**無法自動回復**，應用可能只還原了一部分。資料庫沒有執行時，系統也無法確認執行個體中是否還有其他資料庫；這時仍會重建整個資料庫資料卷，其中若有其他資料庫將會遺失，結果頁的「注意事項」會寫明。只在應用已經無法運作、又沒有可用的還原前備份時使用。「不建立還原前備份，直接還原」這個選項目前只有單元測試與頁面測試，未在實驗室設備上實測。

## 在另一台設備還原

### 目標設備須符合

| 條件 | 說明 |
| --- | --- |
| CPU 架構相同 | 來源與目標架構不同時預檢會提示；備份內含其他架構的映像時預檢失敗。實驗室只驗證過 x86_64 |
| 系統版本 | 已驗證的組合為 Ubuntu 24.04、Cockpit 362、Podman 4.9（4.9.3）；其他組合未驗證 |
| 已安裝本專案 | 含「備份與還原」套件，以及 age 與 zstd（`bootstrap-ubuntu.sh` 會安裝），見 [deployment.md](deployment.md) |
| 已安裝該應用的目錄項目 | 應用 ID 與來源相同。應用尚未部署時，目錄項目還要提供部署範本。**還原以這台設備的目錄項目為準**。2026.11.15.2 起，備份附有建立時的目錄項目：這台設備沒有或不同時，可在預檢審查後安裝（見下方「備份附上的應用設定」） |
| 這台設備的加密金鑰 | 原位還原會先建立以這台設備金鑰加密的還原前備份，所以要先在「加密金鑰」建立金鑰（「預設加密備份」關閉時不需要）；沒有時預檢會說明，不會停止任何服務 |
| 應用擁有者帳號 | 這台設備目錄項目指定的帳號必須存在；UID 可以與來源不同（實驗室由 UID 1001 還原到 1007）。帳號要能執行 rootless Podman（已設定 subuid／subgid），並已啟用 linger，使用者服務管理器正在執行。備份中資料卷與主機資料夾的檔案擁有者（容器內的 UID／GID）都必須在這個帳號的 subuid／subgid 對應範圍內，還原作業在「相容性檢查」階段、任何變更之前確認（主機資料夾：實驗室 D2 由 UID 1001、另一個 subuid 範圍還原到 1007） |
| 映像取得得到 | 備份包含映像、這台設備已有同名映像（備份時的版本已不在時，使用設備上現有的版本），或可從映像庫下載。`localhost/` 映像無法下載，這台設備沒有時必須包含在備份中 |
| PostgreSQL 版本 | 10 以上；備份的 PostgreSQL 主版本不可高於這台設備資料庫映像的主版本。整個執行個體方式另外需要映像有資料庫用到的每個擴充功能（例如 pgvector） |
| 可用空間 | 保存位置：上傳需要檔案大小再加 512 MiB，解開備份需要備份內容大小再加 512 MiB；應用擁有者家目錄所在磁碟：約為該應用在備份中的資料量（含映像）的 2 倍再加 512 MiB。原位還原主機資料夾時，新舊兩份內容會同時存在，還原前會另外檢查 |
| PostgreSQL（冷備份） | 這台設備資料庫映像的 PostgreSQL 主版本必須與備份時相同，CPU 架構也要相同；預檢不檢查這一點 |
| 金鑰 | 加密的備份：建立備份那台設備的緊急金鑰，或已匯入這台設備的同一把金鑰。不加密的備份不需要金鑰 |

### 步驟

1. 在來源設備下載備份檔。
2. 在目標設備開啟「從檔案還原」，拖放或選擇 `.tar`（或舊格式 `.woowbackup`）檔並開始上傳。上傳只把檔案放進私有暫存區，不會變更任何應用，過程中可以取消。檔案由瀏覽器分頁傳送，上傳完成前請保持分頁開啟（要離開頁面時會先詢問）。傳送完成後，設備會讀取整個檔案、嚴格檢查外層結構（`.tar` 的每個應用封存檔都和 `backup.json` 記錄的大小與 SHA-256 核對）並計算 SHA-256（這不是完整驗證：內容要到「驗證」或還原時才完整解密核對）；若頁面等候逾時，檔案仍保留在設備上，按「重新確認」即可取得結果。完成後這份備份會以「上傳」類型留在「備份列表」，之後可再還原或刪除。上傳的**未加密**備份無法驗證來源，預檢會提示，確認時要另外勾選信任這個檔案。
3. 加密的備份在頁面要求金鑰時，貼上以 `AGE-SECRET-KEY-1` 開頭的整行金鑰，或讀取緊急金鑰 `.txt` 檔（檔案只在瀏覽器讀取，不會上傳）。勾選「保存此金鑰到這台設備」，日後同一把金鑰的備份就不必再輸入；金鑰要先確認能解開這份備份才會保存，錯誤的金鑰不會被存下。不勾選時，金鑰只交給這次作業使用，作業結束即刪除。
4. 預檢若顯示這台設備沒有某個應用的設定，或設定與備份時不同，按「審查備份中的應用設定」，確認內容後安裝（見下方）。
5. 預檢、確認、進度與結果同原位還原。

### 全新部署或原位還原

| 目標設備狀況 | 還原方式 |
| --- | --- |
| 沒有該應用的任何 Quadlet 檔 | **全新部署**：用這台設備上受信任的範本建立服務，再還原應用機密、設定檔、資料卷、主機資料夾與資料庫。這台設備已有同名的資料卷、資料庫資料卷、應用機密或設定檔（例如先前移除應用時留下的），或目錄列出的主機資料夾已存在且不是空的時，預檢失敗，請先移除；這可避免還原失敗時把它們一併刪除。主機資料夾的上層資料夾不存在時，以應用擁有者身分建立（實驗室 D2、D6 已驗證） |
| 該應用的 Quadlet 檔都在 | **原位還原**：同上一節，先建立還原前備份 |
| 只有部分 Quadlet 檔，或其中有符號連結 | 無法判斷，預檢失敗；請先修復部署 |

全新部署失敗時，系統會移除這次新建立的 Quadlet 檔、服務、資料卷、應用機密、設定檔與網路，並把這次載入映像時移動的映像名稱改回原本的映像（原本沒有該名稱時就移除它），作業顯示「已自動回復」。作業被強制終止或斷電時的處理見「已中斷的作業」。

設定檔會原樣寫入。若其中含有來源設備特有的值（例如 IP、網域），還原後需自行確認。

實驗室已驗證：

- dev-a 的備份經頁面下載、上傳到 dev-b（應用擁有者 UID 不同、應用未部署），全新部署後資料摘要與備份時相同，應用也能寫入新資料。
- 資料卷中 27 個測試項目（涵蓋絕對、相對與懸空的符號連結、硬連結、超過 100 bytes 的檔名與超過 255 bytes 的路徑、空目錄、setgid 與 sticky 目錄、user.* 延伸屬性、非 UTF-8 檔名、FIFO、不同擁有者）：原位還原與跨設備全新部署後，在應用容器內看到的類型、擁有者、權限、大小、修改時間、連結目標、內容雜湊、延伸屬性與硬連結都與備份時相同；只有次秒的修改時間被截到整秒（tar 格式只存到秒）。
- 目標設備已有同名的應用機密、設定檔、資料卷或資料庫資料卷時（逐一測試），預檢與還原都拒絕，沒有刪除或建立任何東西。

### 備份附上的應用設定

2026.11.15.2 起，每份備份都附上各應用建立時的應用設定（目錄項目，不含任何機密）。2026-11-15 在實驗室演練「全新設備還原」時發現：在新設備用「應用設定」掃描產生的設定，可能和來源設備的不同（例如把資料庫改成直接複製資料卷，而不是資料庫匯出），這時備份的內容對不上新設備的設定，無法還原。備份附上設定後，新設備可以改用建立備份時的設定：

- 預檢會為這類應用顯示「備份中的應用設定」與「審查備份中的應用設定」：
  - **這台設備沒有這個應用的設定**：安裝備份中的設定之前，這個應用無法還原。
  - **這台設備的設定檔無法載入**（例如擁有者帳號不存在、檔案格式錯誤）：檢查結果說明原因；可以審查後用備份中的設定取代它。原因是帳號不存在時，備份中的設定通常也需要同一個帳號，請先建立帳號再重新檢查。
  - **這台設備的設定與備份時不同**：可以維持目前的設定（還原以這台設備的設定為準），也可以改用備份中的設定。
- 按下後，頁面以和「應用設定」相同的規則檢查這份設定（帳號是否存在、是否與其他應用衝突等），並顯示：檢查結果、對既有備份的影響與提醒、和目前安裝設定的差異（有安裝時），以及這份設定會做什麼（擁有者、服務、資料庫、資料卷、主機資料夾、應用機密、設定檔、部署範本等）和它的完整內容。
- 通過才能按「安裝備份中的設定…」（取代既有設定時為「改用備份中的設定…」）；對話框再列出擁有者、服務、主機資料夾與部署範本，並要勾選「我已審查這份設定的內容、差異與影響」（上傳的未加密備份要勾選「我已逐項審查這份設定，並信任這個備份檔的來源」）。舊的設定保留在 apps-history，系統日誌也有紀錄。審查後這台設備的設定若被變更，安裝會被拒絕，頁面自動重新審查。
- 安裝後預檢自動重新執行：已輸入的緊急金鑰會保留，你原本的勾選也會保留，只會加勾原本無法還原、現在可以還原的應用。按「重新檢查」也會保留勾選。
- 沒有通過檢查時，頁面說明原因。請先依原因處理（例如建立擁有者帳號、安裝應用的套件以建立部署範本），再按「重新檢查」。需要修改設定內容時，可以按「複製完整內容」，在「應用設定」掃描到這個應用後貼到它的草稿，修改後安裝。瀏覽器不允許自動複製時（例如以 http 開啟 Cockpit），頁面會改為選取完整內容。
- 還原本身從不自動安裝設定；上傳的未加密備份無法確認設定的來源，頁面會另外提醒逐項審查。
- 2026.11.15.2 之前建立的備份沒有附上設定，預檢會提醒安裝建立備份時使用的設定（請另外保存一份）。
- 2026.11.15.2 起建立的備份，無法在 2026.11.15.1 以前的版本讀取（會顯示內容清單格式不正確）：請先更新目標設備，不要刪除備份檔。備份內的 README.txt 與緊急金鑰檔都有說明。

### 還原以這台設備的設定為準

備份檔提供資料內容（2026.11.15.2 起也附上建立時的應用設定，但只在你審查並安裝後才會成為這台設備的設定）。要寫入哪些應用機密、設定檔路徑、資料卷、資料庫與服務，一律由**目標設備**的目錄項目決定：

- 備份中有、但這台設備目錄未列出的項目，會被略過並在預檢提示。
- 這台設備目錄要求、但備份缺少的項目，會讓預檢失敗。
- 備份檔中的 Quadlet 檔從不安裝；全新部署只用目標設備上 root 擁有的範本。
- 備份檔不能攜帶任何程式；如何備份、還原由設備上安裝的備份元件決定。

## 從 Home Assistant 備份匯入

可以把 Home Assistant OS（HA）的備份檔上傳到這台設備，把其中 WOOWTECH 的 Odoo、n8n、Omnigent、Hermes、EMQX、Headscale、OpenDesign、code-server、Nextcloud 與 LiteLLM 附加元件的資料搬到這台的 Podman 應用。整個過程分成三段：**檢查**（不變更任何資料）→ **轉換**成這台的備份（不停機、不變更任何資料）→ 用一般的**還原**步驟取代這台的資料（和一般還原一樣，先自動保存還原前備份，失敗自動回復）。需要支援 HA 匯入的備份元件；較舊的備份元件會說明需要更新（見下方「錯誤與提示」）。

- **會搬過來的**：資料、資料本身的金鑰（例如 n8n 的加密金鑰、Headscale 的伺服器身分金鑰、LiteLLM 的加密金鑰 salt）和大多數應用的登入帳號（使用者跟著資料走；Hermes 例外，見下方）。
- **保持不變的**：這台的網址（Odoo 的 `web.base.url`、Headscale 的伺服器網址）、連接埠、資料庫密碼、Odoo 主密碼、n8n 的 webhook 網址與佇列設定、應用機密與服務定義，以及這台放在資料以外的設定檔（例如 Hermes 的 `hermes.env`、EMQX 的 `base.hocon`）。
- **條件**（檢查時逐項確認，不符合就無法轉換，並說明原因）：
  - 這台已安裝對應的應用，而且和 HA 那邊是同一個版本：Odoo 每個已安裝模組的版本都相同，n8n、Omnigent、Hermes、EMQX、Headscale、OpenDesign、LiteLLM 本身的版本相同（OpenDesign 比的是核心版本）（HA 附加元件有自己的版本號，檢查時換算成它附帶的產品版本再比較，例如 Omnigent 附加元件 0.1.23 是 Omnigent 0.21.0）；code-server 比較會寫入資料的四個程式：code-server、Pi、Claude Code、Codex（例如附加元件 0.1.14 是 code-server 4.139.1、Pi 0.99.1、Claude Code 2.1.285、Codex 0.167.0），這台的版本由備份元件在一個不連網的暫用容器裡執行各程式的 `--version` 讀取。這台還沒安裝時，HA 備份頁會寫「這台還沒安裝，請先到「應用軟體」安裝同版本」。
  - HA 那台是 x86（amd64）或 ARM（aarch64，例如樹莓派、HA Green）的 64 位元設備，兩種做的備份都能匯入這台。
  - 要搬過來的 Odoo 自訂模組不能含只能在其他處理器上執行的程式（例如 ARM 專用的 `.so`）；有的話會寫出模組名稱並擋下，請先在 HA 換成不含這類程式的版本再做一次備份。Hermes 的資料含其他處理器的程式時，會把檔名列出來並照樣搬過來（對話、記憶與技能照常能用，那些外掛或虛擬環境要在這台重新安裝）。n8n 的社群節點含這類程式時仍可匯入，但會提醒你該節點要在這台重新安裝。
  - Odoo 用到這台沒有的模組時，HA 備份裡要有那個模組。模組放在 HA 的 `/share/odoo_addons` 時，做 HA 備份要把 **share** 資料夾也勾進去。
  - HA 的 n8n 已經建立管理者帳號。
  - Omnigent：資料庫結構版本和這台相同，資料表與欄位也和這台完全相同（不同時會寫出是哪些資料表），HA 備份裡有 Omnigent 的登入金鑰與代理程式檔案。
  - EMQX：HA 的備份裡要有 EMQX 的內建資料庫（EMQX 啟動過）；其他和 HA 不同的地方（帳號驗證、授權、Dashboard 的預設密碼 admin／public、以「plain」保存的密碼等）都照 HA 匯入，需要注意的會列在「匯入前請確認」或提醒裡（見下）。
  - Headscale：不要求版本、IP 位址範圍或存取政策相同：HA 的 IP 位址範圍會寫進這台的設定檔（見下方），轉換後的資料庫要由這台的 Headscale 先試開（`headscale configtest`）通過才會打包；打不開時只有 Headscale 不匯入，這台不會變。
  - LiteLLM：附加元件 0.1.15（LiteLLM 1.104.0）搭配這台同版本的 LiteLLM，兩邊的資料庫結構版本（Prisma 遷移紀錄）與資料表欄位完全相同；HA 備份裡的加密金鑰（`data/secrets/salt_key`）必須就是 HA 資料庫所記錄的那一把，否則搬過來後儲存的供應商憑證無法解密，所以會擋下。HA 的資料庫若是在執行中備份的（含有 `backup_label` 或 `tablespace_map`），也會擋下（LiteLLM 附加元件備份時會先停止，正常的備份不會有）。HA 用 PostgreSQL 18、這台用 17：只有 LiteLLM 這樣從較新的版本搬到較舊的版本，而且只搬資料列（見下方）。這台的 LiteLLM **應用設定要用「單一資料庫」方式**（一個資料庫匯出項目，沒有資料卷或主機資料夾）：還沒安裝應用設定時，到「應用設定」掃描，LiteLLM 的草稿已經選好這個方式，審查後直接安裝即可；已經以冷備份或整個執行個體方式安裝的，檢查會擋下，請到「應用設定」掃描，在 LiteLLM 的草稿改選「單一資料庫」並安裝，再匯入一次。改變方式後，這個應用之前的備份無法以新設定還原（還原那些備份要先裝回原本的設定），所以安裝後請先再做一次備份。
  - 這台的空間足夠。

### 各應用搬什麼、留什麼（Omnigent、Hermes、EMQX、Headscale、OpenDesign、code-server、Nextcloud、LiteLLM）

還原前的說明會逐項列出下面這些內容（由備份元件寫出），檢查結果也會列出各項的數量。

- **Omnigent**：只搬 HA 的**資料**：資料庫結構（資料表、欄位、預設值、檢查與索引）用這台 Omnigent 自己的，HA 備份裡的資料庫結構不會執行；轉換時會確認這台的結構在讀取期間沒有改變，並在完成前檢查新的資料庫只含這台的結構與 HA 的資料。使用者帳號、工作階段、代理程式、排程、上傳的檔案和檔案區換成 HA 的；HA 的登入金鑰（accounts-cookie-secret）一起搬過來，所以這台目前登入的瀏覽器與裝置要重新登入。這台的管理者與 runner 帳號會保留、密碼不變；HA 也有同名帳號時以 HA 的為準。HA 的分享與管理者執行期設定不會搬過來，這台維持自己的設定。
- **Hermes**：對話、記憶、技能、排程、外掛與 HA 的設定檔（`config.yaml`）換成 HA 的。這台的 Dashboard 密碼、API 金鑰、Webhook 與工作階段金鑰以及 `hermes.env` 保持不變，`hermes.env` 中的金鑰會蓋過 HA 的同名金鑰。HA 的外掛會取代這台的外掛與配對（例如 Omnigent、Paseo）。HA 的 `/media` 資料夾不會搬過來。附加元件版本、這台的版本讀不出來，或資料夾裡記的版本不同，都只是提醒，不會擋下匯入；真正決定的是資料本身（資料庫結構版本不能比這台新）。HA 資料裡應該是一般檔案卻是連結或資料夾的項目、損毀的次要資料庫（連同它的 WAL）、取不到內容的硬連結都不會搬，會列在「匯入前請確認」；指到執行期檔案的硬連結改成複製檔案內容。沒有 `state.db` 或 `state.db` 損毀時，只有 Hermes 不匯入，這台的 Hermes 不會變。檔案再大也不會被拒絕（超過 8 MiB 的 `.env` 因為要先濾掉這台自己管理的金鑰，無法不處理就搬，會略過並列出）。這台應用設定裡的其他資料卷與資料夾（例如冷備份的資料庫資料卷）會照這台現在的內容原樣帶過去。
- **EMQX**（和 HAOS 還原一樣，以 HA 的為準）：MQTT 帳號、ACL 規則、Dashboard 帳號（含預設的 admin／public）、API 金鑰、封鎖名單、PSK、保留訊息，以及帳號驗證、授權來源（含 ACL 檔案）、「沒有符合規則的主題時」要允許或拒絕的處理、規則和連接器設定，都換成 HA 的；HA 的 API 金鑰會取代這台的，HA 的 EMQX 外掛不會搬過來。這台的節點名稱、連接埠、位址和其他設定保持不變；這台 bootstrap 帳號檔建立的 MQTT 帳號（例如 woow）會接到 HA 的內建資料庫認證上（接不上時會在提醒裡說，匯入後可能要重新建立）；這台自己的 ACL 檔案不會寫回，匯入前的自動備份裡還有。檢查時會先在暫用的 EMQX 裡試做一次完整匯入（多花約 1～2 分鐘），所以下列事項在「匯入前請確認」就看得到，確認一次就好：HA 的設定裡有能讀取這台檔案或環境變數的項目（用「file://」讀檔當密碼的設定、使用 jq 的規則）、會收到每個連線用戶端帳號與密碼的項目（HTTP、LDAP、SQL 等外部帳號驗證與外部授權來源、ExHook 伺服器），都會照 HA 原樣啟用，頁面列出它們的名稱，請只匯入你信任的備份；HA 的 EMQX 沒有啟用帳號驗證時，匯入後連得到這台 MQTT 的人不用帳號就能連線（頁面會寫這台的 MQTT 埠目前只有本機能連或整個區網都能連；公開網址或 ngrok 無法從這台查出，一律提醒）；HA 的 Dashboard 還在用預設的 admin／public，而這台的管理頁開在區網或有對外通道時，也要確認；EMQX 匯入時有部分設定無法匯入也要確認（名稱會列出來）。HA 用「plain」（不加密）保存 MQTT 密碼、或有沒有以目前雜湊方式保存的帳號時，會照 HA 匯入並提醒：明文密碼會留在這台和之後每一份備份裡。備份裡有好幾個 EMQX 資料庫又沒有記錄用的是哪一個時，自動選最後寫入的那個，可以在頁面改選。還原後會再核對 MQTT 帳號、ACL 規則和金鑰都和轉換時相同，不同就自動回復；只有設定不同（例如轉換之後這台改過設定）時只提醒，不回復。這台自己設的 EMQX_AUTHORIZATION__*／EMQX_AUTHENTICATION__* 環境變數在匯入後的下一次啟動會蓋過 HA 的設定，檢查會列出變數名稱（不列內容）。MQTT 密碼的保存方式（密碼雜湊）也以 HA 的為準：和這台不同時，這台現有的 MQTT 帳號匯入後無法再用原本的密碼登入，檢查會先列出這些帳號（只列名稱），匯入後要重新設定。這台在 EMQX 管理頁自己建立的 MQTT 帳號，匯入後會被 HA 的帳號取代（只保留這台 bootstrap 帳號檔的帳號），這是預期的行為。
- **Nextcloud**：使用者、檔案、分享、行事曆、聯絡人、應用程式密碼與 HA 的自訂應用（custom_apps）換成 HA 的；Nextcloud 的身分資料（instanceid 與加密用的 secret）也一起搬，所以 HA 的應用程式密碼和驗證碼式的雙重驗證（TOTP）可以繼續使用；綁定 HA 網址的通行金鑰或安全金鑰（WebAuthn）換網址後要重新登記。使用者的檔案放在 HA 的 share 資料夾（預設 `/share/nextcloud`）；備份裡沒有它時照常匯入（使用者檔案不會搬），處理方式見下方「Nextcloud 匯入」。這台的網址、信任網域、資料庫密碼、郵件與快取設定保持不變；Office 會改用這台的 Collabora（HA 暫存的 Collabora 設定會換成這台的，匯入後馬上可以開文件）。團隊資料夾（Team folders）的檔案和儲存空間記錄也會一起搬並改成這台的路徑。HA 的物件儲存（S3）不支援（Nextcloud 不匯入，其他應用照常）；伺服器端加密、使用者檔案裡的符號連結和 `.htaccess` 的處理見下方「Nextcloud 匯入」。這台的使用者檔案放在網站資料夾裡，所以匯入時一定會寫入 Nextcloud 自己的保護檔（`.htaccess`，禁止直接從網址下載檔案）。HA 先備份資料庫、Nextcloud 重新啟動後才備份 share 資料夾，如果備份當時有人在上傳或刪除檔案，檢查會提醒「檔案清單…和實際檔案不一致」，匯入後請照提醒執行一次檔案掃描（`podman exec -u www-data nextcloud-app php occ files:scan --all`）。HA 的 Nextcloud 資料庫裡 Nextcloud 本身不會建立的函式與觸發程序（例如相簿應用 Memories 建立的）不會搬，改列在「匯入前請確認」；其他種類的物件（檢視表、自訂類型等）仍會讓 Nextcloud 不匯入，見下方「Nextcloud 匯入」。匯入後請把 HA 的 Nextcloud 附加元件永久停用，並把同步用戶端、行事曆與聯絡人改連到這台的網址。
- **Headscale**：使用者、裝置、預先授權金鑰與 DNS 額外記錄換成 HA 的，HA 的伺服器身分金鑰（noise）也一起搬過來。這台的伺服器網址與 API 金鑰保持不變：HA 的 API 金鑰不會搬過來，這台的 Headplane 與 MCP 管理工具照常可用。**IP 位址範圍會改成 HA 的**（寫進這台設定資料夾裡的 `config.yaml`；應用設定沒有把設定資料夾列為主機資料夾時改不了，範圍保持這台的，範圍外的裝置會列在「匯入前請確認」）。**存取政策**：HA 有政策就換成 HA 的（資料庫裡的政策；HA 的政策檔不會套用，確認裡會寫）；HA 沒有政策，就保留這台現有的（政策存在資料庫時由備份元件複製進轉換後的資料庫；備份元件還不能複製時，這次只有 Headscale 不匯入，因為清掉政策會讓所有裝置互通）。HA 的伺服器身分金鑰不能用時，沿用這台的金鑰，所有裝置要重新登入（會列在確認裡）。HA 的 DNS 額外記錄格式不正確，或這台設定的檔案路徑會蓋到資料庫或身分金鑰時，這次不搬 HA 的 DNS 記錄並列在確認裡。
- **OpenDesign**：專案、對話與訊息（`app.sqlite`）、執行紀錄、成品、設計系統與範本、品牌、資料庫、記憶、技能、外掛、偏好設定，以及在 OpenDesign 裡設定的外部 MCP 伺服器、連接器與媒體服務金鑰換成 HA 的；偏好設定與外部 MCP 伺服器設定裡指向 HA 資料夾（`/data/opendesign`）的路徑會改成這台的（`/app/.od`）；Paseo 自己登記的 MCP 項目（`woow-paseo`）不會從 HA 搬過來，維持這台的。這台的登入密碼（API 權杖）、MCP 權杖與工具設定、代理程式（Claude Code、Codex、Pi、OpenCode）的登入、Omnigent 連線、Paseo 配對、安裝識別與 `open-design.env` 保持不變。HA 專用的共用工作區與共用技能會原樣放進這台的資料夾，但這台不會自動使用。兩邊的 OpenDesign 核心必須是同一個版本（附加元件 0.2.15 = 核心 `05b23f5a`，OpenDesign 0.24.1），否則檢查會說明版本不同。
- **code-server**（目錄項目 `woow-code-server`；三個資料卷，目錄有列出時加上工作區資料夾）：
  - 搬過來：VS Code 的設定（HA 的設定蓋過這台的，但 HA 專用而這台沒有的預設不搬：zsh 終端機、Prettier 格式化工具、Home Assistant／ESPHome 的 YAML 語言；這台的 ACP 代理程式、工作區信任與延伸模組自動更新設定保留，HA 另外加的 ACP 代理程式一起搬）、快捷鍵、工作設定、程式碼片段、全域狀態與本機記錄（兩邊都有的檔案以 HA 的為準）；HA 自己安裝、這台還沒有、而且不是其他處理器專用的延伸模組（`extensions.json` 換成這台的路徑）；Pi 的對話、Claude Code 的專案對話、檔案記錄與輸入記錄（兩邊依時間合併）、Codex 的對話與封存對話、技能，以及 Pi 的設定與模型清單（兩邊都有的檔案以**這台的**為準；同名的技能整個保留這台的）；共用 MCP 伺服器（`shared/mcp.json`：HA 的伺服器加進這台的清單，同名的保留這台的；帶有標頭或環境變數、或連到 HA 內部位址的會列出來請你確認）。
  - 工作區：HA 的 `/share/projects` 在 HA 的 share 資料夾裡，只有 HA 建立備份時勾選了 share 才會在備份中；有的話放進這台工作區資料夾（預設是擁有者的「桌面」`~/Desktop`）裡新的 `ha-projects-<日期>` 資料夾，這台原有的檔案不動。這台的應用目錄沒有列出工作區資料夾時，工作區不會搬過來。

- **LiteLLM**：虛擬金鑰、使用者、團隊、組織、模型、儲存的供應商憑證、預算、用量紀錄、管理介面存的設定與 ChatGPT 訂閱登入換成 HA 的；HA 的加密金鑰（salt）一起搬過來，取代這台的應用機密 `litellm-salt-key`（還原前備份保有這台原本的金鑰與資料，還原失敗自動回復或之後還原到匯入前，兩者都會放回來）。這台的主金鑰（master key）、管理介面帳號密碼、資料庫密碼與網址、`config.yaml`、`litellm.env` 與服務定義保持不變。只搬 HA 的資料：資料庫結構用這台 LiteLLM 自己的（轉換時在同一個快照讀出並確認期間沒有變動），HA 的資料表內容逐表以這台的欄位清單搬到新的資料庫，HA 備份裡的資料庫結構、HA 自己的 `woow` 結構描述與兩個手動建立的用量索引、HA 的其他機密檔與設定都不會搬過來。**這台原本的虛擬金鑰會失效**：檢查結果與還原前的說明會列出這台目前使用 LiteLLM 金鑰的其他應用（依這台的應用目錄、設定檔、服務定義與 Pi 代理程式的模型供應商清單 `models.json` 判斷，例如 Hermes、OpenDesign、Omnigent、Pi Agent；只讀出「有沒有用」，不讀出金鑰），匯入後要為它們重新設定金鑰；除了這個提醒，匯入不會改動那些應用。HA 的 LiteLLM 在資料庫裡存的代理設定（環境變數、記錄或通知的回呼）也會一起搬過來，並在這台生效（這台的 LiteLLM 以資料庫裡的設定為準）；檢查結果與還原前的說明會列出這些設定的名稱（不顯示內容），請確認都是你自己設定的再正式匯入。HA 的 LiteLLM 在資料庫裡存了會載入並執行程式的設定（例如 `post_call_rules`、`custom_auth` 這類自訂程式掛勾，或名稱裡有「.」的回呼模組）時，檢查會擋下並列出它們，請先在 HA 的 LiteLLM 移除後再重新備份（包含自訂模型供應商的處理程式、自訂護欄、轉送端點的程式模組、JWT 自訂驗證、路由外掛與自訂金鑰管理程式）；這些設定讀不完整（內容過大或逾時）時也會擋下，轉換時還會在新的資料庫叢集裡用實際搬過來的資料再檢查一次。應用設定有資料表內容核對（`postgres-digest`，草稿會加入）時也能匯入：轉換出來的備份沒有這項摘要，所以還原前的檢查會提醒、結果頁寫「未比對」；匯入前自動保存的還原前備份則有，還原失敗自動回復、或之後還原到匯入前時，會在應用啟動前逐表比對這台原本的資料是否都回來了。

### 步驟

1. **取得 HA 備份檔**：在 HA 的「設定 → 系統 → 備份」下載備份（`.tar`）。加密的備份請一併準備 **HA 備份金鑰**，也就是 HA 的「備份加密金鑰」（在同一頁的備份設定裡可以看到，格式像 `ABCD-EFGH-IJKL-MNOP-QRST-UVWX-YZ12`）；較舊的 HA 備份如果是用自己設定的密碼加密，就用當時設定的密碼。
2. **上傳**：在「從檔案還原」選擇或拖放這個檔案並開始上傳，和上傳一般備份檔相同。設備認出這是 HA 的備份後，會直接打開它的 HA 備份頁（不會像一般備份那樣先檢查內容）；之後也可以在「備份列表」找到它（標示「HA 備份」）。同一個檔案上傳兩次，只會留下一份。設備讀 HA 備份的方式和 HAOS 一樣寬：用 GNU tar、bsdtar 或 macOS 重新打包過的備份、檔案後面多出來的內容、備份說明檔裡看不懂的名稱或日期（日期顯示「日期不明」，清單改用上傳時間排序），都不會讓上傳失敗。只有說明檔（`backup.json`）不見、重複或看不懂，或檔案本身損毀、不完整、超出安全限制（例如外層項目超過 4096 個、說明檔超過 16 MiB），才會拒收。某一個附加元件的資料有問題時（檔案缺少、重複、不完整、損毀，或使用這台還不支援的加密格式），只有那一個會標出原因、不能匯入，其他附加元件照常。
3. **HA 備份頁**：列出名稱、HA 建立時間、是否加密（匯入時要不要 HA 備份金鑰）、大小與上傳時間，以及每個附加元件會怎麼處理：「可以匯入」（寫出這台對應的應用）、「還沒安裝」或「這台沒有對應的應用」。HA 把每個附加元件分開加密，所以「要不要金鑰」看的是可以匯入的附加元件本身；從 HA 下載的解密副本也可能還留著加密的附加元件。按「檢查並匯入…」開始匯入步驟。
4. **選擇應用**：勾選要搬過來的應用；這台還沒安裝的應用不能勾。勾了 Hermes、EMQX 或 Headscale 時，頁面會提示它們的附加元件檔案比較大（Hermes 的資料可能有好幾 GB，EMQX 與 Headscale 的附加元件裡還有 HA 自己建立的映像檔），檢查和轉換會花比較久的時間。「預設加密備份」開著而這台還沒有加密金鑰時，這一步就會提示「尚未建立加密金鑰」並提供「設定加密金鑰」：轉換好的備份要用這台的金鑰加密，沒有金鑰就不能轉換（仍可以先檢查）。設定好金鑰後，請回到 HA 備份重新開始匯入。
5. **金鑰**（只有所選的附加元件，或它們要讀的 HA share 資料夾有加密時，只問一次）：輸入 HA 備份金鑰。金鑰只留在這個頁面，交給檢查和轉換作業使用，用完就刪除，**不會存到這台設備**；離開這一頁或結束這次匯入後就要重新輸入。金鑰不正確時，頁面回到這一步並顯示備份元件的說明（例如「HA 備份金鑰不正確，請確認後再試一次。」），可以修正後再試。
6. **檢查**：背景作業「檢查 HA 備份」解開所選的附加元件，確認版本、模組與內容，在同一頁顯示進度（可以安全取消時會有「取消作業」）。檢查不會停止或變更任何應用；一個應用有問題（例如它的檔案損毀）只有它不能匯入，其他應用照樣有結果。
7. **結果與確認**：頁面最上面一行寫「可以匯入 N 個，不能匯入 M 個」。每個應用一張卡片，寫「可以匯入」或「不能匯入」。
   - **不能匯入的應用會自動排除，不會擋住其他應用。** 卡片寫出原因和你可以做什麼（例如它的檔案損毀、備份是在 EMQX 執行中做的）；這台的這個應用不會有任何變更，其他應用照常匯入。檢查結果沒有包含的應用也一樣，會列出名稱，可以按「重新檢查」再試。
   - 每張卡片還列出版本（版本不同只是告知，不再擋住匯入）、搬什麼（Odoo、n8n、Omnigent、Hermes、EMQX、Headscale、OpenDesign、code-server、Nextcloud、LiteLLM 各自的數量與匯入後怎麼登入，見上方「各應用搬什麼、留什麼」）、**系統會自動做**的事（不用勾，例如先把資料庫啟動起來讀）和**匯入後請留意**的事（不用勾）。
   - **需要你選的事**：Odoo 的資料庫（只有一個能搬時已經選好；有多個時自己選一個，每個資料庫列出聯絡人、使用者、附件、模組與大小；真的不能搬的那個寫出原因並且不能選）；備份裡有同一個附加元件來自兩個商店時，選要匯入哪一個；EMQX 有多個節點時選要匯入哪一個。選了附加元件或節點後，按「重新檢查」用這個選擇再檢查一次。
   - **匯入前請確認**：所有有後果的事列在**同一份清單**，勾一次「我了解上面列的事，開始匯入」就是全部確認。第一行永遠是「匯入會取代這台這 N 個應用現在的資料。匯入前會自動各做一份備份，失敗會自動退回。」；Odoo 的備份有多個資料庫時，再寫哪幾個會留在 HA（這台的 Odoo 一次只放一個資料庫，以後再匯入另一個會取代這次的）；其餘是備份元件列出的事，例如缺的東西（HA 備份沒有 share 資料夾、這台沒有的模組）、略過的檔案、匯入時會暫停的服務、安全上要注意的設定。每一行只寫名稱，不顯示密碼或金鑰。沒有勾就不能按「匯入」；換了選項（例如換了 Odoo 資料庫）使清單變了，要重新勾。
   - 「這只是測試」和以前一樣，預設不勾（見下方「測試匯入」）。
   - 按「匯入」開始整個匯入；「只轉換，之後再還原」只把資料轉成這台的備份，不取代這台現在的資料，轉換好的備份留在「備份列表」，之後自己再還原。
   - 這一頁不再有「有一個應用沒有通過，所有應用都不能轉換」的限制；只有一個應用都不能匯入時，才沒有「匯入」可按。
8. **匯入**：按「匯入」後，頁面直接開始，沒有另外的對話框。系統**一個應用接著一個應用**處理：轉換成這台的備份 → 自動保存這個應用的匯入前備份 → 換上 HA 的資料 → 健康檢查。頁面列出每個應用現在做到哪裡（等待中、轉換中、匯入中、已匯入…），下面是正在處理的那個作業的進度。每個應用只停自己的那一段時間；哪一個失敗，只退回它自己，其他應用照常。
   - **這台還沒有加密金鑰時**，匯入開始時會自動建立一把（不用先到「加密金鑰」設定），頁面上方的橫幅和匯入頁會一直提醒你下載並保存緊急金鑰，直到你確認已保存：沒有它，換機或重灌後就解不開加密的備份。
   - **取消**：「取消匯入」停掉目前的作業，整個匯入也跟著停止（還沒開始的應用標示「沒有開始」，這台的它們沒有任何變更）。「做完這個應用就停止」讓正在處理的應用做完，再停下來；已經進入不能中斷的階段時，也可以按這一個。
   - **離開頁面或重新整理不會停止匯入**（HA 備份金鑰在按下「匯入」時就交給設備，之後不需要）。回來時，頁面上方「進行中」的橫幅（或「活動紀錄」）可以打開進行中的作業，作業頁會列出整個匯入的每個應用，一個作業做完會自動接到下一個；從「總覽」重新整理時，頁面也會直接帶到進行中的作業。
   - **按下按鈕後設備很久沒有回應時**（等了兩分鐘），頁面不會直接說失敗：作業可能已經開始，頁面會用同一個要求再確認幾次，不會重複開始。仍然沒有回應時，請再按一次剛才的按鈕（只會接上同一個作業），或到「活動紀錄」看有沒有進行中的作業。
9. **結果**：匯入結束後，每個應用一行：**已匯入**（附這個應用的「匯入前備份」連結，要退回就用它還原）、**已退回原狀**（這個應用匯入失敗，已自動退回匯入前的狀態）、**沒有成功**（寫原因；需要人工處理時用紅色，並寫出要用哪一份匯入前備份還原）、**沒有匯入**（不能匯入的應用，寫原因和下一步）、**沒有開始**（匯入被停止，這台的它沒有任何變更）、**已轉換成備份**（只轉換，或匯入被停止；轉換好的備份在「備份列表」，按「還原到這台…」就用一般的還原步驟匯入）。「這次匯入和檢查時看到的不同」（例如檢查之後又多了一個服務掛在同一個資料夾）的應用只有它被排除，結果頁給「重新檢查並確認這個應用」。已匯入的應用下面接著寫「匯入之後請做」（把 HA 那邊的附加元件停掉、重新設定 MCP 管理工具、n8n 要修改的工作流程…）。
10. **匯入之後**：結果頁的「匯入之後請做」只列出要做的事，而且只列這次還原的應用：
    - 請把 HA 那邊的附加元件停掉（寫出 HA 附加元件的名稱），避免同一件事兩邊各做一次（例如排程或工作流程在兩邊各跑一次）；
    - 這台有 Odoo 或 n8n 的 MCP 管理應用（目錄項目 `odoo-mcp-admin`、`n8n-mcp-admin`，以這台目錄裡的名稱顯示）時，到那裡重新設定登入資料（登入帳號已經換成 HA 那邊的）；
    - 備份元件提醒的事，例如用 HA 那邊的帳號登入這台的 Odoo 或 n8n、確認搬過來的 n8n 社群節點能正常使用；Omnigent、Hermes、EMQX、Headscale 的提醒見下方「各應用匯入之後要做的事」；
    - 上傳的 HA 備份檔還在這台時：「匯入完成後，建議刪除這份 HA 備份檔（裡面可能有 HA 的密碼與權杖）。」並連到那份 HA 備份；
    - 可能需要修改的 n8n 工作流程。

### 一次匯入多個應用：一個接一個

勾了好幾個應用時，這台不是把它們一次全部換掉，而是**一個應用做完再做下一個**：先把這個應用的資料轉換成備份，接著自動保存這個應用的「還原前備份」、換上 HA 的資料、確認它正常；做完才換下一個應用。每個應用只停機自己的那一段時間，「還原前備份」也是每個應用各有一份。

- **一個應用有問題，只影響它自己。** 轉換失敗、還原前的檢查沒通過、或換上之後起不來（會自動退回匯入前的狀態），都只有那個應用沒有匯入，其他應用照常匯入。匯入結束後，每個應用各有一行結果：**已匯入**、**已退回原狀**、**沒有匯入**（會寫原因和下一步）。轉換好的備份都會留在「備份列表」，沒有匯入的應用可以之後再試。
- **會讓整個匯入停下來的事。** 你按了取消、HA 備份金鑰不對或缺少、這台的磁碟空間不足、上傳的 HA 備份檔本身有問題（不完整或被改過），或設備在匯入中重新開機。還沒做到的應用會標示「沒有開始」並寫明原因；這台的這些應用沒有任何變更。
- **取消。** 「取消匯入」會停掉目前的作業，整個匯入也跟著停止（還沒開始的應用標示「沒有開始」）。「做完這個應用就停止」會讓正在處理的應用做完（轉換之後的匯入也會做完），再停下來；已經進入不能中斷的階段時，也可以按這一個。
- **中途中斷。** 設備重新開機或程序被終止時，已經匯入完成的應用不受影響；中斷當下的那個應用會顯示「中斷」並說明這台是否有變更，沒有開始的標示「沒有開始」。系統不會自己接著做，請在「備份列表」確認結果後，對沒做完的應用重新匯入。
- **空間。** 一次只處理一個應用，所以磁碟用量的高峰是「最大那個應用」的量，不是全部加起來；轉換好的備份與還原前備份會一直留著，需要空間時到「清理備份」刪除。
- **在「備份列表」還原轉換好的備份。** 由 HA 轉換出來、含有多個應用的備份，從「備份列表」還原時也是一個應用一個應用做，一個失敗不會讓其他已經還原好的應用退回。一般備份的還原維持原本的方式（失敗時全部自動退回）。

### 各應用匯入之後要做的事（Omnigent、Hermes、EMQX、Headscale、OpenDesign、LiteLLM）

這些提醒由備份元件寫出，結果頁照原文列出（數量與網址是這次匯入的）：

- **Omnigent**：用 HA 那邊的 Omnigent 帳號和密碼登入；把每一台 runner（例如 HA 的 Pi Agent、其他電腦上的 omnigent host）改連到這台的 Omnigent 網址並重新登入，在那之前 HA 的 runner 會顯示離線；HA 啟用中的排程會在這台執行，請確認它們有可用的 runner（測試匯入時改為提醒：已暫停幾個排程，確認無誤後再到 Omnigent 重新啟用）；HA 有公開分享的工作階段時，提醒它們搬過來後仍然公開。Omnigent 沒有 MCP 管理工具，所以沒有 MCP 的提醒。
- **Hermes**：用**這台**的 Hermes Dashboard 密碼登入（不是 HA 的）；呼叫 Hermes API 或 Webhook 的地方改用這台的網址與 API 金鑰；**重新配對 Hermes 的 Omnigent 與 Paseo 外掛**，HA 上的配對不會沿用；HA 的設定連到 HA 內部的位址時（例如 `homeassistant.local` 或 HA 上其他附加元件），改成這台連得到的位址；用到 HA 的 `/media` 的設定、排程或技能改用這台的資料夾；HA 的排程會在這台執行，請先停掉 HA 的 Hermes。
- **EMQX**：把 MQTT 裝置與服務（例如 Home Assistant 的 MQTT 整合、Zigbee2MQTT）改連到這台的 EMQX；用 HA 那邊的 EMQX Dashboard 帳號和密碼登入；HA 沒有啟用帳號驗證時，匯入後這台也一樣不用帳號就能連線，要用帳號的話請先在 EMQX 管理頁「存取控制 → 認證」開啟；HA 的規則或連接器連到 HA 內部的位址時要改；HA 的 EMQX 外掛需要時請在這台重新安裝；HA 的 EMQX 附加元件頁的選項（例如自己設的 EMQX_ 環境變數 env_vars）沒有搬過來，設過的話請到這台 EMQX 的環境設定檔補上；HA 的 API 金鑰已取代這台的，使用這台 EMQX API 的工具要換成新的金鑰；HA 保存 MQTT 密碼的方式和這台不同時，重新設定檢查頁列出的這台 MQTT 帳號：到這台 EMQX 管理頁「存取控制 → 認證」的內建資料庫替這些帳號重設密碼或重新建立，由 bootstrap 帳號檔建立的帳號（例如 woow）刪除後重新啟動 EMQX 就會用原本的密碼建回。
- **Headscale**：**把每一台裝置的登入伺服器改成這台的網址**（例如 `tailscale up --login-server=<這台的網址>`），不再使用 HA 的網址；**把 HA 的 Headscale 附加元件永久停用**（關掉開機自動啟動）：兩台伺服器使用同一個身分金鑰卻有不同的資料，會讓裝置連線錯亂。
- **OpenDesign**：用**這台**的 OpenDesign 帳號 `open-design` 和這台的 API 權杖登入（不是 HA 的登入）；代理程式沿用這台原本的登入，HA 上登入的帳號不會搬過來，需要時在這台的終端機重新登入；Omnigent 與 Paseo 沿用這台的連線與配對，請到 HA 的 OpenDesign 連過的 Omnigent 伺服器移除 HA 那台主機；HA 的 OpenDesign 附加元件內建的 MCP 伺服器不會搬過來，指向它的 MCP 連接器（例如 claude.ai）要刪掉，改用這台的 MCP 網址與權杖重新建立；在瀏覽器裡輸入的模型金鑰（BYOK）不在備份裡，要在這台重新輸入；從資料夾匯入的專案在這台打不開，要重新匯入；HA 有啟用中的例行工作時，提醒先停掉 HA 的 OpenDesign，避免重複執行。
- **code-server**：用**這台**的 code-server 密碼登入；Pi、Claude Code、Codex 沿用這台的登入，需要時在 code-server 的終端機重新登入（`pi` 的 `/login`、`claude auth login`、`codex login --device-auth`）；HA 的對話記錄搬過來後只能查看（工作目錄從 `/share/projects` 變成 `/workspace`）；Omnigent 與 Paseo 連接器維持這台的，HA 的 code-server 連過 Omnigent 時請在 Omnigent 上移除 HA 那台主機；HA 的 SSH 金鑰、git 身分與 zsh 指令記錄不會搬過來；沒有搬過來的延伸模組（其他處理器專用）、HA 自訂的 ACP 代理程式、帶權杖的 MCP 伺服器與連到 HA 內部的位址會逐一列出；工作區裡的 `node_modules`、`.venv` 若來自 ARM 的 HA，請在這台重新安裝。code-server 沒有 MCP 管理工具，所以沒有 MCP 的提醒。
- **LiteLLM**：用**這台**的主金鑰與管理介面密碼登入（HA 的主金鑰在這台不能用）；HA 的虛擬金鑰在這台繼續有效，原本連到 HA 的用戶端改連到這台的 LiteLLM 網址；**為這台使用 LiteLLM 金鑰的應用重新設定金鑰**（名單見還原前的說明）；有 ChatGPT 訂閱登入時請停掉 HA 那邊的 LiteLLM（登入權杖會輪替，兩邊同時用會讓其中一邊失效），HA 在備份之後還執行過的話到這台的 ChatGPT 頁面重新連結；HA 的模型設定連到 HA 內部的位址時改成這台連得到的位址。
- **MCP（Hermes、EMQX、Headscale、OpenDesign、LiteLLM）**：這台有對應的 MCP 管理應用（目錄項目 `hermes-mcp-admin`、`emqx-mcp-admin`、`headscale-mcp-admin`、`opendesign-mcp-admin`、`litellm-mcp-admin`，以這台目錄裡的名稱顯示）時，提醒到那裡確認或重新設定連線資料（MCP 管理工具的設定不會從 HA 搬過來）；另外提醒：HA 上如果有「Woow Hermes MCP Server」等 MCP 附加元件，請把它停掉，並把指向它的 MCP 連接器（例如 claude.ai）刪掉，改用這台的 MCP 網址重新建立。這些 MCP 提醒由備份元件寫出，頁面不會再用自己的話重複一次。

轉換好的備份會留在「備份列表」（標示「由 HA 轉換」），詳情頁寫出它來自哪一份 HA 備份；之後要再還原它，按「還原」即可。

### 測試匯入

先試試看時，在「結果與選項」勾選「這只是測試」。測試匯入只關掉下面寫的功能，還原前的說明、結果頁、轉換好的備份與作業頁都會寫明這是測試匯入，以及各應用關掉了什麼、什麼沒有關掉：

| 應用 | 測試匯入時 |
| --- | --- |
| n8n | 搬過來的工作流程全部先停用 |
| Odoo | 不寄信、不執行排程動作（並換一個新的資料庫識別碼） |
| Omnigent | 啟用中的排程全部先暫停；確認無誤後到 Omnigent 重新啟用 |
| Hermes | **不會暫停任何功能**：排程和訊息機器人照常執行，所以測試時請停掉 HA 那邊的 Hermes 附加元件，避免兩邊各做一次 |
| EMQX、Headscale、OpenDesign、code-server、LiteLLM | 不會先關掉任何功能，還原後照常運作（OpenDesign 的例行工作會照常執行） |

只匯入 Odoo、n8n 或 Omnigent 時，測試期間 HA 那邊可以照常使用；有 Hermes、EMQX 或 Headscale 時則不一定（Hermes 要先停掉 HA 那邊的附加元件；Headscale 的提醒會請你停用 HA 的 Headscale 附加元件）。確定要正式搬過來時，請重新匯入一次，並且不要勾選。

### 在列表中、刪除與作業紀錄

- 「備份列表」的類型篩選「HA 備份」會列出上傳的 HA 備份與由 HA 轉換的備份；搜尋也找得到 HA 備份的名稱與附加元件名稱，計數包含 HA 備份。
- 上傳的 HA 備份檔會一直留在這台，直到你刪除（「清理備份」與保留份數不會刪它）。在 HA 備份頁或列表按「刪除這份 HA 備份」（先確認）只會刪除這台上的 HA 備份檔：HA 那邊的備份不受影響，已經轉換好的備份也會保留。作業正在使用它時無法刪除，頁面會連到那個作業。
- 「活動紀錄」把這兩種作業寫成「檢查 HA 備份」與「轉換 HA 備份」，作業頁列出結果（檢查的結果也列出每個 Odoo 資料庫能不能搬、原因與需要注意的地方）；轉換的結果頁有「還原到這台…」可以直接開始還原。
- 「總覽」的本機儲存空間另外列出上傳的 HA 備份份數與大小（它們不算在備份的佔用空間裡）。

### 匯入時這台會自己處理的事

和 HAOS 還原一樣，下面這些不用你先準備；做不到的，只有那一個應用不匯入，並寫出原因，這台的應用不會有任何變更。

- **映像不在這台**：自動下載（用這個應用自己的帳號，和它下次啟動時會做的一樣），結果頁會寫「已自動下載」。下載不到（沒有網路、映像倉庫拒絕、空間不足，或是在這台自己建置而現在不見了的映像）才會停下，並說明原因與要怎麼做。
- **資料庫或服務停著**：為了讀取這台目前的設定，會暫時把它啟動，等它準備好再讀，讀完自動恢復原狀（停止）：檢查時是這個應用檢查完，轉換時是整個轉換結束。結果頁會寫「原本停著，已暫時啟動」。啟動不了或一直沒有準備好，只有這個應用不匯入。
- **這個帳號的背景服務（linger）沒開**：自動開啟，這個設定會保留，讓應用在沒有人登入時也能執行；開不起來時會說明是這個原因，不會再說成「還沒有部署完成」。
- **HA 備份裡的硬連結**：指到沒有搬過來的檔案時，改成複製檔案內容；做不到的只略過那一個並列在「匯入前請確認」。
- **這台資料卷裡你自己建立、指到資料卷外面的符號連結**：還原不接受這種連結，所以匯入時只略過那一個連結並列出（顯示全部數量與前 20 個名稱），其餘照搬。
- **等待時間依資料量放大**：資料大的應用會等得比較久，不會因為「等不及」而失敗；原本的等待時間是最短的下限。
- **失敗的原因**：用固定的句子說明（例如「磁碟空間不足」「資料庫帳號或密碼和這台的設定不符」「映像倉庫拒絕下載」），不會把命令的輸出（可能含密碼或資料）原樣顯示。
- **暫用容器或資料卷移除不了**：只佔用空間、不影響資料，作業紀錄會有一行提示，作業結束時與下次作業開始時再清；不會讓匯入停下。

### 匯入 HA 備份時，這台會自動處理的事（還原步驟）

匯入 HA 備份的最後一步是把轉換好的備份還原到這台。和一般還原不同的地方，都會先列在「匯入前請確認」裡，不是做完才告訴你：

* **暫停正在用同一份資料的服務**：如果檔案管理、code-server 之類的服務掛著這個應用的資料夾（或整個家目錄），或寫入它的資料卷，匯入時會先暫停它們，完成後自動啟動；確認清單會寫出服務的名稱。暫停期間它們無法使用。不是由服務啟動的容器沒辦法自動暫停，會請你先停止它，只有那個應用不匯入。只會暫停你確認過的服務：確認之後才開始使用這份資料的服務不會被偷偷暫停，這個應用會先停下來（還沒有變更任何東西），請你再確認一次，其他應用照常匯入。
* **擴大帳號可用的編號範圍**：備份裡有檔案的擁有者編號超出這個應用的帳號目前可用的範圍時，會在確認後擴大它（這個帳號的所有服務會停止約 1 分鐘再自動啟動）。這件事要到轉換完才知道，所以會停在「再確認並匯入這個應用」。
* **資料庫服務裡的其他資料庫**：如果這個應用的資料庫服務裡還有其他資料庫，匯入前會先把整個資料庫服務存成完整複本，放在「還原前備份」裡（名稱開頭是「保留的複本」，不會自動刪除，可以下載或刪除）。匯入完成後，這些資料庫會自動放回去；放不回去的會列出名稱和原因，資料仍在完整複本裡。匯入失敗時，會用這份複本把整個資料庫服務原樣退回。資料庫服務沒有在執行時，無法確認裡面有沒有其他資料庫，也會先存完整複本；想省下這份複本，請先啟動資料庫服務再檢查。需要的空間約是資料庫服務大小的 2.2 倍，不夠時只有這個應用不匯入，其他不受影響。
* **慢一點的啟動**：資料量大時，資料庫和應用啟動會花比較久，匯入會等到它們真的起不來才退回，等待時間依資料量計算（最多 1 小時），作業紀錄會每分鐘寫一次「還在啟動」。
* **缺少的資料卷**：這個應用的資料卷不見時，會先建立一個空的再匯入。
* **讀不到的核對值**：匯入後如果應用沒有回報核對值，這一項會標示為「沒有比對資料」，其他核對（資料摘要、健康檢查）照常進行。

一般（不是從 HA 轉換的）備份還原維持原有的檢查，不受這些改變影響。

### Odoo 匯入：哪些會自動處理、哪些要你確認

和 HAOS 還原一樣，Odoo 不會因為「兩邊設定不一樣」就整個拒絕；做不到的，只有那一個資料庫（或 Odoo 本身）不匯入，並寫出原因，這台的 Odoo 不會有任何變更。

**這台會自動處理（結果頁寫「系統會自動做」，不用勾）**

- 這台 Odoo 用的映像、資料庫映像、讀 HA 資料用的 PostgreSQL 16 映像不在這台：自動下載，下載不到才停下並說明。
- 這台的 Odoo 資料庫停著：暫時啟動來讀，讀完恢復原狀。資料庫與帳號的名稱讀這台 Odoo 設定檔裡的設定。
- 這台 Odoo 的升級標記不存在或不是目前映像的：由程式寫上目前映像的標記（HA 的資料庫和這台的模組版本相同，不需要再升級）。
- 這台 Odoo 的資料庫帳號不存在、沒有可用的密碼，或是超級使用者：用這台設定檔裡的帳號和密碼建立或重設，並一律建成一般帳號（HA 來的內容不能以超級使用者權限執行）。設定檔裡也沒有密碼時才會停下。
- 應用設定裡這台自己多出來的資料卷、資料夾：照這台現在的內容原樣帶過去，不會被 HA 的資料取代。
- 時區檔這類不是 Odoo 資料的掛載：略過，不會交給暫時用的容器。
- HA 的資料庫用了這台的 PostgreSQL 映像有、而且 PostgreSQL 自己認為安全（trusted）的擴充功能（例如 pgcrypto）：自動建立。用了 vector 而這台沒有對應的映像：自動下載。
- 資料庫名稱可以是任何文字（中文、空白、符號都可以）；資料量大時，等待時間和可處理的清單大小會自動放大。

**匯入前請確認（只勾一次；名單多一個名字就要再確認）**

- **缺的模組**：HA 的資料庫已安裝、但這台和備份裡都沒有的模組。資料都還在資料庫裡，但用到這些模組的畫面、排程和報表會出錯；匯入後這台之後更新 Odoo 時，套件的升級檢查（upgrade-gate.sh）會因此被擋下來（結束碼 4），要先補上這些模組。自訂模組放在 HA 的 share 資料夾時，做 HA 備份要把 share 一起勾進去。
- **缺套件的自訂模組**：需要這台沒有的 Python 套件，只有那個模組不搬（其他照搬）。
- **只有資料庫超級使用者才能建立的物件**（事件觸發、外部資料、自訂語言…）：這台不建立它們，只略過；如果其他資料要靠它們才放得進去，匯入會停下，這台沒有任何變更。
- **留在 HA 的其他資料庫**：這台的 Odoo 一次只放一個資料庫，所以只搬你選的那一個；其他的會留在 HA（HA 停用後就看不到了），以後再匯入另一個會取代這次的。結果頁和匯入紀錄會列出沒搬的資料庫名稱。
- **略過的項目**：備份裡的裝置檔、指到外面的連結、太大的設定檔等，只略過那一個，列出全部數量與前 20 個名稱。

**只是提醒（匯入後請留意）**：資料庫有尚未完成的模組安裝或升級（照 HA 的狀態搬過來，請到「應用程式」套用或取消）、自訂模組標示不可安裝、需要這台沒有的程式、含有別種處理器的程式、啟用中的寄信伺服器與排程、網站網域會改成這台的網址、網址沒有換成這台的、這台 PostgreSQL 調整過但新叢集不接受的設定（回到預設值，資料不受影響）。

**仍然會停下的情形（只有 Odoo 或那一個資料庫）**：不是 Odoo 的資料庫、模組清單或內容讀不出來、模組版本和這台不同、HA 的 PostgreSQL 比這台新、HA 的擴充功能這台沒有、HA 沒有任何資料庫、這台的 Odoo 資料沒有掛在 /var/lib/odoo 、應用設定缺少它的資料卷，或這台資料庫的超級使用者密碼直接寫在 Quadlet 的 Environment= 裡（請改用 podman secret 的 POSTGRES_PASSWORD_FILE，或環境檔 EnvironmentFile=）；環境檔裡 POSTGRES_USER、PGDATA 等設定的寫法如果有引號、跳脫字元或變數，也會停下並指出檔案和設定名稱。

### Nextcloud 匯入：哪些會自動處理、哪些要你確認

和 HAOS 還原一樣，Nextcloud 不會因為「兩邊設定不一樣」或「備份少了某樣東西」就整個拒絕；做不到的，只有 Nextcloud 不匯入、其他應用照常，並寫出原因，這台的 Nextcloud 不會有任何變更。

**這台會自動處理（結果頁寫「系統會自動做」，不用勾）**

- 這台的 Nextcloud、資料庫或 Redis 停著：暫時啟動來讀，讀完恢復原狀；啟動不了才停下並說明。
- 這台的 `config.php` 不是 Nextcloud 自己寫的樣子（含有函式或變數）：改由這台 Nextcloud 自己的 PHP 讀出設定值（只讀，不改檔案）。
- 這台的資料庫裡沒有 `config.php` 寫的資料庫帳號，或它沒有可用的密碼：用 `config.php` 裡的帳號與密碼在新的資料庫建立（密碼不會出現在任何指令或紀錄）；`config.php` 裡也沒有可用的密碼時才會停下。
- 這台 Nextcloud 用的資料庫帳號是超級使用者：放入 HA 的資料時改用權限低的暫時帳號，放完再把資料交回原帳號（HA 來的內容不能以超級使用者權限執行）；匯入後帳號仍和這台原本一樣。
- HA 的資料庫用了這台的資料庫映像也有的擴充功能：自動啟用後再放資料；這台的映像沒有時才停下，並寫出名稱。
- 使用者檔案裡有硬連結指到沒有搬的檔案（更新程式暫存、Office 暫存）：改成複製檔案內容。
- HA 的 Nextcloud 版本讀不到：改用附加元件版本推算；HA 備份時在維護模式但兩邊版本相同：照常匯入，匯入後這台不在維護模式（版本不同才停下，因為可能升級到一半）。
- HA 的 PostgreSQL 比這台的新：不事先擋，直接試著放進去；放不進去才停下，並說明請先把這台的資料庫更新到同一版，不會只放一半。

**要你在「匯入前請確認」勾一次的**

- HA 備份沒有包含 share 資料夾、share 裡找不到使用者檔案資料夾（或缺少 `.ncdata` 標記，可能當時沒有掛上）、或使用者檔案放在備份不會包含的位置（網路磁碟、其他路徑）：帳號、設定、行事曆、聯絡人與分享照常搬，**使用者檔案不會搬**，Nextcloud 的檔案列表看得到名稱但打不開；這台原本的使用者檔案會先存進匯入前備份。匯入後請把檔案複製到這台的使用者檔案資料夾，再執行 `podman exec -u www-data nextcloud-app php occ files:scan --all`。
- 使用者檔案裡的符號連結（捷徑）和網站設定檔 `.htaccess`：不會搬（連結可能指到這台資料夾外；這台的使用者檔案在網站資料夾裡，`.htaccess` 可能讓檔案被公開），其他檔案照常搬，名單會列出來；匯入後請執行一次檔案掃描。
- HA 開了伺服器端加密：金鑰和檔案會一起搬，但這種備份還沒有實測過；匯入後如果檔案打不開，請用匯入前自動做的備份退回。
- HA 的資料庫有 Nextcloud 不會建立的函式或觸發程序（例如相簿應用 Memories 建立的）：這些程式不會搬，資料表和資料照搬，名單會列出來；用到它們的應用匯入後部分功能可能要重新設定。其他種類的資料庫物件（自訂型別、檢視表、規則…）目前仍然不能匯入。
- HA 的資料庫除了 Nextcloud 用的 `public` 之外還有其他 schema：只搬 `public`，其他不會搬，Nextcloud 本身不受影響。

**匯入後請留意（提醒，不用勾）**：讀不到這台的 Office 設定時，匯入後 Office 設定會是 HA 的，需要重新設定；這台 PostgreSQL 自己的設定放不進新資料庫時改用預設值，資料沒有影響。

### 錯誤與提示

- **金鑰不正確或沒有輸入**：回到「金鑰」步驟，顯示備份元件的說明（「HA 備份金鑰不正確，請確認後再試一次。」或「這份 HA 備份已加密，請輸入 HA 備份金鑰。」）。
- **這台還沒有加密金鑰**（「預設加密備份」開著）：選擇應用與結果的步驟都會提示，「下一步：轉換…」不能按；到「加密金鑰」設定好後，回到 HA 備份重新開始匯入。
- **已有作業正在進行**：一次只能有一個作業；頁面會連到進行中的作業，等它完成後再試。
- **空間不足**：顯示需要與可用的空間；刪除不需要的備份後再試。
- **Omnigent 的資料庫結構不同或正在改變**：HA 與這台的資料表或欄位不同時，檢查會寫出是哪些資料表，請先讓兩邊的 Omnigent 版本一致；轉換時這台的資料庫結構剛好在改變（例如 Omnigent 正在升級或重新啟動）時，轉換會停止並寫「這台 Omnigent 的資料庫結構在轉換期間改變了…」，這台沒有任何變更，等它正常執行後再轉換一次。
- **Omnigent 的 HA 備份內容前後不一致**：轉換時，HA 的資料會先放進一個用這台 Omnigent 資料庫結構建立的新資料庫，再重新清點一次（帳號、工作階段、代理程式、排程與啟用中的排程、Runner 主機、上傳的檔案清單、公開分享、外部連線憑證，以及每個資料表的筆數）；和檢查時 HA 的資料庫回報的不同時（備份可能被竄改過），轉換會停止並寫「這份 HA 備份的 Omnigent 資料庫回報的內容和它實際的資料不一致…」與不一致的項目（只寫項目名稱與筆數，不寫內容），這台沒有任何變更。HA 資料庫匯出清單中的序號（SEQUENCE SET）項目含有序號值以外的內容時，轉換也會停止（「…無法安全地搬過來。」）。
- **HA 的 Omnigent 資料不符合這台的資料庫結構**：HA 的資料是放進這台 Omnigent 自己的資料庫結構裡；其中有這台的結構不接受的資料時（例如違反欄位的檢查條件、必填的欄位是空的、資料重複或參照的資料不存在，通常表示 HA 的資料庫曾被手動修改或已損壞），轉換會停止並寫「HA 的 Omnigent 資料不符合這台 Omnigent 的資料庫結構…」，訊息不會列出資料內容，這台沒有任何變更。
- **EMQX 的備份是在 EMQX 執行中製作的**：HA 的 EMQX 附加元件沒有「停止後再備份」的選項，執行中製作的備份可能只寫了一半的內建資料庫。資料能完整讀出時，檢查會通過，但會提醒這件事；讀不完整、EMQX 無法匯出或匯入時，檢查或轉換會停止，不會做出少了資料的備份，並說明：「…請先在 HA 停止 EMQX 附加元件，再重新製作備份後匯入（附加元件停止時製作的備份最可靠）。」照做後，上傳新的 HA 備份再匯入一次。
- **EMQX 檢查提醒保存 MQTT 密碼的方式不同**：「HA 的 EMQX 保存 MQTT 密碼的方式（…）和這台（…）不同，匯入後以 HA 的為準：這台現有的 MQTT 帳號（…）匯入後無法再用原本的密碼登入，要在匯入後重新設定…」。這是提醒，可以照常匯入；括號裡是這台內建資料庫的帳號名稱（最多列 10 個，其餘寫「等 N 個」）。到這台 EMQX 管理頁「存取控制 → 認證」的內建資料庫替這些帳號重設密碼或重新建立；由這台 bootstrap 帳號檔建立的帳號，刪除後重新啟動 EMQX 就會用原本的密碼建回。兩邊的方式相同時不會出現這個提醒。讀不到這台的帳號或雜湊方式時，檢查只提醒「讀不出這台 EMQX 的 MQTT 帳號和密碼保存方式，沒辦法事先列出匯入後會失效的帳號（功能不受影響）；匯入後這台原本的 MQTT 帳號可能要重設密碼：到這台 EMQX 管理頁「存取控制 → 認證」的內建資料庫替這些帳號重設密碼或重新建立；由這台 bootstrap 帳號檔建立的帳號，刪除後重新啟動 EMQX 就會用原本的密碼建回。」，不會停止。HA 的 EMQX 沒有啟用內建資料庫認證、而這台有 MQTT 帳號時，提醒改成「HA 的 EMQX 沒有啟用內建資料庫的帳號密碼認證，匯入後以 HA 的為準：這台的 MQTT 帳號（…）匯入後無法再用帳號密碼登入。要繼續使用這些帳號，請先在 HA 的 EMQX 管理頁「存取控制 → 認證」啟用內建資料庫認證，再重新製作 HA 備份。」。
- **EMQX 檢查提醒 HA 用「plain」（不加密）保存 MQTT 密碼，或有以明文保存的密碼**（2026-11-25 起不再擋，和 HAOS 還原一樣照 HA 匯入）：「HA 的 EMQX 用「plain」（不加密）的方式保存 MQTT 帳號的密碼；會照 HA 原樣匯入，明文密碼會留在這台的資料卷、轉換出的備份和之後每一份備份裡，這台之後新增的 MQTT 帳號也會用明文保存。裝置照常登入。若要避免，請先在 HA 的 EMQX 管理頁「存取控制 → 認證」把密碼雜湊方式改成 plain 以外的方式並重設密碼，再重新備份。」；監聽器或閘道的內建資料庫用 plain 時：「HA 的 EMQX 在 MQTT 監聽器或閘道（gateway）的內建資料庫認證用「plain」（不加密）的方式保存 MQTT 帳號的密碼；會照 HA 原樣匯入，這些帳號的明文密碼會留在這台的資料卷和之後每一份備份裡（監聽器的認證設定不會搬，那些帳號在這台沒人用）。」；沒有以所屬認證目前的雜湊方式保存的帳號：「HA 的 EMQX 內建資料庫裡有 … 個 MQTT 帳號的密碼沒有以所屬認證目前的雜湊方式保存，可能是明文（例如在改用其他雜湊方式之前用「plain」設定，或以「hash」方式匯入帳號時填入了沒有雜湊的密碼；括號裡是不屬於全域認證的帳號所在的監聽器或閘道）；這些帳號在 HA 現在也無法用密碼登入，會照 HA 原樣匯入。真的是明文時，明文密碼會留在這台的資料卷和之後每一份備份裡。可以略過它們：在 HA 重設這些帳號的密碼或刪除不用的帳號，再重新備份。」（列出帳號名稱，最多 20 個）。讀不出 HA 的保存方式時只提醒「讀不出 HA 的 EMQX 的 MQTT 密碼保存方式，無法事先知道有沒有明文密碼；照 HA 原樣匯入，真有明文密碼時它會留在這台和之後每一份備份裡。」。
- **EMQX 匯入前請確認的項目**：每一項都列出名稱，勾一次「我了解」就好；沒有確認的轉換只會停下這個應用（「匯入前還有事情要確認」），其他應用照常。「HA 的 EMQX 設定有 N 處用「file://」讀取本機檔案當作密碼（…）」、「HA 的 EMQX 規則有 N 條使用 jq 函式（…）」、「HA 的 EMQX 設定有外部帳號驗證／啟用的 ExHook 伺服器（…）」、「HA 的 EMQX 授權設定有外部來源（…）」：它們會照 HA 原樣啟用，動過手腳的備份可能把這台的 MQTT 帳號檔、管理頁密碼或環境變數送到 HA 設定的伺服器，請只匯入你信任的備份。「HA 的 EMQX 沒有啟用帳號驗證，會照 HA 原樣匯入：匯入後，連得到這台 MQTT 的人不用帳號就能連線和收發訊息…」。「HA 的 EMQX Dashboard 仍用預設帳號密碼（admin／public）…這台的 Dashboard 目前開在區網或有對外通道…」（只在管理頁連得到時才要確認，否則是提醒）。「EMQX 匯入 HA 的資料時，有部分設定無法匯入（…）」。
- **EMQX 檢查只是提醒的項目**：「HA 的權限（ACL）檔取代了這台的（…）」（這台原本的檔案不會寫回，匯入前的自動備份裡還有）、「這台 EMQX 設有 N 個控制帳號驗證或授權的環境變數（…）會在下一次啟動蓋過 HA 的設定」、「這台 EMQX 執行中的設定和它的設定檔不同（…）」、「這台 EMQX 的設定提到的檔案不在資料卷裡（…）」、「這台預先建立的 MQTT 帳號（…）可能要在匯入後重新建立或重設密碼」、「暫用的 EMQX 的系統訊息沒辦法暫停，保留訊息的筆數可能差幾筆」、「讀不到這台 EMQX 內建資料庫的核對值，這次略過還原後的帳號與 ACL 規則核對」。
- **這台的 EMQX 停著**：檢查與轉換會自動把它啟動來讀取設定，讀完恢復原狀（停止）；啟動不了才會停下這個應用，說明原因。**映像不在這台**時會自動下載（自動下載不了才停下）。
- **EMQX 檢查說 HA 的備份沒有 EMQX 的內建資料庫**：EMQX 從沒啟動過，沒有東西可搬；只有 EMQX 不會匯入，這台的 EMQX 不會變，其他應用照常。請先在 HA 啟動一次 EMQX 附加元件再重新備份。
- **EMQX 無法讀取 HA 的帳號驗證或授權設定**、**EMQX 匯入後，HA 的帳號驗證或授權設定（…）沒有出現在暫用的 EMQX 裡**：匯入已停止，這台沒有任何改變。「HA 沒有開帳號驗證」是 HA 自己的設定，會照 HA 匯入並在匯入前請您確認；但讀不出 HA 的設定，或匯入沒有把 HA 的帳號驗證或授權來源帶進暫用的 EMQX 時，不會把這台的設定換成不完整的清單（那可能讓所有人都連不上或都連得上）。請在 HA 先停止 EMQX 附加元件，重新備份後再匯入；仍然一樣請把這份備份交給支援人員檢查。
- **EMQX 匯入後，帳號驗證或授權沒有成為 HA 的設定**、**EMQX 匯入後未能保留目標有效設定（…）**、**EMQX 候選啟動後的節點名稱和這台不同**：轉換已停止，什麼都沒有改變；請先在「應用軟體」重新啟動 EMQX 再重新檢查與轉換；仍然出現時請聯絡我們。
- **還原後 EMQX 核對不一致**：MQTT 帳號、ACL 規則或金鑰和轉換時核對的不同時，還原會停止並自動回復到還原前的狀態，訊息寫出不同的項目，例如「EMQX 還原後的內建資料庫（emqx_acl）和轉換時核對的不同，已停止；…」。只有設定不同（例如轉換之後這台改過設定、CPU 數不同）時只在作業紀錄提醒，不回復。
- **EMQX 匯出的資料含有不屬於這次匯入的內容（…）、或在匯入前無法檢查**：轉換先用 HA 的資料開一個暫用的 EMQX 匯出帳號、規則等資料，再匯入另一個用這台設定開的暫用 EMQX；匯入前會核對匯出檔裡只有這次要搬的設定與資料表（括號裡是多出來的檔案或設定項目的名稱）。不符合或讀不出來時在匯入前就停止，這台什麼都沒有改變。請在 HA 停止 EMQX 附加元件後重新備份再匯入；仍然出現時請聯絡我們。
- **EMQX 匯入後未能保留目標有效設定（…）**：暫用的 EMQX 匯入 HA 的資料後，會把這台 EMQX 自己的設定（授權來源、監聽埠、節點與叢集等）放回去並逐項核對（核對時把 EMQX 自動補上的預設值也算進去）；括號裡是不同的設定項目，轉換已停止，什麼都沒有改變。請先在「應用軟體」重新啟動 EMQX 再重新檢查與轉換；仍然出現時請聯絡我們。
- **檢查或轉換比較久**：Hermes 的資料可能有好幾 GB，EMQX 與 Headscale 的附加元件裡還有 HA 自己建立的映像檔（每個約 100–500 MB，會解開後略過），所以比 Odoo、n8n 久；進度會寫出正在處理哪個應用。
- **系統缺少 python3-nacl 或 python3-cryptography**：2026 年 3 月以後的 HA 加密備份需要 python3-nacl，較舊的 HA 加密備份需要 python3-cryptography。安裝或更新 Cockpit 時會自動補裝，所以正常不會看到這句；看到時請管理者重新執行安裝（`sudo python3 scripts/manage.py install`），缺的套件會自動補裝。這台連不到套件庫時，更新仍然照常完成，安裝訊息會說明沒補到哪些套件、原因與怎麼辦；補到之前這些備份讀不了（`sudo python3 scripts/manage.py status` 可以查看，讓這台連上網路或自行安裝這些套件後，再執行一次安裝即可）。
- **備份元件太舊**：上傳 HA 備份檔時會被拒絕為「這不是 woowtech 備份檔」，頁面另外提示「如果這是 Home Assistant 的備份檔…請先更新備份元件」；匯入相關的按鈕則顯示「這台設備的備份元件版本還不能匯入 Home Assistant 的備份」。請把備份元件更新到與頁面相同的版本。
- **讀不出來的資料**：壓縮檔或加密內容壞掉、被截斷、被改過的附加元件不會匯入；請在 HA 重新備份後再上傳。這台的應用不會變更。
- **略過的項目**：單一檔案搬不了時只略過那一個並列在「匯入前請確認」：檔名空白、太長或含控制字元的項目、裝置檔、FIFO、佔用 HA 機密檔位置的連結或資料夾、指到資料以外的符號連結、找不到內容的硬連結、大小超出上限的設定檔。硬連結（同一個檔案的另一個名字）會連同內容一起搬。
- **上傳一半的檔案**：同時最多 4 個還沒完成的上傳；再開始新的上傳時，會先清掉閒置超過一小時的最舊一個，正在上傳或正在確認的不會被清掉。
- **「這台設備還沒有回應，作業可能已經開始。請再按一次剛才的按鈕…」**：開始檢查、轉換或匯入後兩分鐘都沒有回應。頁面已經用同一個要求再確認過；請再按一次同一個按鈕（只會接上同一個作業），或到「活動紀錄」確認。
- **「找不到指定的作業。看不到進度不代表作業停了…」**：作業紀錄暫時讀不到，只是看不到進度，作業本身可能還在執行。請按「重試」重新讀取，或到「活動紀錄」確認。
- **HA 備份金鑰含有 Tab 或換行等看不見的字元**：頁面照原樣試試看，不會先擋下；金鑰不對時，錯誤說明會多寫一句提醒這件事（複製時常會多出來），請刪掉多餘的字元後再試。只有空白、太長或含空字元的金鑰會在頁面直接擋下。
- **轉換已完成，但作業沒有回報新的備份編號**：轉換好的備份其實已經在「備份列表」（標示「由 HA 轉換」），請到那裡找它再還原；這只是提示，不是錯誤。

### 備份元件比頁面舊時

頁面比設備上的備份元件新（備份元件還不能一次匯入）時，檢查結果沒有新格式，頁面改用舊的兩個步驟（先轉換、再到還原步驟確認），不會把新的欄位送給舊的元件；這種情形下一個應用沒有通過檢查也不再擋住其他應用（只轉換有通過的，沒通過的列出原因）。請把備份元件更新到和頁面相同的版本，就能用一次確認的流程。

## 應用設定：產生與安裝目錄項目

「應用設定」分頁幫管理者為新的應用建立目錄項目，不必從零手寫。詳細規則見 [app-catalog.md](backup/app-catalog.md) 的「用「應用設定」產生與安裝」。

1. **已安裝的應用設定**：列出這台設備目前的目錄項目，可「移除…」（先預覽，勾選確認後才移除；應用本身與它的備份都不會被變更，但在重新安裝設定之前無法備份或還原它）。
2. **掃描應用擁有者**：選擇帳號後按「掃描 Quadlet 服務定義」。系統以該帳號的身分讀取 `~/.config/containers/systemd/`，依相依關係、網路、資料卷與標籤把容器分組成應用，產生草稿。只會讀取，不會變更任何服務；不讀取環境變數檔，也不顯示 `Environment=` 的值。
3. **審查草稿**：每個草稿列出掃描到的容器、PostgreSQL 備份方式（預設冷備份，可切換為整個執行個體或單一資料庫；還沒安裝的 LiteLLM、n8n 與 Hermes 預設單一資料庫，這是它們從 Home Assistant 匯入唯一支援的方式）、「這份設定會備份什麼」，以及需要注意的地方：沒有列入的敏感或禁止路徑（例如 `~/.ssh`、桌面）、權限超過 0644 的設定檔、直接寫在 `Environment=` 的機密、猜測的資料庫名稱等。草稿也會加入內建資料核對。
4. **編輯與預覽**：可以直接編輯 JSON；格式錯誤會立即標出行數，停止輸入後以這台設備的規則檢查，並顯示與目前安裝的設定之間的差異、對既有備份的影響（例如新增資料卷後，舊備份在新設定下無法還原），以及這個應用已有幾份備份。
5. **安裝**：檢查通過後按「安裝應用設定…」（取代既有設定時為「取代已安裝的設定…」），在對話框勾選「我已審查上面的內容、差異與影響」。設定檔以 root 擁有、權限 0644 寫入；被取代的舊設定保留在 `/etc/woowtech-cockpit/backup/apps-history/`（每個應用最近 10 份）。安裝與移除都記錄在系統日誌，作業進行中時不能安裝或移除。
6. **ID 與擁有者**：草稿的 ID 已被另一個帳號的應用設定使用時，草稿標為無法安裝，請先把 `id` 改成其他名稱；已安裝的應用設定也不能直接改成另一個帳號（它的備份會被還原到新的帳號，並計入那個帳號的保留份數），確實要搬移時請先移除再以新帳號安裝。還原時若備份來自另一個帳號，相容性檢查會提醒。
7. **健康檢查網址**：草稿只沿用 `HealthCmd=` 網址的路徑；EMQX 入口的 `/readyz` 只回應容器內部（從設備連線會得到 403），管理頁 `/` 是網頁（備份元件的檢查會得到 406），用這兩個網址還原都會被判定失敗，草稿改用 broker 自己的公開 API `/api/v5/error_codes`，已安裝的設定會在草稿中提示並改用；網址中 `?` 之後的查詢參數（可能含有存取權杖）不會寫進設定，因為應用設定檔所有帳號都能讀取，需要時請自行加入。設定檔路徑不可位於 `~/.config/fish/`、`~/.config/git/` 等殼層或 git 的設定目錄。

安裝只寫入目錄項目，不會建立全新部署用的範本（`quadlet.template_dir`）；沒有範本的應用只能原位還原。草稿是起點，正式應用仍需依 [app-catalog.md](backup/app-catalog.md) 的審查清單審查並在實驗室演練。備份元件較舊、不提供這些指令時，分頁會說明「這台設備尚不支援應用設定掃描」。

## 清理備份與保留原則

「總覽」的「各應用的備份空間」與「備份列表」都有「清理備份」入口：

- **各應用的備份空間**：每個應用的備份份數（手動、排程、還原前、上傳）、佔用空間、最新備份時間與目前的保留原則。
- **保留原則**：預設與每個應用可以設定「全部保留」或「保留最新幾份」（1–1000），只計算與刪除**手動**備份（排程備份不算在內，它們依「排程備份」自己的保留份數清理，頁面也會寫出目前保留幾份）；一份備份含多個應用時，要超出每個應用的保留份數才會刪除。「驗證」未通過的備份無法還原，不計入保留份數，本身也會列為可刪除（原因「驗證未通過」），所以保留的是最新幾份沒有驗證失敗的備份。還原前自動備份維持原規則（每個應用最新 3 份），上傳的備份只會在你勾選時刪除。
- **預覽清理**：變更原則後先按「預覽清理」，列出會刪除的備份與原因（例如「示範筆記應用」第 7 新，保留最新 5 份）與可釋放的空間；可以取消勾選，也可以在「其他備份」另外勾選要刪除的備份（例如舊的上傳）。
- **受保護的備份**：正被作業使用的備份、還原作業進行中時的還原前備份，以及失敗或中斷的還原仍需要的還原前備份與它的來源備份（沒有還原前備份、但已經變更了應用的失敗還原，也保護它的來源備份），一律不會被刪除，頁面列出原因。有作業紀錄無法讀取時，全部備份暫時受保護（那份紀錄可能就是需要保護的還原）。
- **確認**：按「刪除 N 份備份…」（或只變更原則時「儲存保留原則…」），在對話框勾選「我了解這些備份刪除後無法復原」。刪除時若有備份剛好變成受保護，系統會略過並說明原因。儲存的原則之後在每次手動備份成功時自動套用，結果頁會列出依原則刪除的備份。每一筆刪除與原則變更都記錄在系統日誌。

原則保存在 `/etc/woowtech-cockpit/backup/retention.json`（root 擁有）；檔案不存在時全部保留，檔案損毀或權限不安全時頁面會提示，並且不會自動刪除任何備份。

## 加密金鑰與緊急金鑰

### 設備金鑰

每台設備有一把備份金鑰（age X25519），在這台設備建立的備份都用它加密。在「加密金鑰」按「建立加密金鑰」建立；金鑰保存在 `/etc/woowtech-cockpit/backup/keys/`，只有 root 可讀取。金鑰以 `XXXX-XXXX-XXXX-XXXX` 格式的金鑰 ID 識別，備份詳情會顯示該備份是用哪一把金鑰加密。

### 緊急金鑰

建立金鑰後，頁面顯示金鑰 ID 與完整金鑰，並提供「下載緊急金鑰」與「複製金鑰」。緊急金鑰檔名為 `woowtech-backup-key-<主機名稱>-<金鑰 ID>.txt`，內含金鑰 ID、建立時間、建立設備、以 `AGE-SECRET-KEY-1` 開頭的金鑰，以及在其他設備還原的步驟。這些步驟提醒：目標設備的「備份與還原」要是 2026.11.15.2 或更新版本，並先在「加密金鑰」建立這台設備自己的金鑰；備份不含映像時要先安裝各應用的套件；預檢時可以審查並安裝備份附上的應用設定。2026.11.15.1 之前下載的緊急金鑰檔，步驟裡寫的是舊格式的 `.woowbackup`，2026.11.15.2 之前下載的寫的是「先在應用設定建立設定」；金鑰本身相同，仍可用來還原 `.tar` 備份。

保存後勾選「我已將緊急金鑰保存到這台設備以外的安全位置」，再按「完成」。確認之前，頁面會持續提醒；離開「加密金鑰」頁時，頁面上的金鑰內容會被移除，需要時再按「顯示並下載緊急金鑰」。

確認後頁面不再顯示金鑰內容。需要另一份時，在「加密金鑰」按「重新下載緊急金鑰…」：頁面先以對話框說明這個檔案可以解開這台設備的所有備份，以及保管方式，按對話框中的「下載緊急金鑰」才下載。下載的檔案同樣含有完整金鑰；檔案在瀏覽器中產生，金鑰不會顯示在頁面上。

**遺失緊急金鑰的後果：** 這台設備故障或重新安裝時，設備上的金鑰會一起消失。沒有緊急金鑰，用它加密的備份將**永遠無法還原**，任何人（包括 woowtech）都無法找回或重設。

請保存在密碼管理器、加密隨身碟，或列印後上鎖保管。不要用電子郵件、聊天訊息或公開雲端分享傳送，也不要和備份檔放在同一處：同時取得金鑰與備份檔的人，可以讀取備份中的資料庫、檔案與應用機密。

### 匯入其他設備的金鑰

這台設備需要經常還原另一台設備的備份時，可在「加密金鑰」的「匯入其他設備的金鑰」貼上金鑰或讀取緊急金鑰檔，或在還原時勾選「保存此金鑰到這台設備」。匯入的金鑰只用於解密，不會用來加密這台設備的新備份。

目前不提供更換（輪替）設備金鑰，也不能從頁面移除已匯入的金鑰。

## 作業與進度

備份、還原與驗證都以背景作業執行（systemd 暫時單元 `woowtech-backup-<作業 ID>.service`）。關閉瀏覽器或連線中斷都不影響作業；重新開啟頁面會回到進行中的作業。「活動紀錄」列出最近 50 筆作業，每筆可查看階段、進度與最近 200 行紀錄；紀錄不含金鑰與應用機密內容。排程備份沒有執行的那幾次，也以「未執行」列在作業之間（見「排程備份」）。設備保留最近 200 筆已結束作業的紀錄與日誌，更舊的自動刪除（仍需處理的紀錄另外保留，見 [operations.md](operations.md)）。

**同一時間只能有一個作業。** 已有作業進行中時，新的要求會被拒絕（`busy`），頁面會連到進行中的作業。重複送出同一個要求（例如逾時後再按一次）會回到同一個作業，不會重複執行。

### 階段

| 作業 | 階段 |
| --- | --- |
| 備份 | 準備 → 檢查空間與應用 → 暫停應用寫入 → 匯出資料庫 → 匯出資料卷與設定 → 恢復應用 → 加密封裝（未加密的備份為「封裝（未加密）」）→ 驗證備份 |
| 還原 | 準備 → 解密並驗證檔案 → 相容性檢查 → 預先寫入主機資料夾 → 保存還原前資料 → 停止應用 → 還原資料 → 啟動應用 → 健康與資料核對 → 封裝還原前備份；失敗時加上「自動回復」（其中也會封裝還原前備份） |
| 驗證 | 準備 → 解密並驗證檔案（逐項檢查內容）→ 核對結果 |
| 建立未加密副本 | 準備 → 解密並驗證檔案 → 封裝未加密副本 → 驗證副本 |

沒有主機資料夾時，「預先寫入主機資料夾」顯示「略過」；全新部署，或沒有建立新的還原前備份時，「保存還原前資料」與「封裝還原前備份」顯示「略過」；在停機期間封裝時，「封裝還原前備份」在「保存還原前資料」期間就顯示完成，之後的還原與自動回復步驟都維持完成；還原已完成但封裝失敗時，「封裝還原前備份」顯示「失敗」，之後系統補做成功時改為完成。資料摘要在「匯出資料庫」「匯出資料卷與設定」期間計算，還原時在「還原資料」（檔案）與「啟動應用」（資料庫，其他服務啟動前）期間比對。「活動紀錄」中「建立未加密副本」的作業類型顯示為「未加密副本」。

### 狀態

| 狀態 | 意思 |
| --- | --- |
| 等待開始 | 已排入，尚未開始 |
| 執行中 | 正在執行 |
| 已完成 | 成功。還原時代表健康檢查通過，且資料核對一致或沒有可比對的快照 |
| 失敗 | 沒有完成。備份失敗不會留下備份檔；還原若在變更資料前失敗，應用未被變更。顯示「需人工處理」時，代表自動回復也沒有完成 |
| 已自動回復 | 還原在開始變更後失敗，系統已用還原前備份（全新部署則移除新建立的項目）回到還原前的狀態；錯誤訊息說明失敗原因 |
| 已中斷 | 作業程序意外結束（例如被強制終止、斷電、重新開機），見下方 |
| 已取消 | 依要求在安全的檢查點停止：備份不會列出、寫入服務已恢復；還原在變更任何資料前就停止 |

### 取消

只能在不會留下不完整狀態的階段取消：

- **備份**：「暫停應用寫入」之前，以及「加密封裝」「驗證備份」期間（未完成的備份檔會被丟棄，服務在這之前已恢復）。從暫停寫入到恢復應用之間不能取消。
- **還原**：只能在「相容性檢查」結束之前取消（之後開始預先寫入主機資料夾與建立還原前備份）。
- **驗證**與**建立未加密副本**：隨時可以取消（設備上的資料不會改變）。

不能取消時頁面顯示「目前階段無法取消」（`not-cancellable`），作業會繼續到完成或自動回復。取消要求一旦被接受，作業一定在進入下一個不能取消的階段之前停止，不會接受取消之後又暫停寫入或開始變更資料。

### 已中斷的作業

作業程序被強制終止、斷電或系統重新開機時，作業無法自行收尾。之後開啟頁面（讀取狀態、作業或活動紀錄）時，系統會把它標為「已中斷」，並且：

- 清除它的暫存資料與暫時金鑰；
- 重新啟動備份時被暫停、還沒恢復的寫入服務；
- 清除沒有完成的全新部署（見下方）；
- 整理主機資料夾旁留下的 `<路徑>.woowbk-new-<作業 ID>` 與 `<路徑>.woowbk-old-<作業 ID>`：`<路徑>` 不見而原本的內容還在時把它移回，移除沒寫完的新內容，絕不刪除僅存的一份，結果寫在作業訊息中（實驗室 D4 以三種時間點的強制終止驗證）。請勿自行刪除或改名這些資料夾；
- **不會自動重做**任何作業。

系統關機或重新開機時，若還原已開始變更資料，作業不嘗試自動回復，而是自己結束為「已中斷」，保存的還原前資料留在原處；開機後第一次開啟頁面或執行作業時，系統會先把它封裝成還原前備份（大型應用約需一分鐘，頁面這段時間會等待），作業結果再寫出還原前備份 ID，之後依下方方式處理。作業被強制終止或斷電時也一樣。

還原期間被暫時停用的服務，在作業中斷後仍保持停用，開機後也不會自動啟動，避免應用在只還原一半的資料上執行（資料庫服務不受影響，可能仍在執行）。這時管理者會看到：

- **總覽**：應用狀態「異常」，說明「服務 … 已被暫時停用，表示先前的還原沒有完成；請使用還原前備份或同一份備份再次還原」。這個應用暫時不能建立備份。
- **作業結果**：「作業意外中斷」與「接下來怎麼做」；還原已開始變更資料、且有還原前備份時，提供「使用還原前備份還原」。
- **再次還原時的預檢**：以「注意」提示服務因先前的還原沒有完成而被暫時停用，這次還原完成後會恢復。

處理方式：

- **備份中斷**：到「總覽」確認應用已恢復執行，再重新建立備份。中斷的備份不會被列出。
- **原位還原中斷**：按「使用還原前備份還原」，把應用回到這次還原開始前的狀態。應用處於異常狀態時，系統通常無法再建立新的還原前備份；因為還原的是還原前自動備份，會直接還原（失敗時無法自動回復，見「無法建立還原前備份時」），完成後被停用的服務會恢復。不要手動解除停用（`unmask`）後啟動。若在建立還原前備份之前就中斷，應用資料應未被變更；確認應用狀態後再決定是否重新還原。
- **全新部署中斷**：系統判定中斷時會清除未完成的部署（Quadlet 檔、服務、資料卷、應用機密、設定檔與網路），結果訊息說明是否完整清除；清除完成後可再次還原同一份備份，未能完整清除時依訊息列出的項目人工處理。資料匯入已完成、服務已解除停用或正在執行的部署可能已有新資料，系統不會自動移除，訊息會要求人工確認。**映像名稱不會改回**：作業載入映像時移走的既有名稱（例如設備上舊版的 `localhost/<應用映像>:<標籤>`）之後仍指向備份中的映像；原本的映像只剩其他名稱，沒有其他名稱時會變成無名稱映像。只有作業自己執行的自動回復會把映像名稱改回。
- 不確定應用狀態時，先到「服務管理」檢查服務，或聯絡系統管理員。主機端的處理方式見 [operations.md](operations.md)。

實驗室已驗證（2026-11-13 最終回歸）：

- 在「還原資料」階段強制終止（SIGKILL）原位還原：作業「已中斷」並列出還原前備份 ID；用它還原（12.7 秒，系統沒有再建立新的還原前備份）後，資料與中斷前完全相同。
- 還原進入「啟動應用」階段時重新啟動設備：開機後作業為「已中斷」並列出還原前備份 ID，應用服務沒有啟動、總覽顯示「異常」；用還原前備份還原（約 15 秒）後，資料與還原前完全相同。
- 全新部署在「啟動應用」階段被強制終止：復原移除整個部署，同一帳號的其他資料卷、應用機密、設定檔、網路與映像名稱都沒有變；之後再做全新部署成功。
- 備份在暫停寫入、匯出資料庫、匯出資料卷、加密封裝與驗證備份各階段被強制終止：作業「已中斷」；在寫入服務暫停期間被終止時，由復原流程重新啟動它們；暫存清除，沒有留下未列出的備份檔，下一次備份成功。

## 錯誤代碼

頁面顯示中文訊息；代碼供回報問題時使用。

| 代碼 | 意思與常見原因 | 處理方式 |
| --- | --- | --- |
| `invalid-request` | 輸入或請求不正確，例如金鑰不是以 `AGE-SECRET-KEY-1` 開頭的完整一行、建立不加密的備份或關閉預設加密時沒有確認風險、還原上傳的未加密備份時沒有確認信任來源、應用設定沒有通過檢查或在預覽之後被改過（請重新預覽）、備註含換行、上傳檔案大小與宣告不符（上傳未完成）、這台設備已有同 ID 但內容不同的備份；應用目錄項目格式錯誤也使用此代碼 | 依訊息修正後重試；金鑰請完整複製一行；上傳不完整請重新上傳；目錄項目錯誤請交給應用套件維護者（見 [app-catalog.md](backup/app-catalog.md)） |
| `not-found` | 找不到備份、作業或上傳工作（可能已刪除，或未完成的上傳超過 24 小時已被清除）；或找不到應用的設定檔 | 重新整理列表；重新上傳；確認應用部署完整 |
| `busy` | 已有作業進行中（作業進行中也不能安裝或移除應用設定、清理備份）；已有 4 個尚未完成的上傳；要刪除的備份正被作業使用，或在還原作業進行中刪除還原前備份 | 等進行中的作業或上傳完成後再試，頁面會連到進行中的作業 |
| `key-required` | 這台設備沒有加密這份備份的金鑰 | 輸入建立備份那台設備的緊急金鑰，或先匯入金鑰 |
| `wrong-key` | 提供的金鑰不是加密這份備份的那一把，或金鑰無效 | 核對備份顯示的金鑰 ID 與緊急金鑰檔上的金鑰 ID 是否相同 |
| `no-device-key` | 這台設備尚未建立備份金鑰；建立加密的備份，以及「預設加密備份」開啟時的原位還原（建立加密的還原前備份）都需要它 | 到「加密金鑰」建立金鑰並保存緊急金鑰 |
| `not-a-backup` | 檔案不是 woowtech 備份檔 | 確認選擇的是下載的 `.tar`（或舊格式 `.woowbackup`）檔，且下載完整 |
| `unsupported-format` | 備份檔格式版本較新，或加密、壓縮方式不受支援 | 將這台設備的備份元件更新到不舊於建立備份的版本 |
| `corrupt-archive` | 檔案損毀或遭修改，例如被截斷、位元錯誤、內容與清單不符 | 不要用它還原；改用另一份備份，或從原設備重新下載 |
| `invalid-manifest` | 備份的內容清單格式不正確 | 同上；若確定來源可信，保留檔案並回報 |
| `limit-exceeded` | 超出安全限制：超過 40,000 個項目、內容清單超過 16 MiB、總量超過 16 TiB、資料卷超過 4,000,000 個項目（映像 100,000 個）；設定檔、部署範本、目錄項目過大；或指令輸出超過上限 | 本版本無法處理此檔案或設定；設定過大時請應用套件維護者調整 |
| `insufficient-space` | 空間不足：建立備份（預估量 2.2 倍加 512 MiB）、上傳（檔案大小加 512 MiB）、解開備份（內容大小加 512 MiB）、封裝時、匯出時保留空間不足，或還原前備份在應用恢復後與停機期間都放不下封裝（原位還原在停止服務前就拒絕，不做任何變更）；保存還原前資料後可用空間少於 512 MiB（在任何變更前拒絕）；原位還原主機資料夾時放不下新舊兩份內容 | 刪除不需要的備份（需要的先下載）或擴充磁碟後再試；備份會在暫停服務前就停止 |
| `incompatible` | 相容性檢查未通過：缺少映像、PostgreSQL 主版本較高或早於 10、整個執行個體方式的映像缺少擴充功能或備份的方式與這台設備的目錄不同、映像架構不同、Quadlet 檔不完整、全新部署時已有同名資料卷／應用機密／設定檔、原位還原時資料庫執行個體有未宣告的資料庫或無法列出、備份中的資料卷、主機資料夾或映像封存含有不安全或不支援的內容、主機資料夾的檔案擁有者超出這台設備應用擁有者的 UID／GID 對應範圍、全新部署時主機資料夾已存在且不是空的、備份缺少這台設備設定需要的項目、缺少部署範本、備份由較新版本的轉接器建立；自動回復需要的映像版本已不在設備上 | 依預檢逐項處理後按「重新檢查」；相容性檢查未通過時，沒有任何變更。資料卷或映像封存被拒絕的備份不要再用 |
| `app-not-in-catalog` | 這台設備沒有該應用的目錄項目 | 先安裝經審查的目錄項目；正式應用目前尚未提供 |
| `owner-missing` | 應用擁有者帳號不存在、家目錄設定不正確，或無法以該帳號執行命令 | 建立與目錄項目同名的帳號（UID 可不同），設定 rootless Podman 與 linger |
| `not-deployed` | 應用尚未部署在這台設備（無法備份），或找不到目錄列出的資料卷 | 確認應用已部署並啟動，資料卷名稱與目錄項目一致 |
| `permission-denied` | 沒有管理員權限；或目錄項目、部署範本與其資料夾的擁有者或權限不安全（不是 root 擁有、可被其他帳號寫入、符號連結）；或擁有者家目錄中的路徑含符號連結 | 在 Cockpit 開啟管理員存取權限；檔案權限由 root 修正（root 擁有，檔案 0644、資料夾 0755） |
| `not-cancellable` | 作業已進入不能中斷的階段 | 等作業結束；還原失敗時會自動回復 |
| `job-failed` | 作業步驟失敗：服務無法停止或啟動、資料庫匯出或匯入失敗、資料摘要與備份時不一致（應用不會啟動，作業自動回復）、資料卷含有還原時無法匯入的內容、健康檢查未通過、資料核對不一致、無法建立還原前備份等；「已中斷」的作業也記錄此代碼 | 查看結果訊息與作業紀錄最後幾行；到「服務管理」檢查服務；出現「需人工處理」時，用列出的還原前備份再次還原 |
| `internal-error` | 未預期的錯誤，例如備份元件安裝不完整或權限不安全、缺少 age、age-keygen 或 zstd（用 `manage.py status` 查看，重新執行 `install` 會自動補裝）、無法啟動背景作業 | 用 `manage.py verify` 檢查、`install` 修復，確認 age 與 zstd 已安裝；查看系統日誌（見 [operations.md](operations.md)） |

頁面另有幾種非代碼狀態：「找不到備份管理程式」表示這台主機未安裝或未完整安裝備份元件；「管理連線已中斷」時按「重新連線」，已送出的背景作業會繼續、不會重送；「操作回應逾時」時先重新整理確認狀態，再決定是否重試。

## 備份檔的內部檢查（資料卷、主機資料夾與映像封存）

備份中的資料卷與映像各是一個 tar 檔。Podman 匯入 tar 時會跟隨封存內先放入的符號連結：實驗室在設備上的 Podman 4.9.3 實測，直接執行 `podman volume import` 或 `podman load`，都會經由植入的絕對路徑符號連結，把檔案寫進應用擁有者家目錄中的其他位置。所以這兩種 tar 一律先完整檢查，再由引擎依檢查過的項目重新產生乾淨的 tar 交給 Podman，Podman 從不讀取備份檔裡原本的位元組。主機資料夾的 tar 也以資料卷相同的規則檢查並重新產生，再以應用擁有者身分解到新的資料夾（實驗室 D5 以多種惡意資料夾 tar 驗證：都在任何變更之前被拒絕）。

- **資料卷**：只接受一般檔案、目錄、FIFO、符號連結，以及指向前面非目錄項目的硬連結；拒絕絕對路徑或含 `..` 的名稱、重複項目、位於符號連結或其他非目錄項目之下的項目、從連結所在目錄解析後會離開資料卷的符號連結、裝置檔與其他類型、超過 4,000,000 個項目（映像 100,000 個），以及應用擁有者的使用者命名空間對應不到的擁有者（UID／GID；匯入 HA 備份時，這個範圍會在你確認後自動擴大）。
- **重新產生時不保留的內容**：非目錄檔案的 setuid／setgid 位元，以及 `user.*` 以外的延伸屬性（例如 file capabilities）。還原結果的「注意事項」與作業紀錄會列出受影響的檔案數與例子。
- **映像**：必須正好是 `podman save` 產生的 OCI 封存，只含一個映像，其設定摘要等於備份記錄的映像 ID，名稱對應這台設備範本需要的映像。載入時映像名稱由這台設備決定，封存不能指定要移動哪個名稱。

檢查的時機：建立備份時檢查每個資料卷匯出（不合規就不建立備份）；「驗證」作業以相同的規則檢查每個資料卷、主機資料夾與映像封存（不檢查與這台設備有關的應用擁有者 ID 範圍與映像名稱）；還原作業在「相容性檢查」階段、建立還原前備份之前再完整檢查一次（含這台設備的 ID 範圍與需要的映像名稱），不合規就停止，設備沒有任何變更。「檢視內容」不做這項檢查。

實驗室已驗證（2026-11-14，格式 2）：把一份新備份的資料卷 tar 加上離開資料卷的符號連結、以設備公鑰重新封裝（所有大小與 SHA-256 都正確）後上傳，「驗證」作業以「備份檔已損毀」失敗並點名資料卷，索引記錄驗證未通過；還原在任何變更之前被拒絕，應用資料不變。

實驗室已驗證：在資料卷 tar 與映像封存的所有真實項目之後，各植入指向家目錄的符號連結與其下的項目，再以設備金鑰重新加密。還原作業在相容性檢查就拒絕，錯誤分別點名容器映像與資料卷；過程中沒有任何 Podman 映像或資料卷事件，沒有建立還原前備份，應用資料、部署檔與映像名稱都沒有變，整台設備找不到植入的檔案。

## 安全須知

- **只有管理員可以使用。** 頁面以 Cockpit 管理員權限呼叫 root helper；helper 在非 root 身分下拒絕執行。任何能在 Cockpit 取得管理員權限的帳號，都能檢視、下載、還原與刪除所有應用的備份；管理員之間沒有分權。
- **備份含有應用機密。** 資料庫、檔案、Podman secrets（例如資料庫密碼與應用金鑰）與設定檔都在備份中。下載的加密檔仍請像保管密碼一樣保管，並與緊急金鑰分開存放。**不加密的備份與「下載未加密版本」建立的副本以明文存放這些機密**，任何取得檔案的人都能讀取；只有管理員明確確認風險後才會建立，副本 15 分鐘後自動刪除，每次建立、下載與刪除（包括過期、被新副本取代）都記錄在系統日誌（`journalctl -t woowtech-cockpit-backup`）；下載未加密的備份與刪除任何備份也會記錄。設備重新開機後，自動刪除的計時器不會保留：已過期的副本在下次開啟備份頁面或執行任何作業時刪除。
- **本機加密不防 root。** 本機備份與設備金鑰在同一台設備上，具有 root 權限的人可以解密本機備份。加密主要保護下載到其他位置的檔案。
- **作業期間有明文暫存（殘留風險）。** 備份與還原過程中，資料庫匯出、資料卷內容與應用機密會以未加密形式暫存在 `/var/lib/woowtech-backup/staging/<作業 ID>/`（只有 root 可存取），作業結束或被判定中斷時刪除。刪除後的資料區塊可能留在磁碟上直到被覆寫，系統不做安全抹除；需要防範磁碟被取出讀取時，請使用整碟加密。
- **金鑰只經標準輸入傳遞。** 輸入的金鑰經 Cockpit 加密連線送到 helper 的標準輸入，不會出現在網址、命令列參數、作業紀錄或日誌。只供單次作業使用的暫時金鑰檔放在 `/run/woowtech-backup/`（記憶體檔案系統，0600），作業結束即刪除。最終回歸以兩台設備的作業紀錄、日誌、索引與 journal，以及主機上 1144 個測試證據檔，比對應用機密、設備金鑰與 age 金鑰格式，沒有任何命中。
- **資料摘要不執行資料庫中的自訂程式。** 計算資料表摘要的帳號通常是資料庫的超級使用者，而資料表可能屬於其他帳號；摘要以資料列型別本身的輸出函式讀取內容（`record_out`），不會執行資料表擁有者可以自訂的型別轉換（以前的寫法會以超級使用者身分執行它，實驗室已重現並確認修正）。
- **只還原可信來源的備份。** 上傳的檔案在完整驗證前一律視為不可信：外層結構、加密認證、每個項目的大小與雜湊都要通過，路徑穿越、連結、多出或缺少的項目都會被拒絕；資料卷與映像封存另外完整檢查並重新產生（見上一節）。`.tar` 備份裡的 `backup.json` 只是說明，還原只以各應用封存檔內經過驗證的內容清單為準。但能解密只證明檔案在加密後沒有被修改，不能證明它來自哪一台設備；**未加密的上傳檔連這一點也無法證明**，所以還原前要另外確認信任它。還原的資料庫內容與設定檔會被應用直接使用。請只還原自己保管的備份檔。

## 已知限制

- **一次只能執行一個作業。** 備份、還原、驗證與建立未加密副本互斥；作業進行中也不能安裝或移除應用設定、不能刪除備份；同時進行中的上傳最多 4 個。
- **備份只保存在這台設備。** 排程備份也一樣，還不會自動複製到 NAS 或雲端等其他位置，請另外下載保存。保留規則有兩種：「每個應用保留最新幾份手動備份」在手動備份成功後套用，或在「清理備份」預覽後確認刪除；「保留最新幾份排程備份」在排程備份成功（或部分完成）後套用；上傳的備份只在勾選時刪除；還原前自動備份每個應用保留 3 份。沒有依時間（例如保留 30 天）的規則。
- **排程備份的限制。** 時間以設備的時間為準，以 5 分鐘為單位，會在設定時間後 5 分鐘內開始；設備沒有開機時只補最近的一次（下一次排程在 3 小時內就不補）；失敗或沒有執行時不會自動重試；尚未就緒的應用會被略過（部分完成）；一次只能有一個作業，排程時間有其他作業進行中時會延後開始。排程檢查需要安裝程式安裝並啟用的系統計時器；以安裝較舊來源的方式降版時，要另外停用它（見 [operations.md](operations.md)）。
- **本機備份不防磁碟故障。** 備份與應用資料通常在同一顆磁碟，請下載保存到其他位置。
- **上傳與下載速度。** 實驗室經真正的 Cockpit 362 以瀏覽器上傳 142 MB 的備份：目前的預設（每段 512 KiB、最多 4 MiB 未確認）6 次中位數 12.8 MB/s（9.8–16.8 MB/s），舊設定（64 KiB、2 MiB）為 6.7 MB/s；量測時主機負載很高（4 核心，1 分鐘平均負載約 8–20）。最終回歸中，從按下上傳到出現金鑰步驟（含傳送後的檢查）共 11.6 秒，下載 4.2 秒。以 12.8 MB/s 推算，1 GB 約需 1.3 分鐘、10 GB 約 13 分鐘；多 GB 的檔案未實測，實際速度取決於網路與設備。
- **未套用的設定變更。** 備份與還原前備份都會重新啟動寫入服務。若應用的設定檔已修改、但尚未重新啟動套用，這次重新啟動會讓新設定生效；如果因此改變了核對值，這份備份不保存資料核對快照，日後用它還原（包括失敗時的自動回復）都無法比對資料。請先套用（重新啟動）或撤回設定修改，再備份或還原。「快照在備份期間改變就不保存」由單元測試驗證；以未套用的設定變更觸發的情況沒有在實驗室設備重現。
- **PostgreSQL。** 支援 PostgreSQL 10 以上。三種方式的限制：
  - 單一資料庫：只備份目錄列出的資料庫，不含角色等叢集層級設定；匯入時所有物件改由目錄指定的資料庫帳號擁有，不還原原本的擁有者與授權；資料庫執行個體中有目錄未宣告的資料庫時，不能原位還原；目標設備的主版本不可低於備份時。
  - 整個執行個體：目錄的資料庫帳號必須是映像建立的初始超級使用者（`POSTGRES_USER`），還原時新建的執行個體只有這個帳號；備份 template0、template1 以外的每個資料庫（範本資料庫也保留）；有不接受連線的資料庫時無法備份，原位還原的相容性檢查也會拒絕（它們不在任何備份中，還原後會永久遺失），請先允許連線或改用冷備份；template1 中自訂的物件不保留（相容性檢查會提醒）；不保留非預設的表空間；目標設備的主版本不可低於備份時，映像必須有資料庫用到的每個擴充功能（例如 pgvector）。映像的初始化程式（例如 postgis、timescaledb）在新的執行個體建立的資料庫，還原時以備份內容重建。
  - 冷備份：還原的設備必須是相同的 PostgreSQL 主版本與 CPU 架構，預檢不檢查版本。
  - 實驗室只驗證過 PostgreSQL 16 還原到 16。
- **資料摘要的範圍。** `postgres-digest` 涵蓋一般資料表與序列，不涵蓋暫存表、擴充功能自己的物件、檢視、具體化檢視、外部資料表與大型物件；`files-digest` 不比對 socket、資料卷最上層資料夾本身，以及資料卷中檔案的 setuid／setgid，清單最大 1 GiB（約 200 萬個項目）。每項摘要在備份時完整讀兩次資料，會延長寫入暫停。兩次讀取之間被寫入又改回原值的資料看不出來；冷備份的資料庫在第二次讀取之後、停止之前的寫入也看不出來，所以仍要把所有會寫入的服務列為寫入服務。PostgreSQL 11 以前讀取的摘要與 12 以後讀取的不比對（浮點數的文字格式不同）。
- **支援的資料形態有限。** 支援具名資料卷（還原時以預設選項重建）、應用自己設定目錄下的單一設定檔（每個最大 16 MiB，權限最多 0644）、Podman secrets（每個小於 512,000 bytes）。主機資料夾（每個應用最多 16 個，整個資料夾備份、沒有排除規則，還原時整個取代）與資料放在主機資料夾的資料庫（冷備份）已在實驗室（D1–D7）與參考主機驗證。冷備份的資料庫只能還原到 PostgreSQL 主版本相同的設備。資料卷中非目錄檔案的 setuid／setgid 與 `user.*` 以外的延伸屬性不保留，修改時間只保留到秒。
- **還原會停機並覆寫資料。** 還原期間應用停止服務；原位還原會覆寫備份之後寫入的資料（保留在還原前備份中）。
- **跨設備範圍。** 只驗證相同架構（x86_64）與上述系統版本；兩台實驗室設備是同一台實體主機上的獨立容器，尚未在兩台實體設備之間演練。
- **金鑰管理。** 不能輪替設備金鑰，也不能從頁面移除已匯入的金鑰。
- **停止的先後。** 寫入服務一次停止，沒有在 Quadlet 寫明 `After=` 的服務會同時停止，主服務可能一開始就停（見「備份如何保持資料一致」的量測）。
- **尚未實測的情境。** 冷備份還原到 PostgreSQL 主版本不同的設備；整個執行個體方式的跨主版本還原與 ICU 語系資料庫在實驗室設備上的還原（ICU 只在一次性容器中試過；pgvector 映像的原位與全新部署還原已在實驗室設備實測）；多 GB 備份與超過 8 GiB 的單一項目；不同 CPU 架構；兩台實體設備之間的還原；「不建立還原前備份，直接還原」選項（只有單元與頁面測試）；在真正的 Cockpit 頁面上按「建立加密金鑰」（實驗室設備的金鑰是在較早的整合輪直接呼叫 helper 建立，之後都沿用它）。這一版頁面上的新流程（加密選擇、下載未加密版本、資料核對與停機時間的結果、應用設定、清理備份）除了頁面 fixture 測試，也已經由兩台實驗室設備上真正的 Cockpit 頁面操作實測，見最後一節。
- **正式應用需逐一接入。** 每個應用需先完成目錄項目審查與實驗室演練；參考主機上已接入的 19 個應用見 [production-onboarding.md](backup/production-onboarding.md)。

| 整個執行個體方式 | 實驗室應用 `woowbk-inst`（pgvector 映像；應用以 `oc_admin` 登入、密碼只在應用資料卷；`odoo` 角色擁有兩個資料庫）：由「應用設定」草稿的「整個執行個體」寫法產生；備份時資料庫不停止；破壞後原位還原與另一台設備全新部署還原，角色與密碼雜湊、成員、設定、擁有者、定序、權限、註解、內容、擴充功能版本（vector 0.8.7）與索引都等於備份時，`odoo` 以原密碼登入，應用正常，資料摘要一致 |
| 加密選擇（頁面與指令） | 關閉「預設加密備份」需要確認；建立頁可選擇加密或不加密；沒有設備金鑰的設備可建立不加密的備份，加密的備份仍需要金鑰；還原前備份跟隨設定；從頁面下載的加密 `.tar` 用 tar 就能列出 `backup.json`、`README.txt` 與應用封存檔，照 README 指令以緊急金鑰解開後每個項目的 SHA-256 都正確；未加密副本可用 tar 與 gzip 解開、從頁面立即刪除；在另一台設備上傳未加密的備份時，預檢警告來源無法驗證、確認時需要另外勾選，還原後資料摘要一致 |
| 被修改的 `backup.json` | 改了應用封存檔的 SHA-256：上傳時拒絕；只改說明文字：可上傳，但檢視、驗證與還原都判定「備份檔已損毀」，資料不變 |
| 清理備份（頁面與指令） | 依應用保留最新 5 份的預覽與引擎計算相同，可取消勾選，確認後刪除並記錄；手動備份成功後依原則刪除較舊的手動備份；被強制終止的還原需要的還原前備份與來源備份受保護、不會刪除，直到之後的還原成功 |
| 停機 | 見「備份如何保持資料一致」與「在同一台設備還原」的量測（兩種 `After=` 寫法、與前一版引擎比較） |
| 既有情境 | `format_e2e.py`（格式 2、加密選擇、舊格式仍可驗證與還原）105 項、`dirs_e2e.py`（主機資料夾 D1–D7）256 項、`cli_e2e.py`（同機、跨設備、故障、回復、中斷、取消、洩漏）122 項全部通過（2026-11-14 更正：`dirs_e2e.py` 的 `prep` 會把 woowbk-dirs 的目錄項目換回不含資料摘要的夾具，所以 D1–D7 實際上沒有資料摘要核對；woowbk-dirs 的資料摘要由 `strengthen_e2e.py digests` 涵蓋）；`hardening.py`（惡意封存檔 28 種、空間不足、資料庫匯出失敗、各階段強制終止、還原中重新開機、約 600 MiB 的資料卷、安裝與回退、巢狀 tar 的符號連結攻擊、檔案保真度、全新部署的殘留物與中斷、洩漏）全部通過；格式 2 的惡意案例在設備內重新封裝，巢狀 tar 被改造的備份現在在「驗證」就失敗。完整的安裝回退鏈在實驗室安裝紀錄中曾被實驗室專用修補改過的那一筆被安裝程式正確拒絕，改以一組乾淨的安裝紀錄驗證 |

### 2026-11-14 審查修正與最終回歸

整合後的安全與正確性審查指出的問題都已修正，各有單元測試或實驗室測試（細節見 [CONTRACT.md](backup/CONTRACT.md) 開頭的修訂說明與第 13 節）。實驗室的重點結果：

| 項目 | 結果 |
| --- | --- |
| 資料摘要不再執行資料庫中的自訂程式 | 一次性的 PostgreSQL 16 容器中，沒有超級使用者權限的資料表擁有者定義了自訂型別轉換；修正前的摘要寫法以超級使用者身分執行它（在資料庫容器內寫出檔案），引擎的寫法不會；沒有自訂轉換的資料表摘要與修正前完全相同 |
| 備份期間有寫入者 | 目錄沒有停止的容器與資料庫容器內的工作持續寫入時：備份兩次讀取的資料庫摘要不同，不保存這一項；在寫入時還原失敗的備份，還原前備份同樣不保存，自動回復完成、應用沒有停在暫時停用；寫入者仍在時還原一份正常的備份，資料仍在變動的那一項顯示「未比對」，還原完成 |
| 整個執行個體方式 | 重寫後的還原（每個資料庫都以備份內容重建，包括 `postgres` 與映像建立的資料庫；以初始化時間確認是新的執行個體；套用角色定義後再確認管理帳號）在原位與另一台設備的全新部署都通過：角色與密碼雜湊、成員、設定、擁有者、定序、權限、註解、內容與索引都等於備份時 |
| 既有情境 | `cli_e2e.py` 122 項、`hardening.py` 551 項、`format_e2e.py` 105 項、`dirs_e2e.py` 255 項、頁面 fixture 52 項、真正頁面 68 項全部通過；單元測試三種環境各 856 項 |

實驗室中也遇到一次失敗：用來模擬寫入者的另一個容器，在應用容器停止後有幾秒連不上資料庫，還原前備份兩次讀取剛好相同而保存了摘要，自動回復時它又寫入兩列，回復因此失敗，應用停在暫時停用；之後以那份還原前備份再次還原就恢復了。這次失敗促成了「還原時摘要不一致會再讀一次」的修改。正式主機沒有安裝這一版。
