# Cockpit 側邊欄整合本機 Pi Web：研究與建議

日期：2026-11-13；狀態：研究，未建置入口、未更改 Cockpit、Pi Web、網路或權限。

## 目標

使用者登入 Cockpit 後，點選側邊欄「Pi Web」，在右側內容區操作目前這台設備的 Pi Web，體驗類似 Home Assistant ingress。Pi Web 的主機、身分與是否單一登入仍需使用者確認。本文件不將 mock 或網頁載入當成對話已測通。

## 此主機實際觀察

- Cockpit 362 的 socket listening，使用 HTTPS 9090。Cockpit 套件可透過 `manifest.json` 在側邊欄註冊頁面；現有 `/usr/local/share/cockpit/woowtechservices` 是例子。
- 目前監聽 `127.0.0.1:30141` 的是本機使用者 systemd 服務 `pi-web.service`，執行 Node／Next.js 進程；其 unit 是 `/home/woowtechopenclaw/.config/systemd/user/pi-web.service`，執行腳本在 `~/.local/share/pi-agent/bin/pi-web-start.sh`。不可誤認為同名 Podman unit 或直接啟動另一套 Pi 實例，否則可能改用不同資料與對話。
- HTTP 唯讀探測：`GET /` 回 307 到 `/login`；未認證 `GET /api/sessions` 回 401。這表明這一實例目前有登入門檻，不代表已完成所有安全測試。
- 本機安裝的 pi-web package metadata 版本顯示 0.10.0；需注意 runtime／建置版本可能不一致，後續應由實際執行產物與 UI 再確認。
- 本機登入程式碼將 Pi Web session cookie 設為 `HttpOnly`、`SameSite=Lax`、`Path=/`，`Secure` 依請求環境判定；若 iframe 為跨站，需實測瀏覽器是否傳送 cookie。不同 port 並不構成 cookie 隔離，不能只依 port 做安全區分。
- 本機程式碼使用根路徑如 `/api/...`，SSE `EventSource` 用於對話事件；還有終端 API 與 service worker 相關資源。因此把應用簡單放進 `/pi/` 子路徑可能造成 API、靜態資產、登入導向與 service worker 路徑錯誤；需要支持 basePath 的建置或適配，不能只改 iframe 的 src。
- 目前登入的 Pi Web 是宿主原生實例；Podman Pi Agent 專案的版本與認證描述不必然適用此實例。該專案 README 有較舊「Pi Web 自身沒有登入」的描述；本機測得 307/401 及安裝程式碼顯示有密碼 session，切勿混用兩者結論。

## 技術選項

| 選項 | 可行方向 | 主要條件與限制 |
| --- | --- | --- |
| A. 獨立 HTTPS origin + Cockpit 套件 iframe | 在 Cockpit 插件中顯示以獨立主機名稱／origin 提供的 Pi Web；專用受控反向代理指向本機 loopback，保留 Pi Web 自身登入。 | 必須驗證 Pi Web、Cockpit 包裝頁和瀏覽器的 `frame-src` / `frame-ancestors`／X-Frame-Options、cookie SameSite、CSRF／Origin、SSE／WebSocket 及 TLS。不同 port 是不同 origin，但 cookie 不以 port 隔離；若不同 hostname 又可能碰到第三方 cookie 限制。根路徑應由該獨立 origin 提供，避免子路徑破壞。這是優先 PoC 候選，尚未實測。 |
| B. 統一反向代理，同 origin 分路徑 | 以共同入口分別轉給 Cockpit 與 Pi Web，右側顯示 iframe。 | Pi Web 根絕對路徑、登入、Next.js assets、service worker 需要真正的子路徑支援；單純 proxy_pass 前綴不夠。應用同源也可能擴大對 Cockpit origin 的存取能力，需嚴格信任和安全審查。不得假設瀏覽器同源即自動完成安全單一登入。 |
| C. 單獨頁簽或獨立入口 | 側邊欄顯示說明及在新頁籤打開 Pi Web。 | 作為 iframe／瀏覽器政策不相容的後備方案；不符合優先目標的右側嵌入體驗。仍需安全發佈與認證。 |
| D. Cockpit channel 或改寫 Pi Web 前端 | 研究以 Cockpit 前端 API 作代理，或將 Pi Web 功能重新做成 Cockpit package。 | Cockpit 官方討論的外部 channel 為探索方向，不保證完整 Next.js 的路由、cookies、SSE、WebSocket 可工作；若自行重做介面，維護成本與版本漂移很高，不作直接假定。 |

Cockpit 官方的 [Embedding and Integrating Cockpit](https://docs.cockpit-project.org/cockpit-guide/368/guide/embedding.html) 主要討論「把 Cockpit 嵌入其他應用」，不能倒過來宣稱已支援任意外站嵌入 Cockpit。Cockpit 社群 [外部應用與 session 討論](https://github.com/cockpit-project/cockpit/discussions/19603) 中也沒有承諾一般用途的現成 ingress。Cockpit 套件入口參考 [362 packages](https://docs.cockpit-project.org/cockpit-guide/362/guide/packages.html)。

## 驗證過程建議

1. 啟動隔離 mock upstream，保留正式服務，驗證 Cockpit `manifest` 選單與 iframe 欄寬、高度、桌面與手機收合。
2. 決定 Pi Web 位址與代理 origin，使用測試憑證與隔離代理；檢查未登入、錯登入、登出、重新登入、session 過期與不同 Cockpit 使用者是否有正確存取邊界。Cockpit 登入成功不等於 Pi Web 已登入。
3. 僅透過授權的測試使用者與測試資料接入現有 Pi Web，驗證首頁、靜態資源、登入 cookie 與受保護 API；輸出脫敏狀態、不得讀取或列印 provider key、對話內容或 session cookie。
4. 驗證真實 SSE 持續串流與斷線重連、上傳下載、設定、MCP 與終端；若啟用 WebSocket 功能，實測 upgrade。驗證手機、1440／1024／768／390／320px 與小高度，保留鍵盤操作及頁面焦點。
5. 使用測試對話送一次經授權的非破壞性訊息，明確記錄是否取得真正 assistant 回覆；如涉及模型額度或資料權限先依現場狀況決定。未做過真實測試就不可宣稱實際對話通過。
6. 驗證直接存取代理、未登入與 Cockpit 登出後的存取；若保留 Pi Web 自身登入，Cockpit 登出不必然讓 Pi Web session 同步失效，必須以實測結果向使用者說明，若需聯動登出則另設計。
7. 正式整合先記錄變更／部署方式、資產來源、回退、服務依賴與不影響既有 Pi Web 資料；與 Cockpit repo 目前由其他對話處理的備份功能互不覆寫。

## 重要權限邊界

Pi Web 是強權限代理操作介面，後端以 pi-web 服務帳號可存取的資料和工具權限執行。能進入 Cockpit 的每位使用者是否也應能使用同一 Pi Web，應明確設計，不能只因登入 Cockpit 就自動假設全部允許。不可公開 `127.0.0.1:30141` 到全網、不可把 Pi Web 密碼寫到前端、URL 或 Git、不可無條件移除 Origin／CSRF 防護。若採 Cockpit 單一登入，應另行研究可信身份傳遞、逐使用者授權和登出語意，未驗證前不能宣稱已完成 SSO。
